## 3. ГЛАВНОЕ: условие краша (это то, на чём я потерял больше всего времени)

### 3.1. Формат config_2 (проверено)

| Смещение | Размер | В оригинале | Смысл |
|---|---|---|---|
| 0 | 1 | `02` | номер варианта (сверяется с зашитым в exe; при несовпадении — `ERROR: variant does not match`, `exit(-1)`) |
| 4 | 4 | 1075 | `shell_len`, печатается программой |
| 8 | 4 | 2500 | `dst_len`, печатается программой |
| 16 | 2 | 1075 | дубль `shell_len` младшим словом |
| 18 | 2 | 2500 | дубль `dst_len` младшим словом |
| 20…47 | — | — | прочие поля шапки |
| 48 | 6 | `/start` | маркер начала данных |
| 54… | 1069 | буквы | полезная нагрузка |

Программа печатает: `VERSION: 0.3`, `Variant: 2`, `read config:  shell_len N  dst_len M`,
`buffer: <строка>`. **`buffer:` печатает не более 2500 символов** — это и есть размер
приёмного буфера (константа в стеке). Это наблюдение — ключ ко всему.

### 3.2. Что НЕ влияет (я проверял и потерял на этом часы)

- **допись в конец файла** (любой длины: 1 КБ, 5 КБ, 100 КБ) — печатается те же 1069
  символов, краха нет. Байты после исходной нагрузки в копирование не попадают;
- изменение **одного** поля на `0xFFFFFFFF` при коротком payload — краха нет;
- `fread` в цели читает файл **целиком** (`malloc(размер_файла+1)` → `fread`), поэтому
  «огромный файл» сам по себе ничего не ломает.

### 3.3. Что работает (воспроизводится)

```python
import struct
orig = open("lab1/vulns/config_2", "rb").read()      # 1123 байта
d = bytearray(orig)
d[54:54] = b"b" * 5120        # ВСТАВКА сразу за маркером /start (не в конец файла!)
d[8:12]  = (0xFFFFFFFF).to_bytes(4, "little")   # dst_len
open("lab1/work/config_2", "wb").write(bytes(d))
# затем запустить lab1/work/vuln2.exe с рабочим каталогом lab1/work
```

Результат: `0xC0000005` (ACCESS_VIOLATION). Замеры: **нативно 5/8…10/10**,
под отладчиком 5/6 (зависит от раскладки памяти — перезапись адреса возврата не всегда
даёт обращение по недопустимому адресу).

**Механизм (подтверждён регистрами):** данные из позиции за `/start` копируются в
**константный буфер 2500 байт на стеке**; длина берётся из шапки и **не сверяется с
размером буфера**. В эталонном краше копируется 6188 байт (`EAX=EDX=0x182C`), падение
происходит внутри копирования.

**Минимальность:** критично поле на **смещении 8** (`dst_len` = `0xFFFFFFFF`) +
достаточно длинные данные **сразу за маркером** (порог ≈ 2500–5000 байт: при 2500 —
единичные падения, при 5000+ — устойчиво). Поля на смещениях 4 и 312 **не обязательны**.

**Простой рецепт для отчёта/скрипта:** «вставить много байт сразу после `/start` и
поставить `0xFFFFFFFF` в поле длины» — это ровно то, что делает найденный краш.

### 3.4. Ловушка, в которую я попал (не повторять)

Первый «краш», который я нашёл (правка смещения 312 на `0x7FFFFFFF`), **оказался
артефактом**: `read_config` делает `ftell` → `malloc(размер)` → `fread`, и если файл
`config_2` в этот момент перезаписывается другим процессом, условия гонки дают
`0xC0000005` при неизменном exe. У меня параллельно работал второй агент, писавший тот
же файл. **Правило: одновременно `lab1/work/config_2` пишет ровно один процесс.**
Проверять краш надо повторными прогонами (≥ 5–10) и, если возможно, нативно тоже.

## 4. IDA: почему не запускалась и что делать

**Симптом:** `ida.exe - System Error: The code execution cannot proceed because
MSVCP140.dll was not found` (и то же для `idat64.exe`). До этого был `0xC0000135`.

**Причина:** в системе **нет VC++ рантайма** (`msvcp140.dll`, `vcruntime140.dll`,
`vcruntime140_1.dll` отсутствуют в `System32` — проверено). IDA 7.7 собрана на VC++.

**Что я сделал:** скопировал эти три DLL из поставки Edge
(`C:\Program Files (x86)\Microsoft\Edge\Application\<версия>\`) в `C:\Tools\IDAPro77\`.
После этого `idat64.exe` **перестал падать с 0xC0000135** и стал доходить до проверки
лицензии (в логе: `License not yet accepted, cannot run in batch mode -> OK`).

**Правильное решение (рекомендую вместо копирования DLL):** поставить официальный
**Microsoft Visual C++ 2015–2022 Redistributable (x64)** — это одна установка, и она
закрывает вопрос для IDA и для будущих лаб (lab4: CodeQL/SonarQube тоже любят VC++).
Ссылка: `https://aka.ms/vs/17/release/vc_redist.x64.exe`.

**Второй барьер — лицензия.** Принять её можно **только в GUI** (одно нажатие «I Agree»);
программно не получилось: ни `HKCU\Software\Hex-Rays\IDA\LicenseAccepted=1`, ни
`%APPDATA%\Hex-Rays\IDA Pro\ida.reg` не помогают. После принятия GUI-версией
`idat64.exe -A ...` работает в batch-режиме.

**Запуск нашего скрипта (после принятия лицензии):**

```powershell
# файл ida/скрипт писать calls.txt рядом с собой, путь берётся от __file__
& 'C:\Tools\IDAPro77\idat64.exe' -A -L"scratch\ida.log" -S"<полный путь>\lab1\ida\find_calls.py" "<полный путь>\lab1\work\vuln2.exe"
```
Скрипт начинается с `idaapi.auto_wait()`, поэтому в GUI его можно выполнять сразу после
`File → Script file…`.

**Ожидаемый результат (уже получен независимым анализатором, файл `lab1/ida/calls.txt`):**

```
[input]  fopen   call 0x00401604
[input]  fread   call 0x004016A2
[unsafe] memcpy  call 0x004016CF, 0x00401FB4, 0x00401FFE, 0x004029A8, 0x00402B29,
                 0x00402D1A, 0x00403689, 0x0040706D, 0x00407A33
```

**Важно про IDAPython:** сборка IDA 64-битная, `idapyswitch --auto-apply` привязал
Python 3.12 — плагин `idapython3_64.dll` загрузился (в логе видны SyntaxWarning из

Python 3.10 x64 и повторить `idapyswitch --auto-apply`.

**Проверено на этом устройстве (не повторять эти шаги):**

- IDA **работает** после установки Visual C++ Redistributable и однократного «I Agree»
  в диалоге лицензии. Запускать только из `C:\Tools\IDAPro77`.
- `idat64.exe -A -L"<лог>" -S"<скрипт>" "<exe>"` **выполняет IDAPython-скрипт**, но
  **сам не завершается** после скрипта (висит с загруженной базой). Запускать в фоне или
  с таймаутом, результат забирать по файлу, потом убивать процесс.
- Пути в `-S` и к exe должны быть **абсолютными** (относительный путь IDA не находит:
  в логе `... : could not locate file`).
- База `lab1/work/vuln2.exe.id0/id1` уже построена — повторный запуск идёт быстрее.
- Импорты IDA видит: `get_import_module_qty()` → 4 модуля (func, KERNEL32, msvcrt×2),
  `enum_import_names` → 70 имён. Вызовы есть: у импортов есть `code xref` типа 3
  (`near call`) из адресов `0x408xxx` — это **заглушки** вида `jmp ds:__imp_fopen`.
- **НО** готовый `lab1/ida/find_calls.py` в этой базе выдаёт `call sites: 0` (находит
  4 импорта, но не находит вызовы). Причина — фильтр типов xref внутри скрипта
  (`CALL_XREF = {fl_CN, fl_CF, fl_JN, fl_JF}`) не пропускает тип 3. Не трать время на
  расследование: либо поправь фильтр (принимать все code-xref, кроме data), либо обойди
  IDA — адреса вызовов уже известны и подтверждены независимым разбором PE:
  `fopen 0x401604`, `fread 0x4016A2`, `sprintf 0x40154E`,
  `memcpy 0x4016CF, 0x401FB4, 0x401FFE, 0x4029A8, 0x402B29, 0x402D1A, 0x403689, 0x40706D, 0x407A33`.
- Заглушки удобно искать статически: байты `FF 25 <адрес слота IAT>` (по 6 байт),
  а код зовёт их относительным `E8`. Такой поиск даёт те же 12 вызовов.

## 5. Полезные технические знания (если понадобится отладка/трассировка)

1. **Точки останова `int3` в `.text` работают**, если ставить их по **фактической базе
   образа** (колбэк на `CREATE_PROCESS_DEBUG_EVENT`, `lpBaseOfImage`). Я потратил на это
   много времени: ставил по preferred base `0x400000` — не срабатывало.
2. **WOW64-точки останова**: 64-битный отладчик получает `STATUS_WX86_BREAKPOINT`
   (`0x4000001F`), причём `ExceptionAddress` — адрес 64-битной заглушки
   (например `0x77A787F8`), а настоящий адрес = `ctx.Eip - 1`. Проверять попадание надо
   по `Eip - 1`, а не по `ExceptionAddress`.
3. **Соответствие `EXCEPTION_RECORD`**: `ExceptionInformation` — `DWORD[15]`, НЕ `DWORD64[15]`,
   иначе смещается `dwFirstChance`.
4. **Дамп стека**: `ctypes.c_byte * N` даёт знаковые значения и падает на `bytes(buf[:n])`
   (ошибка `bytes must be in range`) — использовать `c_ubyte`.
5. **Поиск вызовов импортов без IDA** (MinGW-специфика этого бинаря): в `.text` есть
   таблица заглушек `FF 25 <IAT>` (по 6 байт: `FF 25 xx xx xx xx 90`), а код зовёт их
   относительным `E8`. Поэтому «наивный» поиск `FF 15` в `.text` находит всего 2 вызова
   (сами заглушки). Алгоритм: перечислить IAT из таблицы импортов → найти `FF 25` →
   найти `E8`, чья цель попадает в таблицу заглушек. Это и делает `scratch/pe_calls.py`.
6. **Парсинг PE**: в секции-заголовке порядок полей `vsize, va, raw_size, raw_ptr`
   (`struct.unpack_from("<IIII", data, off + 8)`) — я перепутал и получил мусор.
7. **DynamoRIO** требует, чтобы каталог конфигурации был доступен на запись:
   `DYNAMORIO_CONFIGDIR=<work>\dynamorio_config`. Если `%TEMP%` недоступен (например,
   запуск из-под песочницы агента), `drrun` возвращает код, который легко принять за краш
   цели, а в stderr пишет `process vuln2.exe registration failed: check config dir`.
   **Признак настоящего краша под drcov — наличие `drcov*.log` в рабочем каталоге.**
8. **Анти-отладки в цели нет** (проверял: нативно и под отладчиком ведёт себя одинаково).

## 7. Как сделать «просто и по-студенчески» (KISS-план)

Цель: минимум кода, который легко объяснить на защите.

1. **`fuzzer.py` (один файл, ~200 строк) — запуск через МЕНЮ, без флагов.**

   Пользователь хочет именно так: запустил `python fuzzer.py` — открылось меню, выбрал
   номер режима, он отработал и вернул в меню. Пункты:

   ```
   1  авторежим: последовательная замена байт граничными значениями (как в ТЗ)
   2  авторежим: покрытие (DynamoRIO drcov) + смена стратегий по покрытию  [доп. задание]
   3  замена одного байта
   4  замена нескольких байт
   5  допись в конец файла
   6  расширение / вставка внутрь (файл длиннее)
   7  поиск разделителей ,:=; и мутация вокруг них
   8  один запуск work/config_2 + регистры и стек, если упало
   9  длинный вход (вставка за маркером) — то, что реально находит краш
   0  выход
   ```

   Реализация — обычный `while True: print(...); input("> ")`, без argparse.
   Флаги можно оставить необязательным бонусом, но основной вход — меню.

   Внутри: `mut_byte`, `mut_multi`, `mut_boundary`, `mut_append`, `mut_expand`,
   `mut_delim`, `mut_long` (ключевая: вставить `b"b" * 5120` сразу за маркером `/start`
   и поставить `0xFFFFFFFF` в 4-байтное поле шапки).

   Запуск цели: `subprocess.run([exe], cwd=work)`; краш = код `0xC000xxxx`
   (`exit(-1)` при неверном варианте крашем **не** считать). При краше сохранять
   `crashes/crash_<N>.bin` и `crashes/crash_<N>.txt` (код исключения, регистры, дамп
   стека, список замен) — это пункт ТЗ про логирование ошибок вместе с заменами.

   Регистры проще всего снять своим мини-отладчиком на `ctypes` (`CreateProcessW` +
   `DEBUG_ONLY_THIS_PROCESS`, `WaitForDebugEvent`, `Wow64GetThreadContext`);
   грабли этого кода уже собраны в §5.2–5.4 — прочитай их до написания.
2. **Режим 1**: цикл по всем смещениям × граничные значения (на месте), затем вторая
   фаза — то же на файле с вставкой за маркером. Вторая фаза находит краш практически
   сразу (на первом же 4-байтном смещении).
3. **Режим 2**: `drrun -t drcov` (через `DYNAMORIO_CONFIGDIR`), считать BB, хранить
   очередь входов, давших новые BB; в `adapt.log` писать смены стратегии по сигналам
   `gain` / `shrink` (BB_run < BB_parent) / `plateau` — это доп. задание.
   Проверенный ориентир: базовое покрытие 499 BB, за прогон поднимается до 501–504 BB.
4. **IDA**: см. §4 — рабочий запуск есть, грабли с фильтром типов xref учти.
5. **x32dbg**: открыть `work\vuln2.exe`, положить в `work` краш-конфиг, снять
   скриншоты: адрес приёмного буфера, адрес saved EIP (`EBP+4`), момент падения.
7. **Отчёт**: каркас в `lab1/report/lab1_report.md` — можно упростить, факты верные.

**Порядок, экономящий время:** сначала краш (п. 1–2, он уже известен), затем cov-режим
и доп. задание, затем IDA (её настройка не зависит от остального), затем отладчик и
отчёт.
