`config_2`, показать покрытие через DynamoRIO, реализовать адаптацию алгоритма по

## 3. Уязвимость и условие краха (переоткрывать не нужно)

Формат `config_2`: байт 0 — номер варианта (не трогать!), смещение 4 — `shell_len`,
смещение 8 — `dst_len`, смещение 48 — маркер `/start`, с 54 — полезная нагрузка.

Данные из позиции за `/start` копируются в константный буфер **2500 байт на стеке**;
длина берётся из шапки и **не сверяется** с размером буфера. Краш требует одновременно:

1. данные лежат **сразу за маркером** `/start` (допись в конец файла не влияет!);
2. данных больше 2500 байт;
3. в шапке завышено поле длины — рабочее смещение **8** (`0xFFFFFFFF`), смещение 4 усиливает.

Минимальный рецепт: `config[54:54] = b"b" * 5120` + `config[8:12] = FFFFFFFF`.

## 5. Фаззер `lab1/fuzzer.py`

### 5.1. Мутации (все пункты ТЗ)

| Функция | Что делает | ТЗ |
|---|---|---|
| `mut_byte` | замена одного байта | ✔ |
| `mut_multi` | замена нескольких байт | ✔ |
| `mut_boundary` | граничные значения: `00, FF, FFFF, FFFFFF, FFFFFFFF, FFFF/2, FFFF/2±1, 7FFFFFFF, 80000000` | ✔ |
| `mut_append` | допись в конец файла | ✔ |
| `mut_expand` | вставка внутрь / удлинение строк | ✔ |
| `mut_delim` | поиск разделителей `,:=;` и мутация вокруг них | ✔ |
| `mut_field` | прицельный перебор 4-байтных полей шапки | следствие анализа формата |
| `mut_inject` | вставка длинных данных за `/start` + порча поля длины | **находит краш** |

Байт 0 (номер варианта) не мутируется никогда — иначе цель выходит с `exit(-1)`.

### 5.2. Запуск и детект ошибки

* запуск: `subprocess.run([work\vuln2.exe], cwd=work)`; цель читает `config_2`
  из своего каталога;
* краш = код `0xC000xxxx` (в Python — отрицательный `exit_code`); `exit(-1)` при
  неверном варианте крашем **не** считается;
* при краше — прогон под мини-отладчиком на `ctypes`
  (`CreateProcessW` + `DEBUG_ONLY_THIS_PROCESS` + `WaitForDebugEvent` +
  `Wow64GetThreadContext`): код исключения, `EAX…EFLAGS`, дамп стека;
* сохраняется пара файлов: `crashes/crash_<дата>.bin` (вход) и `.txt`
  (исключение, регистры, стек, список произведённых замен относительно оригинала).

### 5.3. Логирование

| Файл | Содержимое | В git |
|---|---|---|
| `logs/seq.log` | номер прогона, проход, смещение, было→стало, статус, код возврата, размер файла | нет |
| `logs/cov.log` | то же + `BB_run` / `BB_parent` / `BB_global` | нет |
| `logs/adapt.log` | смены стратегий: `run, from→to, reason, BB_run, BB_parent, BB_global` | **да** (доказательство доп. задания) |
| `crashes/*.txt` | код ошибки, регистры, стек + произведённые замены | **да** |

### 5.4. Меню (основной интерфейс)

```
 1  SEQ-1: последовательная замена байт граничными значениями (ТЗ, авторежим)
 2  SEQ-2: удлинённый файл (вставка за /start) x поля шапки   <- находит краш
 3  COV:   покрытие DynamoRIO + смена стратегий по покрытию   <- доп. задание
 4  COV-контроль: фиксированная стратегия или 4 по кругу без обратной связи
 5  замена одного байта (вручную)          6  замена нескольких байт (вручную)
 7  дописать в конец файла (вручную)      11  вставить внутрь / удлинить (вручную)
 8  найти разделители ,:=; и мутировать   12  увеличить значение поля шапки (вручную)
 9  один запуск work/config_2 (вывод цели, регистры и стек при падении)
10  статистика: журналы, краши, корпус     0  выход
```

Плюс необязательные флаги (`--seq`, `--cov`, `--max-runs N`) для воспроизводимых
команд в отчёте.

## 6. Доп. задание: адаптация алгоритма по покрытию

### 6.1. Обоснование метрики (обязательно в отчёте)

`BB_global` (объединение базовых блоков по всем прогонам) монотонно растёт и
уменьшиться не может. Поэтому «покрытие стало меньше» измеряется двумя способами:

1. **покрытие одного прогона против родителя**: `BB_run < BB_parent` — маршрут
   нового входа короче маршрута файла-родителя (мутация сломала разбор конфига);
2. **прирост покрытия**: 30 прогонов подряд не дали ни одного нового BB —
   покрытие растёт всё меньше.

### 6.2. Алгоритм (весь целиком)

Четыре стратегии, активна ровно одна: `byte → boundary → append → inject` (по кругу).

```
shrink = 0        # сколько раз ПОДРЯД маршрут короче родителя
since_gain = 0    # сколько прогонов ПОДРЯД без нового покрытия

каждый прогон:
    BB_run, BB_parent, новые_BB = прогон_под_drcov()

    если новые_BB:                      # покрытие выросло
        since_gain = 0; shrink = 0
        сохранить вход в corpus/ как будущего родителя
    иначе:
        since_gain += 1

    shrink = shrink + 1 if BB_run < BB_parent else 0

    если shrink >= 3 или since_gain >= 30:      # ← вся адаптация
        стратегия = следующая по кругу
        shrink = 0; since_gain = 0
        запись в adapt.log(run, from→to, reason, BB_run, BB_parent, BB_global)
```

Пороги `3` и `30` — константы, подобраны экспериментально (в отчёте пояснить).

### 6.3. Доказательство работы

* `logs/adapt.log` — таблица смен стратегий с причиной и покрытием;
* рост покрытия **498 → 501…504 BB** (ожидаемые `gain`-события на стратегии `inject`);
* сиды в `corpus/` (требование ТЗ «сохранение изменённых байт с учётом влияния на покрытие»);
* **контрольный прогон с зафиксированной стратегией** (адаптация выключена) — покрытие
  почти не растёт, краш не находится: наглядная разница «с адаптацией / без».

## 9. Грабли (собраны ранее, не наступать)

* **Один писатель**: `work/config_2` не должен писаться двумя процессами одновременно —
  иначе получаются ложные краши (условия гонки в `read_config`).
* **Допись в конец файла не влияет** на копирование; влияет только вставка за `/start`.
* Одного испорченного поля мало: нужны и длинные данные, и завышенная длина.
* `drrun` без `drcov`-лога = сбой инструментирования, а не краш цели; каталог
  `DYNAMORIO_CONFIGDIR` должен существовать заранее.
* В отладчике адреса считать от **фактической** базы образа, не от `0x400000`;
  для WOW64-точек останова реальный адрес = `Eip - 1`; в `EXCEPTION_RECORD`
