## Этап 2 — фаззер

Файлы (stdlib: `argparse`, `ctypes`, `pathlib`, `struct`, `subprocess`, `hashlib`):

| Файл | Роль |
|---|---|
| `fuzzer.py` | меню и CLI |
| `mutations.py` | мутации из ТЗ |
| `adapt.py` | планировщик стратегий по покрытию (доп. задание) |
| `runner.py` | запуск с/без `drrun`, таймаут, без окна WER (`SetErrorMode`) |
| `coverage.py` | разбор `drcov`, множество BB по двум модулям |
| `debugger.py` | `DEBUG_ONLY_THIS_PROCESS`, Wow64-CONTEXT, дамп стека по ESP |

Меню:

1. Авто: последовательная замена байт (граничные значения)
2. Авто: coverage-guided очередь + адаптация стратегий
3. Замена 1 / нескольких байт
4. Допись в файл
5. Расширение / удлинение
6. Поиск разделителей `,:=;`
7. Один запуск + регистры, если упало

CLI те же режимы: `python fuzzer.py auto --seq`, `python fuzzer.py auto --cov`, …

**Последовательный авторежим:** каждое смещение × `0x00`, `0xFF`, `0xFFFF`, `0xFFFFFF`, `0xFFFFFFFF`, половины и ±1 из ТЗ. Стоп: краш или конец прохода.

**Coverage-режим (`auto --cov`):** первый сид — оригинальный `config_2`. Запуск: `bin32\drrun.exe -t drcov -- vuln2.exe`. Новый BB в `vuln2.exe` или `func.dll` → сид в очередь. Мутации не равновероятны: текущую стратегию выбирает `adapt.py` (см. ниже). Стоп: краш, плато после обхода всех стратегий, или `--max-runs`.

### Адаптивный планировщик (доп. задание)

Формулировка: менять алгоритм фаззинга по результатам покрытия; если покрытие становится меньше — переключиться так, чтобы покрытие выросло. Алгоритм свой, описать в отчёте.

**Почему «меньше» — это не глобальный union.** Глобальное множество BB только растёт. «Покрытие уменьшилось» считаем **на одном прогоне** относительно родителя:

| Сигнал | Условие | Смысл |
|---|---|---|
| `gain` | есть BB, которых не было в глобальном множестве | мутант интересный, в очередь |
| `shrink` | BB_run < BB_parent и нет новых BB | путь короче (ранний выход / ошибка разбора) |
| `plateau` | W подряд прогонов без новых BB | стратегия выдохлась |
| `crash` | исключение | успех, не считать shrink |

Краш и таймаут в планировщик как shrink не отдаём: краш — стоп и сохранение; таймаут — отбросить прогон.

**Стратегии** — ровно типы мутаций из ТЗ, одна активна в момент времени:

`byte` → `multi` → `boundary` → `append` → `expand` → `delim`

Стартовая: `byte`. У каждой вес (изначально 1). Выбор при ротации — наибольший вес, при равенстве та, которой давно не пользовались.

**Правила (после каждого прогона):**

1. `gain` — вес текущей стратегии ×2 (потолок 16); обнулить счётчики shrink/plateau; сид в очередь.
2. `shrink` — вес текущей ×0.5 (пол 0.25); `shrink_streak += 1`. После **3** shrink подряд: немедленная смена. Порядок отката (это и есть «придумать самим»): **`append` → `expand` → `delim` → `boundary` → `byte` → `multi`**, пропуская уже текущую. Смысл: in-place порча байт часто ломает разбор и режет покрытие; допись/удлинение сохраняет исходные байты и может открыть новые пути (в том числе overflow по длине).
3. `plateau` — после **W=20** прогонов без `gain`: взять наименее недавно использованную стратегию, увеличить «энергию» (больше байт / длиннее допись).
4. Не дёргать стратегию каждый одиночный shrink — только по порогу 3. Каждая смена пишется в лог.

**Лог** `lab1/fuzzer/adapt.log` (в git, в отчёт таблицей): номер прогона, `from → to`, причина (`shrink` / `plateau` / `gain-lock`), BB_run, BB_parent, BB_global. Без этого лога доп. задание в отчёте не закрыть.

Слепым остаёмся: в `adapt.py` нет `/start`, `shell_len`, смещений 4/8. Эвристика только по числам BB.

CLI тот же: `python fuzzer.py auto --cov`. Отдельный `--adapt` не плодить — доп. задание **и есть** поведение coverage-режима.

**Краш:** файл + текстовый лог (код, EAX…EIP, ESP/EBP, стек) в `lab1/crashes/`. Это артефакт отчёта и задел на lab2.

В код фаззера **не** зашивать `/start`, `shell_len`, смещения 4/8. Если слепой прогон за разумное время не крашит — остановиться и спросить, не включать «smart» самовольно.

Готово, когда: меню и CLI работают; оба авторежима гоняются; покрытие читается; `adapt.py` меняет стратегию по shrink/plateau и пишет `adapt.log`; на искусственном/найденном краше в логе есть код + регистры + стек; оригинал `vulns/config_2` бит-в-бит тот же.

## Этап 4 — прогон

Пользователь гоняет `auto --seq` и `auto --cov`. Агент смотрит логи и `adapt.log`. Краш не затирать.

Для доп. задания на прогоне `--cov` нужны видимые смены стратегии (хотя бы одна по shrink или plateau) и рост BB_global после смены — это скрины/таблица в отчёт.

Если краша нет: сначала диагностика (`drrun` жив, множество BB растёт, WER не блокирует, планировщик реально переключает стратегии). Smart-мутатор только после явного согласия.

Готово, когда в `lab1/crashes/` лежит конфиг, роняющий `vuln2.exe`, плюс лог регистров, и в `lab1/fuzzer/adapt.log` есть смены стратегии.

## Этап 5 — разбор

Пользователь в GUI, агент подсказывает адреса.

1. IDA: скрипт → `fread`/`memcpy` → псевдокод участка на C.
2. x32dbg: `work\vuln2.exe` с краш-`config_2`. Снять: размер буфера, адрес начала буфера, адрес saved EIP, регистры в падении (сверить с логом фаззера).
3. В отчёт: тип (нет проверки длины → stack overflow), ограничения эксплуатации, фикс (`shell_len <= dst_len` до `memcpy`).

`vuln*.exe` не патчить.

Готово, когда есть скрины/числа: буфер, saved EIP, дизасм с комментариями, псевдокод C.
