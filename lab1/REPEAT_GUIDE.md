| Компонент | Путь / версия | Проверка |
|---|---|---|

⚠️ **Подводный камень (проверено на практике).** `drrun` (DynamoRIO) при старте пишет
в свой каталог `C:\Tools\DynamoRIO\logs` и читает/пишет конфигурацию в
`C:\Tools\DynamoRIO`, то есть **вне рабочего каталога проекта**, а `idat64.exe` пишет
настройки **в реестр Windows**. Если запускать их «в песочнице», ограниченной только
каталогом проекта, получаем:

* `drrun … -t drcov` → код `0xC0000005` и **пустой** лог покрытия (легко спутать с крашем
  цели!); фаззер в этом случае честно печатает `Покрытие не получено — проверьте DynamoRIO`;
* `idat64.exe` → `[Error] Fatal registry error: Access is denied` и выход с кодом 1.

**Как быть:** запускать эти две команды из обычной консоли (PowerShell/CMD) под своей
учётной записью — тогда никаких ограничений нет. Фаззер сам подставляет
`DYNAMORIO_CONFIGDIR` в `lab1\fuzzer\cov\dynamorio_config`, поэтому его прогоны покрытия
работают и без ручной настройки. Всё остальное (сам фаззер, нативные запуски цели,
x32dbg) работает в любом случае.

Полезно: перед запуском Python-однострочников с русским текстом выполнить
`$env:PYTHONIOENCODING = 'utf-8'` (или `py -3.12 -X utf8 -c "..."`), иначе вывод падает
с `UnicodeEncodeError` (cp1252).

## Шаг 2. Разобрать формат `config_2` (10 минут)

**Зачем.** Фаззер должен мутировать осмысленные места. Формат восстанавливается по
поведению программы: где номер варианта, где длины, где маркер начала данных. Без этого
мутации «вслепую» бьют по случайным байтам (см. результат SEQ-1 на шаге 4).

**Как.**

```powershell
cd C:\Users\winuser\Documents\mbks_labs
py -3.12 -c "import struct; d=open('lab1/vulns/config_2','rb').read(); print('size',len(d)); print(' '.join('%02X'%b for b in d[:64])); print('shell_len',struct.unpack_from('<I',d,4)[0],'dst_len',struct.unpack_from('<I',d,8)[0],'marker_at',d.find(b'/start'))"
```

**Ожидаемый результат:**

```
size 1123
02 02 00 F4 33 04 00 00 C4 09 00 00 00 00 00 00 33 04 C4 09 08 00 00 00 B8 6B 33 00
B8 6B 33 00 B3 6B 33 00 00 00 00 00 00 00 6A 00 00 00 33 00 2F 73 74 61 72 74 76 62
shell_len 1075 dst_len 2500 marker_at 48
```

Читается так:

| Смещение | Значение | Смысл |
|---|---|---|
| 0 | `02` | номер варианта: при несовпадении цель печатает ошибку и делает `exit(-1)` — **этот байт не мутировать никогда** |
| 4 | `33 04 00 00` = 1075 | `shell_len` — печатается, на копирование не влияет |
| 8 | `C4 09 00 00` = 2500 | `dst_len` — **ключевое поле**: используется как размер приёмного буфера |
| 16 / 18 | `33 04` / `C4 09` | младшие слова тех же длин |
| 48 | `2F 73 74 61 72 74` = `/start` | маркер: данные копируются **с байта 54** |
| 1122 | `00` | нулевой терминатор в конце файла: поэтому допись в конец не попадает в копирование |

Проверить последнее утверждение полезно руками: скопировать конфиг, дописать 5120 байт
`'b'` в конец, ничего не меняя в шапке, запустить цель — она напечатает те же 1068
символов. Это ключ к пониманию, почему «просто длинный файл» не работает.

**В отчёт:** §3 «Формат конфигурационного файла» — таблица смещений + два следствия
(копируется строка за `/start` до нулевого байта; длина копирования берётся из поля
`dst_len`, то есть из файла).

## Шаг 6. Проверить воспроизводимость краха (5 минут)

**Зачем.** Падение вероятностное (ASLR + раскладка стека), и это обязательно надо
показать честно: сколько запусков из 10 падает у краш-конфига и сколько у оригинала.
Без этой проверки преподаватель справедливо спросит «а он вообще стабильно падает?».

**Как** (положить краш-конфиг как рабочий `config_2`, 10 запусков, потом вернуть оригинал):

```powershell
cd C:\Users\winuser\Documents\mbks_labs\lab1\fuzzer
$work = "."
Copy-Item crash\crash_<дата>.bin config_2 -Force
1..10 | ForEach-Object {
    $p = Start-Process -FilePath (Resolve-Path vuln2.exe) -WorkingDirectory (Resolve-Path $work) `
                       -PassThru -Wait -WindowStyle Hidden
    "запуск {0}: 0x{1:X8}" -f $_, $p.ExitCode
}
Copy-Item ..\vulns\config_2 config_2 -Force     # вернуть оригинал
```

> Для надёжности тот же опыт удобно повторить небольшим Python-скриптом
> (`subprocess.run(...).returncode & 0xFFFFFFFF`), как это сделано в `repro.log`.

**Ожидаемый результат.** У краш-конфига — 8–9 запусков из 10 падают с `0xC0000005`,

## Шаг 8. Дополнительное задание: смена алгоритма по покрытию (20–30 минут) ⭐

**Зачем.** Требование преподавателя: *«если фаззер видит, что покрытие становится меньше,
он меняет алгоритм своей работы для увеличения покрытия»*. Нужно реализовать, показать
журнал смен и честно сравнить с контролем.

**Идея, которую надо описать в отчёте.** Глобальное покрытие (объединение блоков по всем
прогонам) только растёт — буквальная трактовка «стало меньше» невыполнима. Поэтому
«уменьшение» измеряется двумя сигналами:

1. `shrink` — покрытие **одного прогона** меньше покрытия его родителя
   (`BB_run < BB_parent`): мутация сломала разбор конфига, маршрут стал короче;
2. `plateau` — 30 прогонов подряд не дали ни одного нового блока: прирост прекратился.

Реакция на любой из сигналов одна: стратегия меняется на следующую по кругу
`byte → boundary → append → inject`, счётчики сбрасываются, событие пишется в
`log/adapt.log`. Пороги 3 и 30 — «терпение» планировщика (обосновать: 3 отсекает
случайные короткие маршруты, 30 даёт стратегии честный шанс, но не даёт залипнуть).

**Как — четыре сессии, которые надо сделать и сравнить:**

```powershell
cd C:\Users\winuser\Documents\mbks_labs\lab1\fuzzer

# 1) адаптация по покрытию (меню, пункт 3; зерно 7 по умолчанию)
py -3.12 fuzzer.py                    # пункт 3 → 600

# 2) адаптация с другим зерном (независимый повтор)
py -3.12 -X utf8 -c "import fuzzer; fuzzer.prepare_work(); fuzzer.mode_cov(600, seed=99)"

# 3) контроль: те же 4 стратегии по кругу, но БЕЗ обратной связи (в меню пункта нет)
py -3.12 -X utf8 -c "import fuzzer; fuzzer.prepare_work(); fuzzer.mode_cov(600, fixed='cycle')"

# 4) контроль: одна фиксированная стратегия
py -3.12 -X utf8 -c "import fuzzer; fuzzer.prepare_work(); fuzzer.mode_cov(600, fixed='boundary')"
```

**Ожидаемый результат** (консоль и журналы; свежие контрольные цифры):

```
Покрытие оригинала: 497 блоков
Режим: смена стратегии по покрытию. Прогонов: 600
  прогон 30: стратегия byte → boundary (нет новых блоков)
  прогон 60: стратегия boundary → append (нет новых блоков)
  прогон 90: стратегия append → inject (нет новых блоков)
  крах 0xC0000005  прогон 91 (inject)  → crash_<дата>.bin
  прогон 91: +9 новых блоков (всего 506), стратегия inject
  прогон 106: стратегия inject → byte (маршрут короче родителя)
  …
Готово: 600 прогонов, блоков 497 → 506, сидов 1, смен 22, крашей 267
```

Сводка для отчёта (все четыре сессии — от базы 497 BB):

| Показатель | `mode_cov(600)` seed 7 | `seed=99` | `fixed='cycle'` | `fixed='boundary'` |
|---|---|---|---|---|
| Итоговое покрытие | **506** | 506 | 506 | **498** |
| Смен стратегии | 22 | 21 | 20 | 0 |
| Крашей | 267 | 196 | 272 | **0** |
| Событие `gain` | прогон 91 (`inject`, +9) | прогон 91 | прогон 91 | прогон 169 (+1) |

**Честный вывод, который обязательно надо оставить в отчёте** (§7.3): механизм
реализован и проверяем по журналу, но на этой цели он **не даёт выигрыша** перед
открытым перебором тех же стратегий — решающим оказывается само наличие стратегии
`inject` в наборе. Зато контроль с одной фиксированной стратегией (`boundary`) даёт
498 BB и **ноль** крахов, то есть смена алгоритма в принципе необходима.

**В отчёт:** §6 (очередь сидов и `cov/`) и §7 целиком: постановка и метрика, алгоритм
(псевдокод), таблица результатов, фрагмент `adapt.log`, честная оценка +
«направления улучшения» (сигнал `shrink` считать только на прогонах без падения).
Приложения: `log/adapt.log`, `log/cov.log`.

```
_main (0x401447)
└─ sprintf(Buffer, "config_%d", 2)                     [0x40154E]
└─ read_config("config_2", &cfg, &data)                [0x40156D]
   ├─ fopen [0x401604] → fseek/ftell → malloc → fread [0x4016A2]

```

Уязвимый участок — `vuln_func` (0x40158D):

```asm
0x00401596  mov  [esp+8], 9C4h        ; Size = 2500 (0x9C4) — РАЗМЕР БУФЕРА
0x004015A6  lea  eax, [ebp+var_9CC]   ; АДРЕС БУФЕРА = EBP-0x9CC
0x004015B4  mov  eax, [ebp+arg_8]     ; eax = dst_len (из файла!)
```

```asm

0x004022DE  mov  byte ptr [ebx+edx], 0  ; <== запись терминатора ЗА буфером
```

отключается, и в 2500-байтовый буфер копируется вся строка (6188 байт).

| Величина | Значение |
|---|---|
| размер приёмного буфера | `0x9C4` = **2500 байт** |
| адрес начала буфера | **`EBP-0x9CC`** |

## Шаг 11. x32dbg: подтвердить адреса своими глазами и снять скриншоты (20 минут) ⭐

**Зачем.** Отладчик даёт наглядное подтверждение: видно инструкцию, на которой падает
цель, и что `EBX` указывает на буфер с байтами `'b'`. Это ещё и скриншоты для отчёта.

**Подготовка:** положить краш-конфиг рабочим конфигом:

```powershell
Copy-Item C:\Users\winuser\Documents\mbks_labs\lab1\fuzzer\crash\crash_<дата>.bin `
          C:\Users\winuser\Documents\mbks_labs\lab1\fuzzer\config_2 -Force
start C:\Tools\x32dbg\release\x32\x32dbg.exe
```

**Порядок действий в x32dbg:**

1. `File → Open` → `lab1\fuzzer\vuln2.exe`.
2. **Узнать фактическую базу** (ASLR включён!): `Alt+M` (Memory Map) → строка `vuln2.exe`
   → скопировать базовый адрес (в артефактах это `0x00DF0000`; у вас будет свой).
3. `Ctrl+G` → ввести `база + 0x158D` (например `0x00DF158D`) → это начало `vuln_func`.
   `F2` — поставить точку останова, `F9` — запустить.
4. Когда отладчик остановится: в окне регистров взять `EBP`, вычислить адрес буфера
   `EBP - 0x9CC`, перейти туда через `Ctrl+G` — в дампе должны быть байты `62`
   (`'b'`, буфер залит `memset`). Полезно посмотреть и `EBP+4` — там лежит адрес
   возврата в `parse_string` (`base+0x1420`).
5. `F2` снять старую точку, `Ctrl+G` → `база + 0x22DE` (инструкция
   `mov byte ptr ds:[ebx+edx], 0`) → `F2`, затем `F9`.
6. Цель падает. Ожидаемая картина (см. `lab1\report\img\x32dbg_crash.png`):
   `EIP = база+0x22DE`, в строке состояния `byte ptr ds:[ebx+edx],0`, `ebx` указывает
   на `"bbbb…"`, в правой панели видны аргументы `"%s"` и строка из `'b'`;
   `EDX = 0x182C` (6188) — длина скопированной строки.
7. `Win+Shift+S` — снять два скриншота: (а) момент падения, (б) дамп по адресу буфера.
   Сохранить как `lab1\report\img\x32dbg_crash.png` и `x32dbg_buffer.png`.

**Альтернатива без отладчика:** те же регистры и стек лежат в
`lab1\fuzzer\crash\*.txt` (их снимает мини-отладчик фаззера) — их можно использовать
в отчёте, а x32dbg нужен ради скриншотов и «ручного» подтверждения.

**В отчёт:** §8.7 — регистры/стек + два скриншота; отметить, что абсолютные адреса
меняются от запуска к запуску (ASLR), а постоянны относительные: `EBP-0x9CC`, `EBP+4`,
2512 байт, `base+0x22DE`.

## 3. Грабли, на которые уже наступали (не повторять)

| Симптом | Причина | Что делать |
|---|---|---|
| `drrun` возвращает `0xC0000005`, drcov-лог пустой | нет доступа на запись в каталог DynamoRIO / запуск в ограниченной песочнице | запускать из обычной консоли; `DYNAMORIO_CONFIGDIR` должен указывать на **существующий** каталог (фаззер делает это сам) |
| `Fatal registry error: Access is denied` при старте IDA | IDA пишет настройки в реестр, ограниченная песочница это блокирует | запускать вне песочницы (обычная консоль) |
| `Нет файлов рядом с fuzzer.py: …` | не выполнен шаг 0 (рабочие копии цели) | `Copy-Item lab1\vulns\vuln2.exe,lab1\vulns\func.dll,lab1\vulns\config_2 lab1\fuzzer\ -Force` |
| Файл испортили, а цель не падает | данные дописаны **в конец** файла — их отсекает нулевой байт на смещении 1122 | вставлять данные **сразу за `/start`** (смещение 54) |
| Испортили поле длины, падения нет | нужно **одновременно** и длинные данные за маркером, и завышенный `dst_len` (смещение 8); поле 4 (`shell_len`) на копирование не влияет | смотреть §8.8 отчёта |
| Следующий прогон идёт «не от того файла» | ручные режимы (пункты 4–9) и «запуск цели» (10) оставляют изменённый `config_2` | скопировать оригинал из `lab1\vulns\config_2` (шаг 0); режимы 1–3 восстанавливают конфиг сами |
| Ложные краши пачками | в `config_2` одновременно пишут два процесса (гонка в `read_config`) | один писатель: не запускать два фаззера на одном рабочем каталоге |
| Цель выходит с `exit(-1)` / «variant does not match» | мутировали байт 0 (номер варианта) | байт 0 не трогать — в фаззере он исключён |
| `UnicodeEncodeError` в python-однострочниках | консоль cp1252 | `$env:PYTHONIOENCODING = 'utf-8'` или `py -3.12 -X utf8 -c "..."` |
| Число BB «прыгает» 497/498/499 | длина пути к цели влияет на обход строки в рантайме MinGW | измерять из `lab1\fuzzer`, сравнивать режимы от одного старта (см. §5) |
| В отладчике адреса не совпадают с отчётом | ASLR включён (образ грузится не по `0x400000`) | считать от фактической базы: `base+0x158D`, `base+0x22DE` |
