# Лабораторная работа № 1 — черновик отчёта (вариант 2)

Тема: изучение принципов поиска уязвимостей в программном обеспечении без исходных кодов.
Цели: `vuln2.exe`, `config_2`, `func.dll`. ТЗ: `lab1/Лабораторная_работа_1_Поиск_уязвимостей_без_исходных_кодов.docx`.

> Черновик. Скриншоты (IDA, x32dbg, консоль фаззера) вставляются в финальный docx.
> ФИО и группу уточнить перед титульным листом.

## 1. Цель работы

Изучить типовые ошибки ПО (отсутствие проверки длины копируемых данных, переполнение
буфера и др.) и освоить поиск таких ошибок без исходных кодов: мутационный фаззинг
формата файла, измерение покрытия кода средством динамической бинарной инструментации,
обратная связь по покрытию, анализ найденной уязвимости в дизассемблере и отладчике.

## 2. Исходные данные

| Файл | Размер | Назначение |
|---|---|---|
| `vuln2.exe` | 45 056 байт | исследуемая программа (32-битная, `DllCharacteristics = 0x0040`: DEP включён, ASLR выключен) |
| `config_2` | 1123 байта | корректный конфигурационный файл (вариант 2) |
| `func.dll` | 10 240 байт | вспомогательная библиотека (`Func1`) |

Наблюдаемое поведение цели:


Цель ищет файл `config_2` **в текущем каталоге** (путь в argv не принимает),
имя файла формируется как `config_%d` по номеру варианта, а номер варианта
сверяется со значением, зашитым в бинарник.

|---|---|---|---|
| 0 | 1 | `02` | номер варианта |
| 4 | 4 | 1075 | `shell_len` — печатается программой |
| 8 | 4 | 2500 | `dst_len` — печатается программой |
| 12 | 4 | 0 | не используется в выводе |
| 16 | 2 | 1075 | дубль `shell_len` младшим словом |
| 18 | 2 | 2500 | дубль `dst_len` младшим словом |

## 4. Разработанный фаззер

`lab1/fuzzer/` — Python 3.12, только стандартная библиотека. Формат конфига в код
не зашит (ни `/start`, ни имена полей, ни их смещения).

| Файл | Роль |
|---|---|
| `fuzzer.py` | меню, CLI, режимы `auto --seq`, `auto --cov`, журналы прогонов |
| `mutations.py` | мутации из ТЗ + детерминированные проходы режима `--seq` |
| `adapt.py` | планировщик стратегий по покрытию (доп. задание) |
| `runner.py` | запуск цели напрямую и под `drrun -t drcov`, таймауты, каталог конфигурации DynamoRIO |
| `coverage.py` | разбор лога `drcov` (только базовые блоки `vuln2.exe` и `func.dll`) |
| `debugger.py` | отладочный цикл (`DEBUG_ONLY_THIS_PROCESS`), 32-битный контекст WOW64, регистры и дамп стека |
| `config.py` | чтение `config.json` (пути к инструментам) |

### 4.1. Реализованные мутации (по ТЗ)

* замена одного байта; замена нескольких байт;
* подстановка граничных значений `0x00, 0xFF, 0xFF/2±1, 0xFFFF, 0xFFFF/2±1, 0xFFFFFF,
  0xFFFFFFFF, 0xFFFFFFFF/2±1`;
* допись в конец файла (данных больше, исходные байты целы);
* вставка внутрь файла (удлинение);
* работа с разделителями полей `,:=;` (в этом файле их нет — стратегия фиксирует
  «нет изменений» и не считается плато);
* перебор 4-байтных полей граничными и «умеренно большими» значениями длины;
* комбинация «удлинить + испортить поле» (для переполнения нужны оба условия сразу).

### 4.2. Режим `auto --seq` (детерминированный)

| Проход | Что делает | Число прогонов |
|---|---|---|
| A | каждое смещение × граничные значения (на месте) | 1123 × 14 = 15 722 |
| B | удлинение файла блоками по 1 КБ | 6 |
| C | удлинённый файл × граничные значения в 4-байтных полях | 4 × 280 × 10 = 11 200 |
| D | обрезка файла | 4 |

Запуск: `python fuzzer.py auto --seq` (или `--passes ABC` / `--max-runs N`).
Каждый прогон пишется в `lab1/fuzzer/seq.log` (номер, проход, смещение, значение,
статус, код исключения, размер файла), что закрывает требование ТЗ о логировании
ошибок вместе с произведёнными заменами.

### 4.3. Режим `auto --cov` (обратная связь по покрытию)

1. Калибровка: оригинальный `config_2` прогоняется под `drrun -t drcov`, множество
   базовых блоков (BB) становится начальным `BB_global` (499 BB).
2. Очередь сидов: мутант, давший **новые** BB, сохраняется в `lab1/fuzzer/corpus/`
   и попадает в очередь как родитель для дальнейших мутаций — это и есть «сохранение
   изменённых байт с учётом их влияния на покрытие кода» из ТЗ.
3. Родитель выбирается из трёх источников: сиды с новым покрытием, самый длинный
   вход (переполнение ищется среди длинных данных) и исходный конфиг (на нём перебор
   полей действительно меняет ход выполнения).
4. Стратегию мутаций выбирает планировщик `adapt.py` (см. раздел 6).
5. Каждый прогон пишется в `lab1/fuzzer/cov.log`; смены стратегий — в `adapt.log`.

### 4.4. Обнаружение ошибки, регистры и стек

Прогон в режиме `--seq` идёт под отладчиком: цель создаётся с флагом
`DEBUG_ONLY_THIS_PROCESS`, на исключении снимается 32-битный контекст
(`Wow64GetThreadContext`) и 128 байт стека по `ESP`. Крашем считается исключение
`0xC000xxxx` (access violation, stack overflow и т. п.); штатный выход с кодом `-1`
(несовпадение номера варианта) крашем не считается. При падении сохраняется пара
файлов в `lab1/crashes/`: `crash_*.bin` — вход, `crash_*.txt` — код исключения,
регистры `EAX…EFLAGS`, дамп стека и список произведённых замен относительно оригинала.
Окно Windows Error Reporting подавляется (`SetErrorMode`), при зависании убивается
всё дерево процессов.

## 6. Дополнительное задание: смена алгоритма фаззинга по покрытию

Формулировка: *«реализовать изменение алгоритма фаззинга в зависимости от результатов
покрытия: если фаззер видит, что покрытие становится меньше, он меняет алгоритм своей
работы для увеличения покрытия; алгоритм придумать самим и описать в отчёте»*.

### 6.1. Как измеряется «покрытие стало меньше»

Глобальное множество BB при фаззинге только растёт, поэтому буквальная трактовка
невыполнима. В работе покрытие сравнивается **с родительским сидом**:

| Сигнал | Условие | Смысл |
|---|---|---|
| `gain` | есть BB, которых не было в `BB_global` | мутант интересен, сид в очередь, вес стратегии ×2 |
| `shrink` | `BB_run < BB_parent` и новых BB нет | путь короче (ранний выход из разбора) — **это и есть «покрытие уменьшилось»** |
| `plateau` | новых BB нет, покрытие не уменьшилось | стратегия выдохлась |
| `noop` | мутация не изменила файл | не считается плато |

### 6.2. Алгоритм

* девять стратегий: `byte`, `multi`, `boundary`, `append`, `expand`, `delim`,
  `field`, `inject`, `combo`; активна ровно одна. Стратегия `inject` (вставка данных
  сразу за маркером + порча двух 4-байтных полей) добавлена по результатам
  экспериментов с переполнением — см. раздел 7;
* `shrink`: вес текущей стратегии ×0.5 (пол 0.25). После **3** shrink подряд —
  смена стратегии по кругу в порядке отката
  `inject → append → expand → combo → field → delim → boundary → byte → multi`
  (сначала то, что сохраняет исходные байты и может открыть новые пути);
* `plateau`: после **W = 20** прогонов без `gain` — переход к следующей стратегии
  по кругу (round-robin, чтобы ни одна стратегия не «залипала») и рост «энергии»
  (больше байт за прогон, длиннее допись);
* `gain`: вес ×2 (потолок 16), счётчики shrink/plateau сбрасываются.
* Каждая смена пишется в `lab1/fuzzer/adapt.log`:
  номер прогона, `from → to`, причина, `BB_run/BB_parent/BB_global`, энергия, веса.

### 6.3. Результат прогонов (доказательство работы адаптации)

**Прогон, в котором найден краш** — `python fuzzer.py auto --cov --max-runs 400`
(журнал `adapt.log` в репозитории — именно от него):

```
[cov] BB оригинала: 499
[adapt] run 20:  byte -> multi     (plateau) BB 499/499/499 energy=2
[adapt] run 40:  multi -> boundary (plateau) BB 499/499/499 energy=3
[adapt] run 60:  boundary -> append(plateau) BB 499/499/499 energy=4
[adapt] run 80:  append -> expand  (plateau) BB 499/499/499 energy=5
[adapt] run 100: expand -> delim   (plateau) BB 499/499/499 energy=5
[adapt] run 149: delim -> field    (plateau) BB 499/499/499 energy=5
[adapt] run 169: field -> inject   (plateau) BB 499/499/499 energy=5
[cov] #170 GAIN +2 BB  total=501  strategy=inject size=5219 seeds=2
[crash] сохранён crash_20260911_182419.bin  exception=0xC0000005   ← краш найден
```

В `adapt.log` этого прогона видно и смены стратегий, и реакцию весов: у `expand`
вес снижен до 0.25 (штраф за серии shrink), остальные сохраняют 1. Именно переход
к стратегии `inject` дал `gain` (+2 BB) и сразу после него — падение цели.

**Длинный прогон** `auto --cov --max-runs 600` (без краха, для статистики покрытия):

| Показатель | Значение |
|---|---|
| Базовое покрытие оригинала | 499 BB |
| Итоговое покрытие | **504 BB** |
| События `gain` | +2 BB (прогон 165, стратегия `inject`), +3 BB (прогон 466, `multi`) |
| Сиды в `corpus/` | 3 |
| Сигналы `shrink` | десятки (прогоны 200, 229, 247, 250, 300, 312, 335, 342, 356, 375, 471, 475, …) |
| Стратегии | задействованы все девять |
| Самый длинный вход | 119 435 байт |

Наблюдения:

* все девять стратегий получают ход; смены происходят и по `plateau`, и по `shrink`;
* веса реагируют на результат: после серий shrink у `multi`, `delim`, `expand`, `combo`
  вес падает до 0.5 и 0.25, после `gain` — удваивается (потолок 16);
* рост `BB_global` подтверждает, что обратная связь по покрытию работает: мутанты
  с новыми BB сохраняются и становятся родителями;
* покрытие растёт редко: большинство мутаций не меняют ход выполнения, поэтому
  основной вклад дают стратегии, меняющие 4-байтные поля и длину файла;
* без стратегии `inject` (прогон на 1500 запусков) покрытие выросло 499 → 503 BB,
  но краш найден не был — наглядная разница между простой очередью по покрытию
  и адаптацией со сменой стратегий.

### 6.4. Связь с поиском уязвимости

Уязвимость (раздел 7) требует одновременного выполнения трёх условий: данные лежат
**сразу за маркером**, их больше, чем вмещает приёмный буфер, и **два поля длины в
шапке завышены**. Поэтому в планировщик добавлены стратегии:

* `field` — перебор 4-байтных полей по кругу граничными и большими значениями;
* `inject` — вставка данных за маркером плюс порча двух 4-байтных полей;
* `combo` — удлинение файла плюс порча поля за один прогон.

Без них фаззер оставался на плато 499 BB и краш не находил.

## 7. Найденная уязвимость

### 7.1. Как найдена

Краш найден фаззером **в обоих режимах**:

| Режим | Команда | Где сработало | Артефакт |
|---|---|---|---|
| детерминированный | `fuzzer.py auto --seq --passes H` | 1-й прогон прохода H | `crash_20260911_181819.bin` (6243 байта) |
| по покрытию | `fuzzer.py auto --cov` | прогон 170 (сразу после `GAIN +2 BB`) | `crash_20260911_182419.bin` (9315 байт) |

Устойчивость (повторные запуски одного и того же конфига):
нативно 5 из 8, под отладчиком 5 из 6 — падение зависит от раскладки памяти
(перезапись адреса возврата не всегда приводит к обращению по недопустимому адресу).

Проход H — это стратегия «вставить данные сразу за маркером и подставить максимальные
значения в два 4-байтных поля шапки». В режиме `--cov` то же делает стратегия `inject`
(она добавлена в планировщик по результатам этих экспериментов).

Артефакты: `lab1/crashes/crash_20260911_181819.bin|txt` и
`lab1/crashes/crash_20260911_182419.bin|txt` (исключение, регистры, дамп стека,
список произведённых замен).

```
status: crash          exception: 0xC0000005 (ACCESS_VIOLATION)
EAX=0x0000182C  EDX=0x0000182C   <- длина копирования = 6188 байт
EBP=0x0073F698  ESP=0x0073EC60   <- кадр стека уязвимой функции
EIP=0x005222DE                   <- падение внутри копирования (libc)
note: seq pass=H offset=8 patch=ffffffff
mutant_size: 6243, appended: 5120 bytes (0x62)
```

### 7.2. Условие срабатывания (измерено)

| Что меняем | Результат |
|---|---|
| только данные в конце файла (допись) | не влияет: печатается те же 1069 символов, краха нет |
| данные **сразу за маркером** `/start`, 5000 байт | копирование доходит до 2500 символов (буфер), краха нет |
| то же + поле длины на смещении 8 = `0xFFFFFFFF` | **краш 4/4** (нативно тоже) |
| то же + поле длины на смещении 8 = `0xFFFFFFFF` + поле на смещении 4 = `0xFFFFFFFF` | **краш 10/10 нативно, 8/10 под отладчиком** |
| данные за маркером без испорченных полей | краха нет (копирование ограничено размером буфера) |

Итог: уязвимость срабатывает, когда **данные расположены сразу за маркером** и
**поля длин в шапке завышены** (`0xFFFFFFFF`). Значение копируемой длины при этом
равно фактической длине данных (6188 байт при вставке 5120 байт после исходных 1068).

### 7.3. Механизм

1. `read_config` открывает `config_2`, определяет размер файла, выделяет буфер в куче
   `malloc(size+1)`, читает файл целиком (`fread`) и копирует 48-байтную шапку в
   структуру; указатель на данные за маркером передаётся дальше.
2. Далее данные из этой позиции копируются в **константный буфер в стеке размером
   2500 байт** (наблюдаемая печать ограничена ровно 2500 символами — это и есть
   размер буфера). Длина копирования берётся из шапки и **не сверяется с размером
   приёмного буфера**.
3. При завышенных полях длины копируется вся фактическая длина данных (6188 байт),
   то есть на 3688 байт больше буфера: перезаписываются сохранённые регистры и адрес
   возврата, нарушение доступа происходит уже во время копирования
   (`EAX=EDX=0x182C`, `EIP` внутри libc).
4. Почему данные обязаны быть именно за маркером: копирование начинается от позиции
   сразу за `/start`; байты, дописанные в конец файла, в копирование не попадают
   (проверено: длина печати не меняется), поэтому «допись в конец» переполнения не даёт.

### 7.4. Тип ошибки, причины, ограничения эксплуатации

* **Тип:** отсутствие проверки длины копируемых данных (CWE-120, переполнение буфера
  в стеке); значение длины берётся из недоверенного файла.
* **Причина:** перед копированием не выполняется проверка `длина ≤ размер буфера`.
* **Ограничения:** копирование начинается строго за маркером, поэтому полезная
  нагрузка должна лежать там, а не в конце файла; падение зависит от раскладки
  памяти (нативно 10/10, под отладчиком 8/10 — при разных раскладках адрес возврата
  может указывать в отображённую память).

### 7.5. Способ исправления

```c
/* перед копированием: длина из файла не должна превышать размер буфера */
size_t copy_len = shell_len;              /* или dst_len — что используется в коде */
if (copy_len > sizeof(dst)) {             /* dst — буфер на 2500 байт */
    fprintf(stderr, "config error: length %zu exceeds buffer %zu\n",
            copy_len, sizeof(dst));
    return -1;
}
memcpy(dst, src, copy_len);
```

Дополнительно: ограничивать чтение (`fread` не больше размера буфера), использовать
`memcpy_s`/`strncpy_s`, проверять арифметику длин на переполнение.

## 9. Ограничения и незакрытые пункты

1. **IDA на текущей машине не запускается:** сборка IDA 7.7 64-битная, IDAPython
   требует согласованной версии Python (`idapyswitch` привязал Python 3.12, при
   запуске — `0xC0000135`, отсутствующий модуль). Варианты: установить Python 3.10 x64
   и выполнить `idapyswitch --auto-apply`, либо запустить GUI `ida.exe` и выполнить
   `File → Script file`. Скрипт `find_calls.py` от этого не зависит; его вывод
   продублирован независимой реализацией (`scratch/pe_find_calls.py`).
2. **Краш вероятностный:** повторные прогоны того же входа не всегда падают
   (зависит от раскладки памяти). Для отчёта нужен устойчивый краш-конфиг — план:
   в x32dbg зафиксировать адрес приёмного буфера и адрес сохранённого адреса возврата
   и подобрать длину, при которой перезапись происходит до чтения за границей буфера.
3. Скриншоты (консоль IDA, x32dbg, вывод фаззера) добавляются в финальный docx.
