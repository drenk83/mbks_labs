# Лабораторная работа № 1

**Тема:** изучение принципов поиска уязвимостей в программном обеспечении без исходных кодов
**Вариант:** 2 (`vuln2.exe`, `config_2`, `func.dll`)
**ТЗ:** `lab1/Лабораторная_работа_1_Поиск_уязвимостей_без_исходных_кодов.docx`

> `lab1/fuzzer.py` и `lab1/ida/find_calls.py` (в финальный docx выносятся приложениями).

## 1. Цель работы

Изучить типовые ошибки программного обеспечения (отсутствие проверки длины копируемых
данных, целочисленные переполнения, переполнение буфера) и освоить методы поиска таких
ошибок при отсутствии исходного кода: мутационный фаззинг формата файла, измерение
покрытия кода средствами динамической бинарной инструментации, фаззинг с обратной связью
по покрытию, анализ найденной уязвимости в дизассемблере и отладчике.

## 2. Исходные данные

Защиты цели (разобраны по заголовку PE и подтверждены наблюдениями):

| Файл | `DllCharacteristics` | Что это значит |
|---|---|---|
| `vuln2.exe` | `0x0040` = `DYNAMIC_BASE` | **ASLR включён** (образ перебазируется при загрузке: `ImageBase` в файле `0x00400000`, фактически загружается по `0x00DF0000`, `0x00970000`, `0x00980000` в разных запусках); флаг `NX_COMPAT` (0x0100) **не выставлен** — двоичный файл не запрашивает DEP, поэтому при политике OptIn (по умолчанию в клиентских Windows) стек остаётся исполняемым |
| `func.dll` | `0x0000` | не выставлен ни `DYNAMIC_BASE`, ни `NX_COMPAT` — библиотека грузится по предпочтительной базе `0x62500000` |

CFG (`GUARD_CF`) не используется ни в одном из модулей. Проверка выполнялась
собственным разбором PE (не по строке из отчёта): `Machine = 0x014C`, `Magic = 0x010B`
(PE32), секция `.reloc` присутствует.
Образ при загрузке смещается относительно предпочтительной базы `0x00400000`
(в проведённых запусках — `0x00DF0000`), поэтому все адреса в отладчике считаются
от фактической базы (`lpBaseOfImage`).

Вывод цели на корректном конфиге:

```
VERSION: 0.3
Variant: 2
Called Hello function from dll
read config:  shell_len 1075  dst_len 2500
buffer: vbzyqgdemwocajesnnuwqhbxtstltmyajhxalgzucstugatmiidkleglhuvaektwknnd…
```

Цель **не принимает путь в аргументах**: имя `config_2` формируется внутри программы

## 3. Формат конфигурационного файла

Формат восстановлен по дизассемблеру (`read_config`) и подтверждён экспериментами.

| Смещение | Размер | В `config_2` | Смысл |
|---|---|---|---|
| 0 | 1 | `02` | номер варианта; при несовпадении — `ERROR: variant does not match`, `exit(-1)` |
| 1–3 | 3 | `02 00 F4` | в коде не используются (проверено побайтово) |
| 4 | 4 | 1075 | `shell_len`; печатается, передаётся в `vuln_func`, **в копировании не участвует** |
| 8 | 4 | 2500 | `dst_len`; печатается и **используется как размер приёмного буфера** |
| 12–15 | 4 | 0 | не используется |
| 16 | 2 | 1075 | младшее слово `shell_len` |
| 18 | 2 | 2500 | младшее слово `dst_len` |
| 20–47 | — | — | прочие поля шапки, на вывод не влияют |
| 48 | 6 | `/start` | маркер начала данных; от него `parse_string` отсчитывает нагрузку |
| 54–1121 | 1068 | буквы | полезная нагрузка |
| 1122 | 1 | `00` | **нулевой байт-терминатор в конце файла** |

Два важных следствия, проверенных экспериментально:

* копируется строка **начиная с байта 54** (сразу за `/start`) и до нулевого байта —
  поэтому **допись в конец файла не попадает в копирование** (её отсекает `00` в конце
  исходного файла);
* длина копирования ограничивается значением `dst_len` из шапки — то есть **из файла**.

## 4. Разработанный фаззер

`lab1/fuzzer.py` — один файл на Python 3.12, только стандартная библиотека.
Запуск: `py -3.12 lab1/fuzzer.py` (открывается меню) либо с флагами
(`--seq1`, `--seq2`, `--cov`, `--cov-fixed boundary`, `--cov-fixed cycle`,
`--mutate byte`, `--run`, `--stats`).

Меню:

```
 1  SEQ-1: последовательная замена байт граничными значениями (ТЗ, авторежим)
 2  SEQ-2: удлинённый файл (вставка за /start) x поля шапки   <- находит краш
 3  COV:   покрытие DynamoRIO + смена стратегий по покрытию   <- доп. задание
 4  COV-контроль: стратегия зафиксирована или 4 стратегии по кругу без обратной связи
 5  замена одного байта (вручную)          6  замена нескольких байт (вручную)
 7  дописать в конец файла (вручную)      11  вставить внутрь / удлинить (вручную)
 8  найти разделители ,:=; и мутировать   12  увеличить значение поля шапки (вручную)
 9  один запуск work/config_2 (регистры и стек при падении)
10  статистика: журналы, краши, корпус      0  выход
```

### 4.1. Реализованные методы фаззинга (требования ТЗ)

| Метод | Функция | Что делает |
|---|---|---|
| однобайтовая замена | `mut_byte` | замена одного байта (0x00, 0xFF, 0x7F, 0x80, случайный) |
| замена нескольких байт | `mut_multi` | 2–8 байт за прогон |
| граничные значения | `mut_boundary` | 1 байт: `00, 7E, 7F, 80, FF`; 2 байта: `0000, 7FFE, 7FFF, 8000, 8001, FFFE, FFFF`; 3 байта: `7FFFFF, 800000, FFFFFF`; 4 байта: `00000000, 0000FFFF, 7FFFFFFE, 7FFFFFFF, 80000000, FFFFFFFE, FFFFFFFF` — всего 22 значения: ноль и максимум (`0x00`, `0xFFFF`, `0xFFFFFF`, `0xFFFFFFFF`) плюс половина диапазона и половина ±1 для каждой ширины |
| граничные значения в полях шапки | `mut_field` | прицельно по 4-байтным полям 4…44 |
| допись в файл | `mut_append` | +16, +64, +256, +1024 или +5120 байт в конец |
| расширение значения поля | `mut_grow` | увеличение 4-байтного поля шапки (×2/×4/×10, +100/+1000/+0x1000) |
| расширение значений полей | `mut_expand` | вставка внутрь файла (в т.ч. сразу за `/start`) |
| разделители полей | `mut_delim` | поиск `,:=;`, размножение разделителя, вставка длинного значения |
| длинный вход (ключевой) | `mut_inject` | вставка 3000–16384 байт за `/start` + завышение поля длины |

Байт 0 (номер варианта) не мутируется никогда — иначе цель завершается с `exit(-1)`.

### 4.2. Автоматический режим последовательной замены (SEQ-1)

Перебираются все смещения файла (кроме первого) и все 22 граничных значения подходящей
ширины. Значения шириной 1 байт помещаются на всех 1122 смещениях (5 значений → 5610
прогонов), значения шириной 2, 3 и 4 байта — только на 1121, 1120 и 1119 смещениях
соответственно (7847 + 3360 + 7833 прогонов). Итого ровно **24 650** прогонов —
именно столько строк в журнале `lab1/logs/seq.log` (24 647 в проходе A плюс проход B).
Формат журнала: номер прогона, проход, статус, код возврата, мутация, размер файла.
Результат: **0 крашей** — одиночная замена байта не создаёт условий переполнения
(см. §8.8).

### 4.3. Проход по удлинённому файлу (SEQ-2)

Файл с вставкой 5120 байт сразу за маркером `/start` × граничные значения в 4-байтных
полях шапки. Первый же прогон (поле по смещению 8 = `0xFFFFFFFF`) даёт падение —
именно этот вход сохранён как краш-конфиг фаззера.

### 4.4. Обнаружение ошибки, код ошибки, стек и регистры

Крашем считается код возврата `0xC000xxxx` (исключение Windows); штатный `exit(-1)`
при несовпадении варианта крашем не считается. После обнаружения краха вход
прогоняется повторно под мини-отладчиком, написанным на `ctypes`
(`CreateProcessW` с `DEBUG_ONLY_THIS_PROCESS`, `WaitForDebugEvent`,
`Wow64GetThreadContext` для 32-битного контекста WOW64, `ReadProcessMemory` для стека).
Снимаются: код исключения, `EAX…EFLAGS`, дамп стека, адрес и значение сохранённого
адреса возврата (`[EBP+4]`), база образа. Всё это вместе со списком произведённых замен
пишется в `lab1/crashes/crash_<дата>.txt`, сам вход — в `crash_<дата>.bin`
(требование ТЗ о логировании ошибки вместе с входными параметрами).

## 5. Измерение покрытия (DynamoRIO)

Покрытие измеряется средством динамической бинарной инструментации **DynamoRIO 11.3.0**
(режим `drcov`), как того требует ТЗ (допускается Intel Pin или DynamoRIO):

```
drrun -t drcov -logdir <каталог> -- work\vuln2.exe        (cwd = lab1\work)
```

Лог `drcov.*.log` содержит таблицу модулей и **бинарную** таблицу базовых блоков
(`BB Table: N bbs`, запись 8 байт: `uint32 start`, `uint16 size`, `uint16 mod_id`,
`start` — смещение от базы модуля). Фаззер разбирает её и учитывает только базовые
блоки цели (`vuln2.exe`) и `func.dll`.

Базовое покрытие оригинального `config_2`: **499 базовых блоков**
(**448 в `vuln2.exe` + 51 в `func.dll`**). Сырой лог покрытия сохранён как
`lab1/logs/drcov_sample.log` — это прямое доказательство работы DBI.

## 6. Режим с обратной связью по покрытию

Очередь сидов: если мутант выполняет базовые блоки, которых не было ни в одном
предыдущем прогоне (`gain`), он сохраняется в `lab1/corpus/` и становится родителем
для дальнейших мутаций — это и есть требуемое ТЗ «сохранение изменённых байт с учётом
их влияния на покрытие кода программы». Родитель выбирается случайно из набора
«оригинал + сиды»; покрытие каждого сида запоминается и используется как база сравнения.

## 7. Дополнительное задание: изменение алгоритма фаззинга по результатам покрытия

### 7.1. Постановка и выбор метрики

Требование: *«если фаззер видит, что покрытие становится меньше, он меняет алгоритм
своей работы для увеличения покрытия; алгоритм придумать самим и описать в отчёте»*.

Глобальное покрытие (объединение базовых блоков по всем прогонам) **монотонно растёт**
и уменьшиться не может, поэтому буквальная трактовка невыполнима. В работе
«уменьшение покрытия» измеряется двумя наблюдаемыми величинами:

1. **покрытие отдельного прогона против родителя**: `BB_run < BB_parent` — маршрут
   нового входа короче маршрута файла-родителя (мутация разрушила разбор конфига,
   цель вышла раньше). Сигнал `shrink`.
2. **прирост покрытия**: 30 прогонов подряд не дали ни одного нового базового блока —
   покрытие растёт всё меньше. Сигнал `plateau`.

### 7.2. Алгоритм

Активна ровно одна из четырёх стратегий мутирования; порядок обхода —
`byte → boundary → append → inject` по кругу.

```
shrink = 0        # сколько раз ПОДРЯД маршрут короче родителя
since_gain = 0    # сколько прогонов ПОДРЯД без нового покрытия

каждый прогон:
    BB_run, BB_parent, новые_BB = прогон_под_drcov()
    если новые_BB:                      # покрытие выросло
        since_gain = 0; shrink = 0
        сохранить вход в corpus/ как будущего родителя
    иначе:
        since_gain += 1
    shrink = shrink + 1 if BB_run < BB_parent else 0

    если shrink >= 3 или since_gain >= 30:      # ← вся адаптация
        стратегия = следующая по кругу
        shrink = 0; since_gain = 0
        запись в adapt.log(run, from→to, reason, BB_run, BB_parent, BB_global)
```

Стратегии: `byte` (один байт), `boundary` (граничные значения), `append` (допись),
`inject` (вставка длинных данных за `/start` + завышение поля длины).
Пороги 3 и 30 — «терпение» планировщика: 3 отсекает случайные короткие маршруты,
30 даёт стратегии честный шанс, но не позволяет залипнуть.

### 7.3. Результаты

Сравнивались три режима на одном и том же базовом покрытии (499 BB), по 600 прогонов
каждый, на одной ревизии кода. Основной эксперимент выполнен с зерном ГПСЧ 7, затем
**весь эксперимент повторён с другим зерном (99), чтобы сравнение было независимым**:

| Показатель | Адаптация по покрытию | Контроль: 4 стратегии по кругу **без** обратной связи | Контроль: только `boundary` |
|---|---|---|---|
| Команда | `--cov` | `--cov-fixed cycle` | `--cov-fixed boundary` |
| Итоговое покрытие (seed 7) | **508 BB** | **508 BB** | **500 BB** |
| Смен стратегии (seed 7) | 21 (17 `plateau`, 4 `shrink`) | 20 (`cycle`) | 0 |
| Крашей (seed 7) | 262 | 274 | **0** |
| Итоговое покрытие (seed 99) | **508 BB** | **508 BB** | — |
| Смен стратегии (seed 99) | 21 | 20 | — |
| Крашей (seed 99) | 207 | 236 | — |
| Событие `gain` | прогон 91, `inject`: **+9 BB** (499 → 508) | прогон 91, `inject`: **+9 BB** | первый новый блок на прогоне 169 (`bb_run` 500 при `bb_parent` 499), глобально 500 BB |
| Журналы | `logs/adapt.log`, `cov.log`, `adapt_seed99.log`, `cov_seed99.log` | `logs/adapt_cycle.log`, `cov_cycle.log`, `adapt_cycle99.log`, `cov_cycle99.log` | `logs/adapt_control.log`, `cov_control.log` |

Сид, давший новое покрытие, сохраняется в каталог `lab1/corpus/` (например,
`seed_0091_424.bin` — вход прогона 91); сам каталог с бинарными сидами в репозиторий
не кладётся (`.gitignore`), сиды идентифицируются по номеру прогона в журнале.

Фрагмент `lab1/logs/adapt.log`:

```
# 2026-09-11 21:59:55 | режим: адаптация по покрытию | BB оригинала: 499
run	from	to	reason	bb_run	bb_parent	bb_global
30	byte	boundary	plateau	499	499	499
60	boundary	append	plateau	499	499	499
90	append	inject	plateau	499	499	499      <- переключение на «inject»
106	inject	byte	shrink	424	499	508          <- покрытие прогона упало: 424 < 499
...
573	byte	boundary	plateau	499	499	508
```

В журнале присутствуют оба типа сигналов: `plateau` (за 30 прогонов ни одного нового
базового блока) и `shrink` (покрытие прогона меньше покрытия родителя — например,
424 против 499). Переключение на стратегию `inject` записано в конце прогона 90 и
действует со следующего прогона: именно на прогоне 91 стратегия `inject` дала
`GAIN +9 BB` (499 → 508) и привела к падению цели:

```
[adapt] run 90: append -> inject (plateau) BB 499/499/499
[crash] 0xC0000005 strategy=inject -> crashes/crash_20260911_214416.bin
[cov] #91 GAIN +9 BB  всего=508  стратегия=inject  родитель=orig  seeds=1
```

**Честная оценка результата.** Открытый контроль показывает, что на этой цели
**выигрыш даёт не обратная связь, а сам факт наличия стратегии `inject` в наборе**:
перебор тех же четырёх стратегий по кругу без всякого анализа покрытия приходит к тому
же результату — 508 BB при обоих зернах. Число найденных крашей при этом сопоставимо
и колеблется от запуска к запуску (адаптация: 262 при seed 7 и 207 при seed 99;
открытый цикл: 274 и 236 соответственно — разброс объясняется вероятностным характером
самого падения цели, см. §8.4). Планировщик по покрытию:

* исправно реализует требуемое заданием поведение: реагирует и на уменьшение покрытия
  прогона (`shrink`), и на прекращение прироста (`plateau`), и ведёт журнал смен;
* обеспечивает тот же уровень покрытия, что и открытый перебор, но **не превосходит**
  его, потому что цель маленькая: покрытие насыщается на 508 BB (единственный «новый
  путь» — вход в функцию копирования с длинной нагрузкой), а условие краха достигается
  одной стратегией.

**Оговорка о методике.** Оба режима запускаются с одним и тем же зерном ГПСЧ, и до
первого расхождения расписания переключений журналы совпадают строка в строку: при
одинаковом стартовом порядке стратегий и пороге 30 прогонов и адаптация, и открытый
цикл переключаются на прогонах 30/60/90. То есть пара «адаптация / цикл» при одном
зерне — это две ветви одной последовательности после точки расхождения, а не два
независимых опыта. Именно поэтому эксперимент повторён с другим зерном (99): вывод
не изменился.

**Ограничение сигнала `shrink`.** Значительная часть таких событий — это прогоны,
на которых цель упала: маршрут обрывается, и покрытие прогона оказывается меньше
покрытия родителя (424 или 422 против 499). Для фаззера это не деградация, а находка,
поэтому краш обрабатывается отдельно (сохраняется конфиг, регистры и стек), а в журнале
прогонов проставляется статус `crash`. В перспективе сигнал `shrink` корректнее считать
только на прогонах без падения — это отмечено в §11 как направление улучшения.

Тем не менее требуемая заданием конструкция «увидел уменьшение покрытия → сменил
алгоритм работы» реализована полностью и проверяема по журналу, а разница с режимом
фиксированной стратегии (500 BB и ни одного краха) показывает, что смена алгоритма
в принципе необходима: без стратегии `inject` уязвимость не находится.

### 8.2. Участок кода с уязвимостью

`vuln_func` — здесь объявлен буфер и вызывается форматирование с длиной из файла:

### 8.3. Восстановленный исходный код участка (язык C)

```c
/* Глобальная структура с шапкой конфига (0x0040DA20) */
struct config {
    unsigned char variant;      /* +0  — номер варианта (сверяется с 2) */
    unsigned char pad[3];
    int  shell_len;             /* +4  — из файла (смещение 4) */
    int  dst_len;               /* +8  — из файла (смещение 8) */
    /* ... остальные поля шапки, 48 байт ... */
};
static struct config cfg;

/* Чтение конфига: файл читается целиком, шапка копируется в cfg,
   указатель на данные за шапкой возвращается через out */
int read_config(const char *FileName, struct config *cfg, char **out)
{
    FILE *Stream = fopen(FileName, "rb");
    if (!Stream) { printf("Error: couldn`t open config file '%s'\n", FileName); exit(-1); }

    fseek(Stream, 0, SEEK_END);
    long ElementCount = ftell(Stream);          /* размер файла */
    fseek(Stream, 0, SEEK_SET);

    char *Buffer = malloc(ElementCount + 1);
    fread(Buffer, 1, ElementCount, Stream);
    Buffer[ElementCount] = '\0';

    if (ElementCount > 0x2F)
        memcpy(cfg, Buffer, 0x30);              /* 48 байт шапки */
    *out = Buffer + 0x30;                       /* данные, начиная с "/start" */
    printf("read config:  shell_len %d  dst_len %d", cfg->shell_len, cfg->dst_len);
    ...
}

/* Рекурсивный поиск маркера: данные копируются ровно из позиции за "/start" */
int parse_string(char *Str)
{
    char *p = strstr(Str, "/start");
    if (p == NULL) {
        vuln_func(Str, cfg.shell_len, cfg.dst_len);   /* длины — из файла! */
        return 1;
    }
    parse_string(p + strlen("/start"));
    return 0;
}

/* УЯЗВИМЫЙ УЧАСТОК */
void vuln_func(char *src, int shell_len, int dst_len)
{
    char buf[2500];                      /* 0x9C4, адрес = EBP-0x9CC */
    memset(buf, 'b', sizeof(buf));

    snprintf(buf, dst_len, "%s", src);   /* ОШИБКА: dst_len не проверяется
                                            против sizeof(buf); при
                                            dst_len = 0xFFFFFFFF ограничение
                                            отключается и строка любой длины
                                            копируется в buf */
    printf("buffer: %s\n", buf);
}
```

### 8.4. Тип ошибки, причина, ограничения эксплуатации

* **Тип:** отсутствие проверки длины копируемых данных — переполнение буфера в стеке
  (CWE-120 / CWE-787), значение длины берётся из недоверенного файла.
* **Причина:** размер приёмного буфера для `snprintf` (`dst_len`) читается из
  конфигурационного файла и нигде не сверяется с фактическим размером буфера (2500).
  При `dst_len > 2500` запись выходит за пределы буфера, при `dst_len = 0xFFFFFFFF`
  ограничение снимается полностью.
* **Ограничения эксплуатации:**
  * данные должны находиться **сразу за маркером `/start`**: копирование начинается
    с байта 54, а исходный файл заканчивается нулевым байтом, поэтому допись в конец
    файла в копирование не попадает;
  * необходимо завышенное поле `dst_len` (смещение 8); поле `shell_len` (смещение 4)
    на копирование не влияет;
  * падение **вероятностное** и зависит от того, насколько далеко за пределы кадра
    уходит запись: при небольшом превышении (`dst_len` = 2501…2502 при нагрузке
    5120 байт) перезапись остаётся в пределах отображённого стека и цель не падает,
    при `dst_len ≥ 3000` падение устойчиво. В протоколе `lab1/logs/repro.log`
    (по 10 нативных запусков на конфиг) наш краш-конфиг `crash_20260911_214402.bin`
    даёт 8 падений из 10, оригинальный `config_2` — 0 из 10, а сохранённые от ранних
    прогонов конфиги (другая длина нагрузки) — 7 и 8 из 10: стабильность зависит
    от того, насколько далеко запись уходит за кадр, и от раскладки стека (ASLR);
  * ASLR у образа **включён**, поэтому адрес буфера на стеке меняется от запуска
    к запуску (наблюдались `0x013FEC0C` и `0x007FF02C`), а вот база кода
    предсказуема только относительно самой базы (`base+0x22DE`).

### 8.5. Механизмы эксплуатации

Найденная ошибка даёт **управляемое переполнение стека**: содержимое копируемой строки
полностью определяется входным файлом, а её длина не ограничена размером буфера.

1. **Управляемость содержимого.** Данные, начиная со смещения 54 (сразу за `/start`),
   копируются в буфер как есть. Значит, байты, которыми перезаписывается стек (в том
   числе сохранённый адрес возврата), задаются файлом.
2. **Точка перезаписи.** Буфер начинается по адресу `EBP-0x9CC`; сохранённый адрес
   возврата лежит по `EBP+4`, то есть на **2512-м байте** от начала буфера. Первые
   2500 байт нагрузки заполняют буфер, байты 2500–2507 перекрывают промежуток до
   сохранённого `EBP`, байты 2508–2511 — сам сохранённый `EBP`, а начиная с байта
   2512 перезаписывается адрес возврата.
3. **Рандомизация адресов.** У `vuln2.exe` выставлен `DYNAMIC_BASE`, то есть **ASLR
   включён**: база образа при каждом запуске своя (`0x00DF0000`, `0x00970000`,
   `0x00980000`), адрес стека также меняется. Постоянным остаётся только смещение
   точки падения от базы модуля (`+0x22DE`). Именно поэтому падение при небольшом
   превышении длины нестабильно: часть записей попадает в отображённые страницы.
4. **Состояние DEP.** Флаг `NX_COMPAT` у `vuln2.exe` **не выставлен**, поэтому при
   политике OptIn процесс получает исполняемый стек — прямой переход на код,
   размещённый в переполненном буфере, в принципе возможен, но требует знания адреса
   стека (ASLR), которое можно получить через модуль без ASLR — `func.dll`
   (`DllCharacteristics = 0`). Альтернатива — возврат в существующий код (ROP).
5. **Ограничение на содержимое нагрузки.** Копирование выполняется как `"%s"` и
   останавливается на нулевом байте, поэтому полезная нагрузка не должна содержать
   `0x00` (иначе перезапись оборвётся раньше адреса возврата) — стандартное требование
   к позиционно-независимому шеллкоду.

Таким образом, уязвимость относится к классу эксплуатируемых: она позволяет
контролируемо перезаписать сохранённый адрес возврата. Практическая демонстрация
эксплуатации — предмет следующей лабораторной работы.

### 8.6. Формат файла, приводящего к краху

Файл собран из оригинального `config_2` (1123 байта) вставкой 5120 байт сразу за
маркером `/start` и заменой поля `dst_len` на `0xFFFFFFFF`:

| Смещение | Размер | Значение | Комментарий |
|---|---|---|---|
| 0 | 1 | `02` | вариант — не менять (иначе `exit(-1)`) |
| 4 | 4 | 1075 (не менялось) | `shell_len`, на крах не влияет |
| **8** | **4** | **`0xFFFFFFFF`** | **`dst_len` — ключевое поле: снимает ограничение копирования** |
| 12–47 | 36 | как в оригинале | прочие поля шапки |
| 48 | 6 | `/start` | маркер начала данных |
| 54 | 5120 | `62 62 …` (`'b'`) | **вставленные данные**; буфер 2500 байт переполняется |
| 5174 | 1068 | буквы (остаток исходной нагрузки) | исходные данные файла, сдвинутые вставкой |
| 6242 | 1 | `00` | нулевой терминатор (в исходном файле был на смещении 1122) |

Важное замечание по результатам: **уязвимое копирование этим скриптом не находится**,
и это ожидаемо. Скрипт ищет вызовы библиотечных функций из белого списка ТЗ, а опасная
операция выполняется внутри самой программы — через внутреннюю реализацию
`snprintf` (`sub_402270` → `sub_4022A0`), которая импортом не является. Уязвимость
выявлена анализом цепочки вызовов от найденных скриптом функций ввода: `fread`
в `read_config` → `parse_string` → `vuln_func` → `snprintf с длиной из файла`.

В конфигурационном файле `config_2` разделителей `,:=;` **нет ни одного** (проверено
побайтовым поиском, см. пункт меню 8): полезная нагрузка состоит только из строчных
латинских букв. Поэтому стратегия `delim` на этом файле фиксирует «нет изменений»
и не считается ни плато, ни падением покрытия.

## 10. Способ исправления уязвимости

```c
void vuln_func(char *src, int shell_len, int dst_len)
{
    char buf[2500];

    /* 1. длина из файла не должна превышать размер приёмного буфера */
    size_t limit = (dst_len > 0 && (size_t)dst_len <= sizeof(buf))
                 ? (size_t)dst_len
                 : sizeof(buf);

    memset(buf, 'b', sizeof(buf));
    snprintf(buf, limit, "%s", src);   /* ограничение теперь всегда корректно */
    printf("buffer: %s\n", buf);
}
```

Дополнительно рекомендуется:

* проверять поля конфига при чтении (в `read_config`): `dst_len` и `shell_len` должны
  быть неотрицательны и не больше размеров соответствующих буферов; при нарушении —
  отказ с диагностикой, а не продолжение работы;
* проверять `ElementCount` (размер файла) перед `malloc`/`fread` и ограничивать
  максимальный размер конфига;
* использовать безопасные варианты функций (`snprintf` вместо `sprintf`,
  `memcpy_s`/`strncpy_s`) и **всегда** передавать им реальный размер буфера
  (`sizeof(buf)`), а не значение из входных данных;
* включить ASLR (`/DYNAMICBASE`) при сборке — это не устраняет ошибку, но усложняет
  эксплуатацию.

## 11. Выводы

1. Разработан мутационный фаззер формата файла на Python 3, реализующий все требуемые
   ТЗ методы (одно- и многобайтовые замены, граничные значения, допись, расширение
   полей, поиск разделителей, автоматический режим последовательной замены), запуск
   цели, измерение покрытия средствами DynamoRIO и режим с обратной связью по покрытию.
2. Реализовано дополнительное задание: планировщик, который по результатам покрытия
   меняет алгоритм мутирования (сигналы `shrink` — покрытие прогона меньше покрытия
   родителя, и `plateau` — прирост покрытия прекратился). В прогоне на 600 итераций
   планировщик 21 раз сменил стратегию, покрытие выросло с 499 до 508 базовых блоков
   и цель упала. Контроль с фиксированной стратегией `boundary` дал 500 BB и ни одного
   краха. При этом открытый контроль (те же 4 стратегии по кругу **без** учёта покрытия)
   показал такой же результат — 508 BB при обоих зернах ГПСЧ (262 и 207 крашей против
   274 и 236 у открытого перебора): на этой цели выигрыш
   даёт наличие подходящей стратегии в наборе, а не сама обратная связь. Этот факт
   приведён в отчёте прямо (§7.3), чтобы не выдавать желаемое за измеренное.
3. Фаззингом найдена уязвимость — отсутствие проверки длины копируемых данных:
   значение `dst_len` берётся из конфигурационного файла и используется как размер
   приёмного буфера `snprintf` без сверки с фактическим размером буфера (2500 байт).
   При `dst_len = 0xFFFFFFFF` строка длиной 6188 байт копируется в 2500-байтовый буфер
   на стеке; падение — `0xC0000005` на записи терминатора (`vuln2.exe+0x22DE`).
4. Определены все требуемые характеристики уязвимости: размер буфера (2500 байт),
   адрес буфера (`EBP-0x9CC`), адрес сохранённого адреса возврата (`EBP+4`, 2512 байт
   от начала буфера), формат файла, приводящего к краху, и способ исправления.
   Защиты цели разобраны заново по заголовку PE: у `vuln2.exe` **включён ASLR**
   (`DYNAMIC_BASE`) и **не запрошен DEP** (`NX_COMPAT` не выставлен), у `func.dll`
   не выставлено ни то, ни другое.
5. Наивный последовательный перебор одиночных замен (24 650 прогонов) уязвимость
   **не** находит: переполнение требует одновременного выполнения двух условий —
   длинных данных сразу за маркером `/start` и завышенного поля длины. Найти её
   позволяет лишь смена алгоритма мутирования (вставка данных за маркером вместе
   с порчей поля длины) — то есть именно то, ради чего в задании требуется режим
   со сменой алгоритма.

**Направления улучшения** (честно, для дальнейшей работы): сигнал `shrink` считать
только на прогонах без падения цели (сейчас падение тоже даёт «уменьшение покрытия»
и учитывается сигналом); для проверки пользы обратной связи ставить контрольные
прогоны с независимыми зернами ГПСЧ и большим числом итераций; для больших целей
добавить минимизацию корпуса и учёт редкости путей (power schedule, как в AFLFast).
