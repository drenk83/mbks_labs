# Лабораторная работа № 1 — черновик отчёта (вариант 2)

Тема: изучение принципов поиска уязвимостей в программном обеспечении без исходных кодов.
Цели: `vuln2.exe`, `config_2`, `func.dll`. ТЗ: `lab1/Лабораторная_работа_1_Поиск_уязвимостей_без_исходных_кодов.docx`.

> Черновик. Скриншоты (IDA, x32dbg, консоль фаззера) вставляются в финальный docx.
> ФИО и группу уточнить перед титульным листом.

## 1. Цель работы

Изучить типовые ошибки ПО (отсутствие проверки длины копируемых данных, переполнение
буфера и др.) и освоить поиск таких ошибок без исходных кодов: мутационный фаззинг
формата файла, измерение покрытия кода средством динамической бинарной инструментации,
обратная связь по покрытию, анализ найденной уязвимости в дизассемблере и отладчике.

## 2. Исходные данные

| Файл | Размер | Назначение |
|---|---|---|
| `vuln2.exe` | 45 056 байт | исследуемая программа (32-битная, `DllCharacteristics = 0x0040`: DEP включён, ASLR выключен) |
| `config_2` | 1123 байта | корректный конфигурационный файл (вариант 2) |

## 4. Разработанный фаззер

`lab1/fuzzer/` — Python 3.12, только стандартная библиотека. Формат конфига в код
не зашит (ни `/start`, ни имена полей, ни их смещения).

| Файл | Роль |
|---|---|
| `fuzzer.py` | меню, CLI, режимы `auto --seq`, `auto --cov`, журналы прогонов |
| `mutations.py` | мутации из ТЗ + детерминированные проходы режима `--seq` |
| `adapt.py` | планировщик стратегий по покрытию (доп. задание) |
| `runner.py` | запуск цели напрямую и под `drrun -t drcov`, таймауты, каталог конфигурации DynamoRIO |
| `coverage.py` | разбор лога `drcov` (только базовые блоки `vuln2.exe` и `func.dll`) |
| `debugger.py` | отладочный цикл (`DEBUG_ONLY_THIS_PROCESS`), 32-битный контекст WOW64, регистры и дамп стека |
| `config.py` | чтение `config.json` (пути к инструментам) |

### 4.1. Реализованные мутации (по ТЗ)

* замена одного байта; замена нескольких байт;
* подстановка граничных значений `0x00, 0xFF, 0xFF/2±1, 0xFFFF, 0xFFFF/2±1, 0xFFFFFF,
  0xFFFFFFFF, 0xFFFFFFFF/2±1`;
* допись в конец файла (данных больше, исходные байты целы);
* вставка внутрь файла (удлинение);
* работа с разделителями полей `,:=;` (в этом файле их нет — стратегия фиксирует
  «нет изменений» и не считается плато);
* перебор 4-байтных полей граничными и «умеренно большими» значениями длины;
* комбинация «удлинить + испортить поле» (для переполнения нужны оба условия сразу).

### 4.2. Режим `auto --seq` (детерминированный)

| Проход | Что делает | Число прогонов |
|---|---|---|
| A | каждое смещение × граничные значения (на месте) | 1123 × 14 = 15 722 |
| B | удлинение файла блоками по 1 КБ | 6 |
| C | удлинённый файл × граничные значения в 4-байтных полях | 4 × 280 × 10 = 11 200 |
| D | обрезка файла | 4 |

Запуск: `python fuzzer.py auto --seq` (или `--passes ABC` / `--max-runs N`).
Каждый прогон пишется в `lab1/fuzzer/seq.log` (номер, проход, смещение, значение,
статус, код исключения, размер файла), что закрывает требование ТЗ о логировании
ошибок вместе с произведёнными заменами.

### 4.3. Режим `auto --cov` (обратная связь по покрытию)

1. Калибровка: оригинальный `config_2` прогоняется под `drrun -t drcov`, множество
   базовых блоков (BB) становится начальным `BB_global` (499 BB).
2. Очередь сидов: мутант, давший **новые** BB, сохраняется в `lab1/fuzzer/corpus/`
   и попадает в очередь как родитель для дальнейших мутаций — это и есть «сохранение
   изменённых байт с учётом их влияния на покрытие кода» из ТЗ.
3. Родитель выбирается из трёх источников: сиды с новым покрытием, самый длинный
   вход (переполнение ищется среди длинных данных) и исходный конфиг (на нём перебор
   полей действительно меняет ход выполнения).
4. Стратегию мутаций выбирает планировщик `adapt.py` (см. раздел 6).
5. Каждый прогон пишется в `lab1/fuzzer/cov.log`; смены стратегий — в `adapt.log`.

### 4.4. Обнаружение ошибки, регистры и стек

Прогон в режиме `--seq` идёт под отладчиком: цель создаётся с флагом
`DEBUG_ONLY_THIS_PROCESS`, на исключении снимается 32-битный контекст
(`Wow64GetThreadContext`) и 128 байт стека по `ESP`. Крашем считается исключение
`0xC000xxxx` (access violation, stack overflow и т. п.); штатный выход с кодом `-1`
(несовпадение номера варианта) крашем не считается. При падении сохраняется пара
файлов в `lab1/crashes/`: `crash_*.bin` — вход, `crash_*.txt` — код исключения,
регистры `EAX…EFLAGS`, дамп стека и список произведённых замен относительно оригинала.
Окно Windows Error Reporting подавляется (`SetErrorMode`), при зависании убивается
всё дерево процессов.

## 6. Дополнительное задание: смена алгоритма фаззинга по покрытию

Формулировка: *«реализовать изменение алгоритма фаззинга в зависимости от результатов
покрытия: если фаззер видит, что покрытие становится меньше, он меняет алгоритм своей
работы для увеличения покрытия; алгоритм придумать самим и описать в отчёте»*.

### 6.1. Как измеряется «покрытие стало меньше»

Глобальное множество BB при фаззинге только растёт, поэтому буквальная трактовка
невыполнима. В работе покрытие сравнивается **с родительским сидом**:

| Сигнал | Условие | Смысл |
|---|---|---|
| `gain` | есть BB, которых не было в `BB_global` | мутант интересен, сид в очередь, вес стратегии ×2 |
| `shrink` | `BB_run < BB_parent` и новых BB нет | путь короче (ранний выход из разбора) — **это и есть «покрытие уменьшилось»** |
| `plateau` | новых BB нет, покрытие не уменьшилось | стратегия выдохлась |
| `noop` | мутация не изменила файл | не считается плато |

### 6.2. Алгоритм

* восемь стратегий: `byte`, `multi`, `boundary`, `append`, `expand`, `delim`,
  `field`, `combo`; активна ровно одна;
* `shrink`: вес текущей стратегии ×0.5 (пол 0.25). После **3** shrink подряд —
  смена стратегии по кругу в порядке отката
  `append → expand → combo → field → delim → boundary → byte → multi`
  (сначала то, что сохраняет исходные байты и может открыть новые пути);
* `plateau`: после **W = 20** прогонов без `gain` — переход к следующей стратегии
  по кругу (round-robin, чтобы ни одна стратегия не «залипала») и рост «энергии»
  (больше байт за прогон, длиннее допись);
* `gain`: вес ×2 (потолок 16), счётчики shrink/plateau сбрасываются.
* Каждая смена пишется в `lab1/fuzzer/adapt.log`:
  номер прогона, `from → to`, причина, `BB_run/BB_parent/BB_global`, энергия, веса.

### 6.3. Результат прогонов (доказательство работы адаптации)

**Короткий прогон** `auto --cov --max-runs 300 --deep`:

Наблюдения:

* все восемь стратегий получают ход; смены происходят и по `plateau`, и по `shrink`;
* веса реагируют на результат: после серий shrink у `multi`, `delim`, `expand`, `combo`
  вес падает до 0.5 и 0.25, после `gain` — удваивается (потолок 16);
* рост `BB_global` подтверждает, что обратная связь по покрытию работает: мутанты
  с новыми BB сохраняются и становятся родителями;
* покрытие растёт редко: большинство мутаций не меняют ход выполнения, поэтому
  основной вклад дают стратегии, меняющие 4-байтные поля и длину файла.

### 6.4. Связь с поиском уязвимости

Краш, найденный в режиме `--seq`, относится к тому же классу, что и стратегия `combo`:
нужно одновременно испортить значение длины и иметь достаточно данных. Именно поэтому
в планировщик добавлены стратегии `field` (перебор 4-байтных полей по кругу) и `combo`
(удлинить и испортить поле за один прогон) — без них фаззер оставался на плато 499 BB.

## 7. Найденная уязвимость

### 7.1. Как найдена

Краш получен фаззером в режиме `--seq` (проход A) на прогоне 4380:
смещение **312** (0x138), подставленное значение **`0x7FFFFFFF`**.
Изменены 4 байта: `66 64 68 72` → `FF FF FF 7F`.

```
status: crash
exception: 0xC0000005   (ACCESS_VIOLATION)
EAX=0x00000FA0  EBX=0x009FF20C  ECX=0x0056A145  EDX=0x00000FA0
ESI=0xFFFFFFFE  EDI=0x009FFE60  EBP=0x009FFBD8  ESP=0x009FF1A0
EIP=0x005622DE
note: seq pass=A offset=312 patch=ffffff7f
```

Артефакты: `lab1/crashes/crash_20260911_173529.bin` (+ `.txt` с регистрами и стеком).

### 7.2. Механизм

`read_config` (0x4015F0) читает конфиг целиком в буфер, выделенный по размеру файла,
и копирует первые 48 байт в структуру; данные за маркером `/start` отдаются дальше
по указателю. Дальнейшая обработка выполняет `memcpy` в буфер ограниченного размера,
беря длину копирования из содержимого файла, **без проверки, что длины хватает**.
Именно это и приводит к нарушению доступа: регистры в момент падения показывают
искомую длину копирования (`EAX = EDX = 0x0FA0 = 4000`) и адреса буферов на стеке
(`ESP = 0x009FF1A0`, `EBP = 0x009FFBD8`, разница ≈ 2616 байт — размер кадра с буфером).

Скриншоты дизассемблера участка и псевдокод на C (восстановленный) — вставить здесь:

```
; участок чтения конфигурации (адреса при загрузке по базе 0x00970000)
0x004016A2  call fread      ; читает файл целиком в буфер, выделенный malloc
0x004016CF  call memcpy     ; копирует 48-байтный заголовок в структуру
```

```c
/* восстановленный фрагмент */
struct config {
    unsigned char variant;        /* +0  */
    unsigned int  shell_len;      /* +4  */
    unsigned int  dst_len;        /* +8  */
    ...
    char         *payload;        /* данные за маркером "/start" */
};

size_t size = file_size(f);
char  *buf  = malloc(size + 1);
fread(buf, 1, size, f);
memcpy(&cfg, buf, 48);            /* только заголовок */
cfg.payload = buf + 48;
/* далее длина берётся из данных файла и передаётся в memcpy без проверки */
```

### 7.3. Тип ошибки, причины, ограничения эксплуатации

* **Тип:** отсутствие проверки длины копируемых данных (CWE-120: переполнение буфера
  при копировании без проверки размера; возможен и целочисленный аспект — длина
  берётся из недоверенного файла).
* **Причина:** длина копирования берётся из входного файла и не сверяется с размером
  приёмного буфера.
* **Ограничения:** размер буфера-источника выделяется по фактическому размеру файла,
  поэтому «слишком большая» длина приводит к чтению за его пределами и нарушению
  доступа раньше, чем к перезаписи адреса возврата; для управляемого переполнения
  нужно, чтобы данных в файле было достаточно, а длина лежала в узком диапазоне
  (около размера буфера). В проведённых прогонах падение регистрировалось
  вероятностно — оно зависит от раскладки кучи и стека (ASLR для кучи/стека включён,
  у образа — выключен), поэтому одиночный повтор может не воспроизводиться.
* **Что нужно доисследовать для отчёта:** точный адрес буфера-приёмника, адрес
  сохранённого адреса возврата и проверка его перезаписи в x32dbg (шаг 5 плана).

### 7.4. Способ исправления

```c
/* до копирования */
if (shell_len > dst_len) {            /* или payload_len > sizeof(dst) */
    fprintf(stderr, "config error: shell_len %u > dst_len %u\n", shell_len, dst_len);
    return -1;
}
memcpy(dst, payload, shell_len);
```

Дополнительно: ограничивать длину при чтении из файла (`fread` не более размера
буфера), использовать `memcpy_s`/`strncpy_s` и проверять арифметику на переполнение
перед выделением памяти.

## 9. Ограничения и незакрытые пункты

1. **IDA на текущей машине не запускается:** сборка IDA 7.7 64-битная, IDAPython
   требует согласованной версии Python (`idapyswitch` привязал Python 3.12, при
   запуске — `0xC0000135`, отсутствующий модуль). Варианты: установить Python 3.10 x64
   и выполнить `idapyswitch --auto-apply`, либо запустить GUI `ida.exe` и выполнить
   `File → Script file`. Скрипт `find_calls.py` от этого не зависит; его вывод
   продублирован независимой реализацией (`scratch/pe_find_calls.py`).
2. **Краш вероятностный:** повторные прогоны того же входа не всегда падают
   (зависит от раскладки памяти). Для отчёта нужен устойчивый краш-конфиг — план:
