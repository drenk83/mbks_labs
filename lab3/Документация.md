# FsFilterX: как устроен и как им пользоваться

Лабораторная 3, вариант 9. Минифильтр файловой системы, дискреционные права в XML, защита файла правил, управление через IOCTL и журнал загрузки образов.

Описание соответствует коду в этом каталоге. План решений лежит в `План.md`, ход работы и результаты прогонов — в `Журнал_действий.md`.

## Что делает драйвер

`FsFilterX` стоит между программой и диском. На открытие, чтение и запись файла он смотрит таблицу правил в памяти и либо пропускает запрос, либо завершает его с `STATUS_ACCESS_DENIED`.

Правила читаются с диска только в двух случаях: при загрузке драйвера и по команде `fsctl reload` или `fsctl set`. На каждую файловую операцию XML заново не разбирается.

Субъект — имя exe-файла, без пути и без учёта регистра. `filetool.exe` и полный путь к этому файлу для драйвера одно и то же. Учётная запись Windows в правилах не участвует.

Путь файла сравнивается целиком, в виде `C:\DriverConfig\data\note.txt`. Драйвер приводит имя тома к диску `C:`. Относительный путь он не разбирает и такой запрос пропускает. Каталоги и подкачку кэша (`IRP_PAGING_IO`) он тоже пропускает.

Дальше три обычных случая:

- Файла нет в `policy.xml`. Доступ есть. Поэтому система и файл вне списка продолжают работать.
- Файл есть, а программы в его списке нет. Отказ.
- Программа есть. Смотрится её флаг. `read="1"` и `write="1"` разрешают, `0` запрещает.

Два пути обрабатываются отдельно от списка:

- `C:\DriverConfig\policy.xml` открывает только `fsctl.exe` и сам драйвер в тот момент, когда он перечитывает правила. Запись в XML это право другим программам не выдаёт.
- `C:\DriverConfig\image.log` открыт всем: драйвер дописывает его, а проверку можно прочитать, пока нотификатор включён.

Проверки стоят на `IRP_MJ_CREATE`, `IRP_MJ_READ` и `IRP_MJ_WRITE`. Запись ловится уже при создании файла. `filetool` открывает файл так, что содержимое стирается до операции записи (`FILE_OVERWRITE`, `FILE_OVERWRITE_IF`, `FILE_SUPERSEDE`, `FILE_CREATE`). Если записи нет, драйвер запрещает само открытие, и старый текст остаётся на месте.

Удаление и переименование драйвер не перехватывает.

## Файлы

| Путь | Зачем |
| --- | --- |
| `FsFilterX\FsFilterX\FsFilterX.c` | драйвер |
| `FsFilterX\FsFilterX\ioctl.h` | общие коды IOCTL, их подключают и драйвер, и `fsctl` |
| `fsctl\fsctl.cpp` | программа управления |
| `filetool\` | программа-испытуемый, её сообщения не менялись |
| `config\policy.xml` | образец правил, его копируют в `C:\DriverConfig\policy.xml` |
| `C:\DriverConfig\Config.txt` | старый текстовый конфиг, драйвер его больше не читает и скрипт его не удаляет |
| `C:\DriverConfig\image.log` | журнал нотификатора |
| `install-filter.ps1` | подпись, установка и проверки, только от администратора |

Образец правил:

```xml
<?xml version="1.0" encoding="utf-8"?>
<policy>
  <file path="C:\DriverConfig\data\note.txt">
    <subject name="filetool.exe" read="1" write="0"/>
    <subject name="notepad.exe" read="0" write="0"/>
  </file>
  <file path="C:\DriverConfig\data\report.txt">
    <subject name="filetool.exe" read="1" write="1"/>
  </file>
</policy>
```

Разбор в ядре принимает этот фиксированный вид: UTF-8 без BOM, перевод строки CRLF, без пространств имён и сущностей. До 32 файлов, до 8 субъектов у файла, имена короче 256 символов. Если IOCTL пришёл, а новый XML битый, в памяти остаются прежние правила, и `fsctl` возвращает на диск предыдущий файл.

Управляющее устройство — `\\.\FsFilterX`. Коды в `ioctl.h`: перечитать правила `0x800`, включить нотификатор `0x801`, выключить `0x802`. Драйвер принимает их только от процесса с именем `fsctl.exe`.

## Запустить и выключить

Служба уже создана, sys лежит в `C:\Windows\System32\drivers\FsFilterX.sys`. Нужна командная строка от администратора. В загрузчике включена тестовая подпись (`testsigning Yes`). Без неё ядро этот sys не загрузит.

Загрузка:

```bat
fltmc load FsFilterX
fltmc filters
```

В списке должна быть строка `FsFilterX` с высотой `370030`. При загрузке драйвер сам читает `C:\DriverConfig\policy.xml`. Если файла нет или XML битый, фильтр всё равно стартует, таблица правил пустая: обычные файлы разрешены, а `policy.xml` по-прежнему закрыт для всех, кроме `fsctl.exe`.

Выгрузка:

```bat
fltmc unload FsFilterX
```

Фильтр снимается с дисков, устройство `\\.\FsFilterX` удаляется, нотификатор снимается и журнал закрывается. Служба в реестре остаётся, следующая загрузка — снова `fltmc load`. Состояние нотификатора после выгрузки не сохраняется: новый запуск начинает с выключенного журнала.

Повторить подпись, установку и весь прогон:

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\winuser\Documents\mbks_labs\lab3\install-filter.ps1
```

Скрипт сначала выгружает фильтр и только потом заново кладёт `policy.xml`, `note.txt`, `report.txt` и `free.txt`. Пока фильтр загружен, `powershell.exe` эти защищённые файлы переписать не может. INF для установки не используется: его секция установки заканчивается на сборке 25952, а на машине сборка 28000.

Собрать заново, из каталога `lab3`:

```bat
msbuild FsFilterX\FsFilterX.sln /p:Configuration=Debug /p:Platform=x64
msbuild fsctl\fsctl.vcxproj /p:Configuration=Release /p:Platform=x64
```

Готовый sys: `FsFilterX\FsFilterX\x64\Debug\FsFilterX.sys`. Готовый `fsctl`: `fsctl\x64\Release\fsctl.exe`. Подпись SHA256, сертификат `WDKTestCert winuser` в `Cert:\CurrentUser\My`, отпечаток `906AA1ADCD98DCBC641051CCBEFA9BAADFAB2206`. Это делает `install-filter.ps1`.

## Команды fsctl

Программа: `lab3\fsctl\x64\Release\fsctl.exe`.

```bat
fsctl show
fsctl reload
fsctl set C:\DriverConfig\data\note.txt filetool.exe 1 0
fsctl notify on
fsctl notify off
```

`show` печатает XML и драйвер не трогает. Устройство для этой команды не нужно.

`reload` просит драйвер перечитать уже лежащий на диске `policy.xml`.

`set` открывает устройство, меняет одну пару «файл + программа» и просит драйвер перечитать файл. Повторный `set` для той же пары заменяет флаги, а не добавляет вторую строку. Путь в этих командах без пробелов. Если перечитывание не удалось, на диск возвращается прежний XML и драйвер читает его ещё раз.

`notify on` открывает `C:\DriverConfig\image.log` на дописывание и ставит `PsSetLoadImageNotifyRoutine`. Каждая загрузка модуля дописывает строку: дата и время, pid, короткое имя процесса, путь образа. Пример:

```text
2026-10-30 16:22:15 pid=9908 process=filetool.exe image=\Device\HarddiskVolume3\Users\winuser\Documents\mbks_labs\lab3\filetool\x64\Release\filetool.exe
```

`notify off` снимает оповещение, дожидается уже вошедшего колбэка и закрывает файл. После этого длина журнала от новых запусков программ не растёт.

Пока нотификатор включён, файл журнала открыт драйвером. Читать его можно: драйвер разрешает чужое чтение. Обычный `ReadAllText` в .NET при этом получает отказ совместного доступа, потому что сам не разрешает писателю остаться. Просмотр в блокноте и чтение с `FileShare.ReadWrite` работают.

## Проверка filetool

`filetool` остаётся испытуемым. Сообщение об ошибке по-прежнему с опечаткой: `file openning failed`.

```bat
filetool\x64\Release\filetool.exe r C:\DriverConfig\data\note.txt
filetool\x64\Release\filetool.exe w C:\DriverConfig\data\note.txt text
```

На образце правил чтение `note.txt` через `filetool` разрешено, запись нет. `report.txt` для `filetool` открыт и на чтение, и на запись. Файл, которого нет в XML, например `C:\DriverConfig\data\free.txt`, разрешён любой программе. Копия `filetool.exe`, переименованная в `notepad.exe`, к `note.txt` не допускается: в правилах у `notepad.exe` оба флага нули.

Последний успешный прогон `install-filter.ps1` от 2026-10-30 закончился с `FAILED 0`. Служба после него осталась запущенной. В `note.txt` после проверки смены прав лежит текст `allowed-now`, а в правилах у `filetool.exe` на этот файл снова `read="1"` и `write="0"`.
