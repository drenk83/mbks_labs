# 1. Введение и постановка задачи

## 1.1. Что требуется по заданию

Лабораторная работа № 3 называется «Разработка защитных компонентов, функционирующих на уровне ядра ОС Windows». В ходе работы требуется изучить примеры драйверов и механизм IOCTL, разработать формат хранения правил, написать драйвер-фильтр, написать приложение управления, защитить конфигурационный файл, добавить нотификатор и команды его установки и снятия.

Вариант 9 задаёт четыре конкретных требования:

- объекты — файловая система;
- контроль доступа — дискреционный, для каждого объекта задаётся перечень прав субъектов, по смыслу аналогичный DACL;
- нотификатор — загрузка исполняемых модулей, функция `PsSetLoadImageNotifyRoutine`;
- формат хранения правил — XML, файл лежит в файловой системе.

## 1.2. Что получилось в итоге

В каталоге лабораторной лежат четыре программные части и вспомогательные файлы:

- минифильтр `FsFilterX` с высотой 370030, группой загрузки FSFilter Activity Monitor и зависимостью от `FltMgr`;
- консольная программа `fsctl` с командами `set`, `show`, `reload`, `notify on`, `notify off`;
- файл правил `policy.xml` и его образец в `config\policy.xml`;
- журнал `image.log`, который ведёт нотификатор загрузки образов;
- скрипт `install-filter.ps1`, который подписывает, устанавливает фильтр и прогоняет проверки;
- испытуемая программа `filetool`, которая не менялась с предыдущей работы.

Схема взаимодействия компонентов:

```text
                    пользовательский режим
   +----------------+          +-------------------+
   | filetool.exe   |          | fsctl.exe         |
   | чтение/запись  |          | правила, IOCTL    |
   +--------+-------+          +---------+---------+
            |                            |
            | CreateFile/ReadFile/       | CreateFile("\\.\FsFilterX")
            | WriteFile                  | DeviceIoControl(0x800..0x802)
            |                            |
            v                            v
   +--------------------------------------------------+
   | FsFilterX.sys                                    |
   | минифильтр: CREATE / READ / WRITE                |
   | управляющее устройство \Device\FsFilterX         |
   | нотификатор PsSetLoadImageNotifyRoutine          |
   +----+-----------------------------+---------------+
        |                             |
        | ZwReadFile                  | ZwWriteFile
        v                             v
   C:\DriverConfig\policy.xml     C:\DriverConfig\image.log
```

Драйвер стоит между программой и файловой системой и не подменяет её. Он смотрит на операции открытия, чтения и записи, сверяет пару «файл и процесс» с таблицей правил и либо пропускает запрос, либо завершает его со статусом `STATUS_ACCESS_DENIED`.

## 1.3. Границы решения

Сразу нужно назвать границы, чтобы дальше не было сюрпризов:

- субъект — имя исполняемого файла, а не учётная запись Windows и не SID;
- права только два: чтение и запись; удаление, переименование, смена атрибутов не перехватываются;
- файл, которого нет в XML, не ограничивается;
- путь приводится к диску `C:`, защищаемые файлы лежат на этом диске;
- относительные открытия от дескриптора каталога не разбираются;
- пути и имена в правилах рассчитаны на латиницу;
- файл правил защищён проверкой имени процесса, поэтому копия программы под именем `fsctl.exe` сможет его открыть;
- журнал нотификатора в политике не защищается.

Часть этих ограничений — сознательный выбор, часть — следствие упрощённой модели. Подробно они разобраны в разделе 16.

# 2. История разработки и ключевые решения

Этот раздел отвечает на вопрос «как мы к этому пришли». Он полезен больше, чем перечень функций: в нём видно, какие варианты отброшены и почему.

## 2.1. Отправная точка

К началу новой работы уже был минифильтр, написанный для предыдущего задания. Он умел перехватывать открытие, чтение и запись, приводил `\Device\HarddiskVolumeN\...` к `C:\...`, определял процесс по имени exe и запрещал запись на открытии с усечением. Правила лежали в текстовом файле `C:\DriverConfig\Config.txt` в формате «путь, затем строки процесс|чтение|запись». Файл перечитывался на каждой операции доступа. Программа `filetool` и тестовая подпись тоже уже были.

Для нового варианта этого не хватало: требовались XML, IOCTL-обновление правил и нотификатор загрузки образов.

## 2.2. Что оставили, что убрали

Оставили:

- каркас минифильтра и высоту 370030;
- группу загрузки FSFilter Activity Monitor и зависимость от `FltMgr`;
- перехват `IRP_MJ_CREATE`, `IRP_MJ_READ`, `IRP_MJ_WRITE`;
- приведение пути к букве диска;
- субъект — имя exe без пути, сравнение без учёта регистра;
- отказ `STATUS_ACCESS_DENIED` на открытии с усечением, чтобы запрещённая запись не стирала файл;
- `filetool` с прежним текстом `file opening failed` (с опечаткой, она сохранена как есть);
- тестовую подпись SHA256 сертификатом `WDKTestCert winuser`;
- уже созданную службу `FsFilterX`.

Убрали:

- текстовый формат `процесс|чтение|запись` и старый разбор `ParseBuffer`;
- перечитывание правил на каждой операции;
- правило «файл есть в списке, процесса в списке нет — разрешить»;
- отчёт, в котором не было XML, IOCTL и нотификатора.

Файл `C:\DriverConfig\Config.txt` не удаляли: в нём кроме лабораторных путей есть строки для `mspaint.exe`, и он может понадобиться отдельно. Драйвер его больше не читает.

## 2.3. Решения, которые не пересматривали

1. Субъект — имя исполняемого файла, а не учётная запись. Так был устроен прежний драйвер, так же проще проверить модель на одной машине.
2. Файл, которого нет в XML, не ограничивается. Иначе фильтр запретил бы системе читать собственные модули.
3. Файл, который в XML есть, ведёт себя как DACL: нет строки для процесса — отказ.
4. Файл правил защищён отдельно и в список объектов политики не входит.
5. Правила перечитываются только при загрузке драйвера и по IOCTL.
6. Нотификатор один — загрузка образа; ставится и снимается только по IOCTL.
7. Журнал открывается при включении нотификатора, а в колбэке только дописывается.
8. Команда управления — отдельная программа `fsctl`, `filetool` не превращали в неё.

## 2.4. Этапы работы

1. Переписали `FsFilterX.c`: свой разбор XML, новая семантика доступа, защита файла правил.
2. Добавили `ioctl.h` с общими кодами и управляющее устройство в драйвере.
3. Написали `fsctl`: чтение и запись XML, команда `set`, `show`, `reload`, `notify`.
4. Добавили нотификатор и журнал: открытие описателя при включении, запись строк в колбэке, снятие при выгрузке.
5. Переписали `install-filter.ps1`: подпись, подготовка файлов, загрузка, проверки, журнал прогона.
6. Прогнали проверки, разобрали ошибки, добились `FAILED 0`.
7. Написали отчёт по новому заданию.

## 2.5. Ошибки первых прогонов

Первые прогоны скрипта дали две поучительные ошибки, обе — в измерительной части, а не в драйвере.

Первая: проверка «журнал не растёт» падала. Длину журнала снимали до команды `fsctl notify off`, а пока нотификатор ещё включён, сам `fsctl.exe` загружает DLL, и эти строки попадают в журнал. Правильно снимать длину после выключения нотификатора. В скрипте это исправлено.

Вторая: несколько проверок `hello` упали, потому что `note.txt` остался с текстом `allowed-now`. Скрипт копировал файл, пока фильтр ещё был загружен, а `powershell.exe` в правилах нет, поэтому перезапись защищённого файла не проходила; `Copy-Item` при `$ErrorActionPreference = Continue` не останавливал скрипт. Исправление: сначала выгрузить фильтр, потом класть файлы, потом загружать.

Отдельно выяснилось, что обычный `[IO.File]::ReadAllText` не открывает `image.log`, пока драйвер держит его на запись: у драйвера `FILE_SHARE_READ`, а .NET не ставит `FILE_SHARE_WRITE`. Чтение с `FileShare.ReadWrite` работает; в скрипте для этого написана функция `Read-Shared`.

Третий прогон завершился с `FAILED 0`; с тех пор схема не менялась.

## 3.2. Сценарий загрузки

```text
fltmc load FsFilterX
  -> DriverEntry
     -> ExInitializeResourceLite(&gRuleLock)
     -> ExInitializeResourceLite(&gLogLock)
     -> FltRegisterFilter(driver, &gRegistration, &gFilter)
     -> CreateControlDevice(driver)
        -> IoCreateDevice(\Device\FsFilterX)
        -> IoCreateSymbolicLink(\DosDevices\FsFilterX)
     -> ReloadPolicy()
        -> ZwCreateFile(\DosDevices\C:\DriverConfig\policy.xml)
        -> ZwReadFile
        -> ParsePolicy
        -> PublishRules
     -> FltStartFiltering(gFilter)
```

Если файла правил нет или он пустой, драйвер всё равно загружается: таблица правил остаётся пустой, обычные файлы разрешены, а `policy.xml` по-прежнему закрыт для всех, кроме `fsctl.exe`.

## 3.3. Сценарий доступа к файлу

```text
CreateFile("C:\DriverConfig\data\note.txt", ...)
  -> IRP_MJ_CREATE
     -> PreCreate
        -> пропуск IRP_PAGING_IO и каталогов
        -> CreatePathToC: "\DriverConfig\data\note.txt" -> "C:\DriverConfig\data\note.txt"
        -> RequestExeName: "filetool.exe"
        -> разбор DesiredAccess и Disposition
        -> AccessAllowed(path, exe, isWrite)
           -> файл в правилах? да
           -> процесс в правилах? да
           -> флаг чтения/записи
        -> разрешено: FLT_PREOP_SUCCESS_NO_CALLBACK
        -> запрещено: STATUS_ACCESS_DENIED, FLT_PREOP_COMPLETE
  -> IRP_MJ_READ / IRP_MJ_WRITE
     -> PreRead / PreWrite
        -> OperationPath: нормализованное имя -> "C:\..."
        -> AccessAllowed
```

## 3.4. Сценарий обновления правил

```text
fsctl set C:\DriverConfig\data\note.txt filetool.exe 1 1
  -> CreateFile("\\.\FsFilterX")            проверка, что фильтр загружен
  -> CloseHandle
  -> LoadPolicy()                            читает policy.xml
  -> замена флагов у пары filetool.exe
  -> SavePolicy()                            пишет policy.xml с CRLF
  -> DeviceIoControl(0x800)
     -> IRP_MJ_DEVICE_CONTROL
        -> DispatchIoctl
           -> CurrentExeName == "fsctl.exe"? да
           -> ReloadPolicy()
              -> ZwReadFile(policy.xml)
              -> ParsePolicy
              -> PublishRules
  -> успех: "правила обновлены"
  -> ошибка: вернуть прежний XML и попросить перечитать ещё раз
```

## 3.5. Сценарий нотификатора

```text
fsctl notify on
  -> DeviceIoControl(0x801)
     -> DispatchIoctl
        -> NotifyOn
           -> OpenLog(image.log)
           -> PsSetLoadImageNotifyRoutine(LoadImageNotify)
           -> gNotifySet = 1

загрузка модуля
  -> LoadImageNotify(fullImageName, processId, imageInfo)
     -> gInsideNotify (защита от повторного входа)
     -> PsLookupProcessByProcessId
     -> CopyShortName
     -> WriteLogLine в уже открытый gLogHandle

fsctl notify off
  -> DeviceIoControl(0x802)
     -> DispatchIoctl
        -> NotifyOff
           -> PsRemoveLoadImageNotifyRoutine
           -> ожидание уже вошедшего колбэка
           -> CloseLog
```

## 3.6. Почему минифильтр

Минифильтр регистрируется у `FltMgr`, сообщает высоту и список операций, а диспетчер сам выстраивает цепочку фильтров. Это проще и безопаснее, чем legacy-фильтр, который встраивался в стек устройств вручную: меньше служебного кода, нет своей обработки передачи IRP вниз, проще выгрузка.

Высота 370030 выбрана в группе FSFilter Activity Monitor. Фильтр с большей высотой видит запрос раньше; группа относит драйвер к наблюдающим фильтрам. Для учебной задачи важно, что фильтр видит открытие до того, как файл будет усечён, и может вернуть отказ.

Нотификатор — отдельный механизм, не связанный с перехватом IRP: `PsSetLoadImageNotifyRoutine` вызывает зарегистрированную функцию при загрузке образа в память. Он не требует своей высоты и работает независимо от фильтра.

## 4.3. Подпись

Драйвер подписывается тестовым сертификатом `WDKTestCert winuser` из хранилища текущего пользователя. Отпечаток сертификата:

```text
906AA1ADCD98DCBC641051CCBEFA9BAADFAB2206
```

Подпись и проверка:

```bat
signtool sign /fd SHA256 /sha1 906AA1ADCD98DCBC641051CCBEFA9BAADFAB2206 /s My FsFilterX\FsFilterX\x64\Debug\FsFilterX.sys
signtool verify /pa C:\Windows\System32\drivers\FsFilterX.sys
```

В загрузчике должен быть включён тестовый режим подписи (`testsigning Yes`), иначе ядро не загрузит драйвер, подписанный локальным сертификатом. Secure Boot на машине выключен.

## 4.4. Служба и экземпляр

Служба создаётся один раз:

```bat
sc create FsFilterX type= filesys start= demand binPath= \SystemRoot\System32\drivers\FsFilterX.sys depend= FltMgr group= "FSFilter Activity Monitor"
```

Параметры экземпляра задаются в реестре:

```bat
reg add "HKLM\SYSTEM\CurrentControlSet\Services\FsFilterX\Instances" /v DefaultInstance /t REG_SZ /d "FsFilterX Instance" /f
reg add "HKLM\SYSTEM\CurrentControlSet\Services\FsFilterX\Instances\FsFilterX Instance" /v Altitude /t REG_SZ /d "370030" /f
reg add "HKLM\SYSTEM\CurrentControlSet\Services\FsFilterX\Instances\FsFilterX Instance" /v Flags /t REG_DWORD /d 0 /f
```

Загрузка и проверка:

```bat
fltmc load FsFilterX
fltmc filters
```

В списке должна быть строка `FsFilterX` с высотой `370030`. Выгрузка:

```bat
fltmc unload FsFilterX
```

## 4.5. Почему не INF

Раздел установки в `FsFilterX.inf` рассчитан на сборки до 25952, а на машине сборка 28000. Установщик INF на такой системе не сработает, поэтому фильтр ставится вручную: копирование sys в `System32\drivers`, создание службы, параметры экземпляра и `fltmc load`. INF остаётся в проекте как исторический артефакт и для возможной установки на другой сборке.

## 4.6. Правило пересборки

Пока фильтр загружен, пересобранный `FsFilterX.sys` нельзя скопировать поверх работающего: файл занят. Порядок такой:

```bat
fltmc unload FsFilterX
copy /Y FsFilterX\FsFilterX\x64\Debug\FsFilterX.sys C:\Windows\System32\drivers\FsFilterX.sys
fltmc load FsFilterX
```

`install-filter.ps1` делает это сам: сначала выгружает фильтр, потом кладёт файлы и sys.

# 5. Формат правил XML

## 5.1. Пример файла

```xml
<?xml version="1.0" encoding="utf-8"?>
<policy>
  <file path="C:\DriverConfig\data\note.txt">
    <subject name="filetool.exe" read="1" write="0"/>
    <subject name="notepad.exe" read="0" write="0"/>
  </file>
  <file path="C:\DriverConfig\data\report.txt">
    <subject name="filetool.exe" read="1" write="1"/>
  </file>
</policy>
```

В образце `filetool.exe` может читать `note.txt`, но не может писать; `notepad.exe` не может ни читать, ни писать `note.txt`; `report.txt` открыт `filetool.exe` на чтение и запись.

## 5.2. Грамматика

Формально формат можно описать так:

```text
policy   := '<policy>' file* '</policy>'
file     := '<file path="' PATH '">' subject* '</file>'
subject  := '<subject name="' EXE '" read="' 0|1 '" write="' 0|1 '"/>'
```

Фактический разбор устроен проще: драйвер идёт по строкам и смотрит только строки, которые после пробелов начинаются с `<file ` или `<subject `. Объявление XML, открывающий и закрывающий `<policy>`, закрывающие `</file>` и пустые строки игнорируются. Поэтому формат принимает ровно тот вид, который пишет `fsctl`, и не требует полноценного XML-парсера в ядре.

Имена тегов и атрибутов фиксированы. Пространства имён, комментарии и подстановки XML-сущностей не поддерживаются.

## 5.3. Семантика

| Ситуация | Результат |
|---|---|
| Файла нет в `policy.xml` | Доступ разрешён любой программе |
| Файл есть, процесса в его списке нет | Отказ |
| Процесс есть, `read="1"` | Чтение разрешено |
| Процесс есть, `read="0"` | Чтение запрещено |
| Процесс есть, `write="1"` | Запись разрешена |
| Процесс есть, `write="0"` | Запись запрещена |
| Путь `C:\DriverConfig\policy.xml` | Только `fsctl.exe` и сам драйвер при перечитывании |
| Путь `C:\DriverConfig\image.log` | Разрешён всем: его дописывает драйвер, его нужно читать при проверке |
| Каталог | Не проверяется, запрос пропускается |

Таблица отражает главное отличие от «пустого DACL»: файл, которого нет в политике, — это объект без ограничений, а файл, который в политике есть, но без строки для процесса, — это объект с пустым списком, то есть запрет. Такое поведение выбрано намеренно, иначе фильтр закрыл бы системе доступ к её же модулям.

## 5.4. Пределы и кодировка

Драйвер проверяет:

- не больше 32 файлов;
- не больше 8 субъектов у одного файла;
- длина пути и имени процесса меньше 256 символов.

Дополнительно файл читается в буфер 8192 байта. Практический предел объёма правил — примерно 8 КБ; политика больше этого размера будет отвергнута, а прежние правила останутся в силе. Это ограничение реализации, а не формата.

Кодировка — UTF-8 без BOM, перевод строки — CRLF. Фактический разбор принимает и LF: он считает разделителями и `\r`, и `\n`. Байты старше 127 в значениях атрибутов отвергаются, поэтому пути и имена должны быть латинскими.

## 5.5. Структуры данных

Драйвер хранит правила в двух статических массивах: `gStaging` для разбора и `gRules` для действующей политики.

```c
#define MAX_NAME 256
#define MAX_FILES 32
#define MAX_SUBJECTS 8

typedef struct _SUBJECT {
    WCHAR Name[MAX_NAME];
    WCHAR ReadFlag;
    WCHAR WriteFlag;
} SUBJECT;

typedef struct _FILE_RULE {
    WCHAR Path[MAX_NAME];
    SUBJECT Subjects[MAX_SUBJECTS];
    int SubjectCount;
} FILE_RULE;

static FILE_RULE gRules[MAX_FILES];
static int gRuleCount = 0;
static FILE_RULE gStaging[MAX_FILES];
static int gStagingCount = 0;
```

Флаги хранятся символами `L'0'` и `L'1'`, а не числами. Так их удобно сравнивать с тем, что пришло из XML, и не нужно отдельно проверять диапазон.

## 5.6. Почему свой разбор, а не библиотека

В ядре нет штатной библиотеки XML, а тянуть сторонний парсер в драйвер ради десяти строк формата нерационально: это лишний код, лишние зависимости и лишняя площадь для ошибок. Формат фиксированный, поэтому построчный разбор с проверкой атрибутов проще, быстрее и понятнее.

Обратная сторона: разбор не является полноценным XML-парсером. Он не проверяет вложенность тегов, не понимает сущности и комментарии, не требует закрывающих тегов. Для файла, который пишет только `fsctl`, этого достаточно; для произвольного XML — нет.

# 6. Каркас драйвера

## 6.1. Include-файлы и константы

```c
#include <fltKernel.h>
#include <dontuse.h>
#include <suppress.h>
#include "ioctl.h"

#define MAX_NAME 256
#define MAX_FILES 32
#define MAX_SUBJECTS 8
#define POLICY_BYTES 8192

#define POLICY_PATH L"C:\\DriverConfig\\policy.xml"
#define POLICY_NT_PATH L"\\DosDevices\\C:\\DriverConfig\\policy.xml"
#define LOG_PATH L"C:\\DriverConfig\\image.log"
#define LOG_NT_PATH L"\\DosDevices\\C:\\DriverConfig\\image.log"
#define CONTROL_EXE L"fsctl.exe"

```

`fltKernel.h` подключает интерфейс минифильтра и ядерные типы. `dontuse.h` и `suppress.h` — служебные заголовки WDK, отключающие предупреждения о функциях, которые в драйвере допустимы. `ioctl.h` — свой заголовок с кодами, его же подключает `fsctl`.

Путь для `ZwCreateFile` задан в NT-форме: `\DosDevices\C:\DriverConfig\policy.xml`. Это важно: в контексте системы буква диска может быть не видна, а symbolic link `\DosDevices\C:` виден всегда. Значение `POLICY_PATH` в форме `C:\...` используется для сравнения с путём, который приходит в IRP.

## 6.2. Регистрация операций

```c
static CONST FLT_OPERATION_REGISTRATION gCallbacks[] = {
    { IRP_MJ_CREATE, 0, PreCreate, NULL },
    { IRP_MJ_READ, FLTFL_OPERATION_REGISTRATION_SKIP_PAGING_IO, PreRead, NULL },
    { IRP_MJ_WRITE, FLTFL_OPERATION_REGISTRATION_SKIP_PAGING_IO, PreWrite, NULL },
    { IRP_MJ_OPERATION_END }
};
```

Для чтения и записи стоит флаг `FLTFL_OPERATION_REGISTRATION_SKIP_PAGING_IO`: диспетчер фильтров сам не будет вызывать предобработчик для операций подкачки. В `PreCreate` такого флага нет, поэтому внутри стоит отдельная проверка `IRP_PAGING_IO`: открытие страницы может приходить и с этим флагом, а проверять его на правила не нужно.

У открытия нет флага пропуска каталогов: каталоги проверяются внутри `PreCreate` по `FILE_DIRECTORY_FILE`.

## 6.3. Структура регистрации

static CONST FLT_REGISTRATION gRegistration = {

## 6.4. DriverEntry

```c
NTSTATUS DriverEntry(PDRIVER_OBJECT driver, PUNICODE_STRING registryPath)
{
    NTSTATUS status;

    UNREFERENCED_PARAMETER(registryPath);

    /* Диспетчер фильтров запоминает эти процедуры и вызывает их для
       управляющего устройства. Поставить их нужно до FltRegisterFilter. */
    driver->MajorFunction[IRP_MJ_CREATE] = DispatchCreate;
    driver->MajorFunction[IRP_MJ_CLOSE] = DispatchClose;
    driver->MajorFunction[IRP_MJ_CLEANUP] = DispatchCleanup;
    driver->MajorFunction[IRP_MJ_DEVICE_CONTROL] = DispatchIoctl;

    status = ExInitializeResourceLite(&gRuleLock);
    if (!NT_SUCCESS(status))
        return status;
    status = ExInitializeResourceLite(&gLogLock);
    if (!NT_SUCCESS(status)) {
        ExDeleteResourceLite(&gRuleLock);
        return status;
    }

    status = FltRegisterFilter(driver, &gRegistration, &gFilter);
    if (!NT_SUCCESS(status)) {
        ExDeleteResourceLite(&gRuleLock);
        ExDeleteResourceLite(&gLogLock);
        return status;
    }

    status = CreateControlDevice(driver);
    if (!NT_SUCCESS(status)) {
        FltUnregisterFilter(gFilter);
        ExDeleteResourceLite(&gRuleLock);
        ExDeleteResourceLite(&gLogLock);
        return status;
    }

    status = ReloadPolicy();
    if (!NT_SUCCESS(status))
        DbgPrint("FsFilterX: policy was not applied, code 0x%08x\n", status);

    status = FltStartFiltering(gFilter);
    if (!NT_SUCCESS(status)) {
        DeleteControlDevice();
        FltUnregisterFilter(gFilter);
        ExDeleteResourceLite(&gRuleLock);
        ExDeleteResourceLite(&gLogLock);
    }
    return status;
}
```

Порядок шагов не случаен:

1. Блокировки создаются до всего остального: они нужны и при чтении правил, и при работе колбэков.
2. `FltRegisterFilter` регистрирует минифильтр и запоминает колбэки. С этого момента `gFilter` валиден.
3. `CreateControlDevice` создаёт управляющее устройство и символическую ссылку. Если это не удалось, фильтр снимается, чтобы не осталось полузарегистрированного драйвера.
4. `ReloadPolicy` читает правила. Ошибка не останавливает загрузку: драйвер стартует с пустой политикой, а причина пишется в отладочный вывод. Это сделано намеренно: сломанный XML не должен превращать машину в нерабочую.
5. `FltStartFiltering` включает перехват. До этого момента фильтр зарегистрирован, но запросы ещё не обрабатывает.

Назначение `MajorFunction` до `FltRegisterFilter` — важная тонкость. Диспетчер фильтров при регистрации запоминает драйвер и его процедуры, а управляющее устройство создаётся уже после. Если назначить `MajorFunction` позже, часть запросов к устройству может прийти к стандартному обработчику и завершиться не так, как нужно.

## 6.5. FilterUnload

```c
static NTSTATUS FilterUnload(FLT_FILTER_UNLOAD_FLAGS flags)
{
    UNREFERENCED_PARAMETER(flags);
    NotifyOff();
    DeleteControlDevice();
    FltUnregisterFilter(gFilter);
    ExDeleteResourceLite(&gRuleLock);
    ExDeleteResourceLite(&gLogLock);
    return STATUS_SUCCESS;
}
```

Порядок обратный загрузке:

1. `NotifyOff` снимает нотификатор и ждёт уже вошедший колбэк. Если этого не сделать, после выгрузки в памяти останется указатель на функцию выгруженного драйвера, и первая же загрузка образа приведёт к падению.
2. `DeleteControlDevice` удаляет символическую ссылку и устройство. После этого `fsctl` не может открыть `\\.\FsFilterX`.
3. `FltUnregisterFilter` снимает фильтр с томов.
4. Удаляются блокировки — после того, как их больше никто не использует.

# 7. Чтение и разбор правил в ядре

## 7.1. Чтение файла целиком

```c
static NTSTATUS ReadWholeFile(const WCHAR* ntPath, char* buffer, ULONG bufferSize, ULONG* readBytes)
{
    UNICODE_STRING name;
    OBJECT_ATTRIBUTES attrs;
    IO_STATUS_BLOCK io;
    HANDLE handle = NULL;
    LARGE_INTEGER offset;
    NTSTATUS status;

    *readBytes = 0;
    RtlInitUnicodeString(&name, ntPath);
    InitializeObjectAttributes(&attrs, &name, OBJ_CASE_INSENSITIVE | OBJ_KERNEL_HANDLE, NULL, NULL);
    status = ZwCreateFile(
        &handle,
        GENERIC_READ,
        &attrs,
        &io,
        NULL,
        FILE_ATTRIBUTE_NORMAL,
        FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,
        FILE_OPEN,
        FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE,
        NULL,
        0);
    if (!NT_SUCCESS(status))
        return status;

    offset.QuadPart = 0;
    status = ZwReadFile(handle, NULL, NULL, NULL, &io, buffer, bufferSize - 1, &offset, NULL);
    if (status == STATUS_END_OF_FILE) {
        *readBytes = 0;
        status = STATUS_SUCCESS;
    } else if (NT_SUCCESS(status)) {
        *readBytes = (ULONG)io.Information;
        if (*readBytes >= bufferSize - 1)
            status = STATUS_BUFFER_OVERFLOW;
    }
    ZwClose(handle);
    return status;
}
```

Что здесь важно:

- `OBJ_KERNEL_HANDLE` создаёт описатель в системной таблице, а не в таблице процесса. Он не виден пользовательскому режиму и не мешает при завершении процесса.
- `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` позволяет открыть `policy.xml` даже если кто-то держит его открытым. Для собственного чтения драйверу это удобно, а защита от чужих процессов всё равно выполняется в `PreCreate/PreRead`.
- `FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE` — синхронное открытие файла, не каталога.
- Читается `bufferSize - 1` байт, чтобы в конце гарантированно остался нулевой байт для строковых функций.
- `STATUS_END_OF_FILE` для пустого файла превращается в успех с нулевой длиной.
- Если прочитано `bufferSize - 1` байт, выставляется `STATUS_BUFFER_OVERFLOW`. Это предупреждение, а `NT_SUCCESS` для него ложен, поэтому `ReloadPolicy` не станет разбирать обрезанный файл. Правила останутся прежними.

## 7.2. Разбор атрибута

```c
static int ReadAttr(const char* line, const char* attr, WCHAR* dest, int destChars)
{
    const char* cursor = line;

    dest[0] = 0;
    while (*cursor != 0) {
        const char* a = attr;
        const char* c = cursor;
        while (*a != 0 && *c == *a) {
            a++;
            c++;
        }
        if (*a == 0 && *c == '"') {
            int n = 0;
            c++;
            while (*c != 0 && *c != '"' && n < destChars - 1) {
                if ((unsigned char)*c >= 128)
                    return 0;
                dest[n++] = (WCHAR)(unsigned char)*c;
                c++;
            }
            if (*c != '"')
                return 0;
            dest[n] = 0;
            return n > 0;
        }
        cursor++;
    }
    return 0;
}
```

Функция ищет в строке подстроку вида `имя="значение"`, начиная с любого места. Если после искомого имени нет кавычки, совпадение не считается. Значение копируется в широкую строку посимвольно, байты старше 127 отвергаются: разбор рассчитан на латиницу. Если строка оборвалась до закрывающей кавычки, возвращается ошибка — так ловится слишком длинное значение, не поместившееся в буфер.

Слабое место: поиск идёт по подстроке, а не по имени атрибута с границей. Для фиксированного формата этого достаточно, но произвольный XML с таким разбором лучше не подавать.

## 7.3. Разбор файла

```c
static NTSTATUS ParsePolicy(const char* text)
{
    char line[MAX_NAME * 2];
    int fileIndex = -1;

    gStagingCount = 0;
    RtlZeroMemory(gStaging, sizeof(gStaging));

    while (*text != 0) {
        int length = 0;
        const char* start;

        while (*text != 0 && *text != '\n' && *text != '\r' && length < (int)sizeof(line) - 1)
            line[length++] = *text++;
        line[length] = 0;
        while (*text == '\n' || *text == '\r')
            text++;
        if (length == (int)sizeof(line) - 1 && *text != 0 && *text != '\n' && *text != '\r')
            return STATUS_DATA_ERROR;

        start = SkipSpace(line);
        if (HasPrefix(start, "<file ")) {
            if (gStagingCount >= MAX_FILES)
                return STATUS_DATA_ERROR;
            fileIndex = gStagingCount;
            if (!ReadAttr(start, "path=", gStaging[fileIndex].Path, MAX_NAME))
                return STATUS_DATA_ERROR;
            gStaging[fileIndex].SubjectCount = 0;
            gStagingCount++;
        } else if (HasPrefix(start, "<subject ")) {
            SUBJECT* subject;
            WCHAR flag[4];
            if (fileIndex < 0)
                return STATUS_DATA_ERROR;
            if (gStaging[fileIndex].SubjectCount >= MAX_SUBJECTS)
                return STATUS_DATA_ERROR;
            subject = &gStaging[fileIndex].Subjects[gStaging[fileIndex].SubjectCount];
            if (!ReadAttr(start, "name=", subject->Name, MAX_NAME))
                return STATUS_DATA_ERROR;
            if (!ReadAttr(start, "read=", flag, 4) || (flag[0] != L'0' && flag[0] != L'1') || flag[1] != 0)
                return STATUS_DATA_ERROR;
            subject->ReadFlag = flag[0];
            if (!ReadAttr(start, "write=", flag, 4) || (flag[0] != L'0' && flag[0] != L'1') || flag[1] != 0)
                return STATUS_DATA_ERROR;
            subject->WriteFlag = flag[0];
            gStaging[fileIndex].SubjectCount++;
        }
    }
    return STATUS_SUCCESS;
}
```

Вспомогательные функции:

```c
static const char* SkipSpace(const char* text)
{
    while (*text == ' ' || *text == '\t')
        text++;
    return text;
}

static int HasPrefix(const char* text, const char* prefix)
{
    while (*prefix != 0) {
        if (*text != *prefix)
            return 0;
        text++;
        prefix++;
    }
    return 1;
}
```

Разбор идёт по строкам. Строка копируется в буфер 512 байт; если она не поместилась, возвращается `STATUS_DATA_ERROR`. Строки, которые не начинаются с `<file ` или `<subject `, игнорируются: так пропускаются объявление XML, `<policy>`, закрывающие теги и пустые строки.

`fileIndex` указывает, в какой элемент `gStaging` писать субъекты. Субъект до первого `file` — ошибка. Превышение 32 файлов или 8 субъектов — ошибка. Флаги принимаются только как ровно один символ `0` или `1`; `flag[1] != 0` отсекает `10`, `11` и прочее.

Ошибка в любой строке возвращает ошибку разбора. До публикации дело не доходит, поэтому действующие правила не меняются.

## 7.4. Публикация правил

```c
static void PublishRules(void)
{
    KeEnterCriticalRegion();
    ExAcquireResourceExclusiveLite(&gRuleLock, TRUE);
    RtlCopyMemory(gRules, gStaging, sizeof(gRules));
    gRuleCount = gStagingCount;
    ExReleaseResourceLite(&gRuleLock);
    KeLeaveCriticalRegion();
}
```

Правила копируются целиком, вместе с неиспользуемыми ячейками массива. Это дешевле, чем копировать по одному элементу, и исключает состояние, когда часть массива уже новая, а часть старая. Читатели берут `gRuleLock` в shared-режиме, поэтому не видят промежуточного состояния. `KeEnterCriticalRegion` отключает доставку обычных APC на время работы с ресурсом.

## 7.5. Перечитывание правил

```c
static NTSTATUS ReloadPolicy(void)
{
    char* buffer;
    ULONG bytes = 0;
    NTSTATUS status;

    if (KeGetCurrentIrql() != PASSIVE_LEVEL)
        return STATUS_INVALID_DEVICE_STATE;
    if (InterlockedCompareExchange(&gLoadingPolicy, 1, 0) != 0)
        return STATUS_DEVICE_BUSY;

    gPolicyReader = PsGetCurrentProcess();
    buffer = ExAllocatePoolWithTag(NonPagedPoolNx, POLICY_BYTES, 'ploP');
    if (buffer == NULL) {
        gPolicyReader = NULL;
        InterlockedExchange(&gLoadingPolicy, 0);
        return STATUS_INSUFFICIENT_RESOURCES;
    }
    RtlZeroMemory(buffer, POLICY_BYTES);

    status = ReadWholeFile(POLICY_NT_PATH, buffer, POLICY_BYTES, &bytes);
    if (status == STATUS_OBJECT_NAME_NOT_FOUND || status == STATUS_OBJECT_PATH_NOT_FOUND) {
        gStagingCount = 0;
        RtlZeroMemory(gStaging, sizeof(gStaging));
        PublishRules();
        status = STATUS_SUCCESS;
    } else if (NT_SUCCESS(status)) {
        buffer[bytes] = 0;
        status = ParsePolicy(buffer);
        if (NT_SUCCESS(status))
            PublishRules();
    }

    ExFreePoolWithTag(buffer, 'ploP');
    gPolicyReader = NULL;
    InterlockedExchange(&gLoadingPolicy, 0);
    return status;
}
```

`gLoadingPolicy` выполняет две роли:

1. Не даёт двум потокам перечитывать правила одновременно.
2. Разрешает драйверу открыть `policy.xml` в обход защиты: `AccessAllowed` проверяет, что `gLoadingPolicy` равен 1 и текущий процесс совпадает с `gPolicyReader`.

`gPolicyReader` запоминается до открытия файла и сбрасывается после. Это нужно потому, что `ZwCreateFile` выполняется в контексте того потока, который вызвал IOCTL, а проверка в `PreCreate` видит именно этот процесс.

Поведение по статусам:

| Что произошло | Результат |
|---|---|
| Файла нет | Публикуется пустая политика, возвращается успех |
| Файл пустой | `ReadWholeFile` возвращает успех и 0 байт, публикуется пустая политика |
| Файл больше буфера | `STATUS_BUFFER_OVERFLOW`, правила не меняются, IOCTL возвращает ошибку |
| Ошибка разбора | `STATUS_DATA_ERROR`, правила не меняются |
| Файл прочитан и разобран | Новые правила публикуются, возвращается успех |

Важно, что пустая политика при отсутствии файла — это не ошибка. Иначе после случайного удаления `policy.xml` фильтр нельзя было бы загрузить, а система осталась бы без защиты файла правил.

## 7.6. Схема перечитывания

```text
IOCTL 0x800
  -> ReloadPolicy
     -> KeGetCurrentIrql == PASSIVE?
     -> gLoadingPolicy: 0 -> 1
     -> gPolicyReader = PsGetCurrentProcess()
     -> ExAllocatePoolWithTag(8192)
     -> ReadWholeFile
        -> ZwCreateFile(\DosDevices\C:\DriverConfig\policy.xml)
        -> ZwReadFile
     -> ParsePolicy -> gStaging
     -> PublishRules -> gRules
     -> gPolicyReader = NULL
     -> gLoadingPolicy: 1 -> 0
  -> статус в IRP
```

Если на любом шаге произошла ошибка, `gLoadingPolicy` и `gPolicyReader` всё равно сбрасываются: иначе следующий `reload` навсегда получил бы `STATUS_DEVICE_BUSY`.

# 8. Определение субъекта

## 8.1. Сравнение без учёта регистра

```c
static int SameText(const WCHAR* left, const WCHAR* right)
{
    while (*left != 0 && *right != 0) {
        WCHAR a = *left;
        WCHAR b = *right;
        if (a >= L'A' && a <= L'Z')
            a = (WCHAR)(a - L'A' + L'a');
        if (b >= L'A' && b <= L'Z')
            b = (WCHAR)(b - L'A' + L'a');
        if (a != b)
            return 0;
        left++;
        right++;
    }
    return *left == *right;
}
```

Функция сравнивает две строки посимвольно, приводя только латинские заглавные буквы к строчным. Русские буквы не приводятся: в правилах и в именах процессов используется латиница. Строки должны заканчиваться нулём; длины не сравниваются отдельно, потому что конец строки и есть нулевой символ.

## 8.2. Выделение имени из пути

```c
static void KeepFileName(WCHAR* path)
{
    WCHAR* slash = NULL;
    WCHAR* cursor = path;
    int i;

    while (*cursor != 0) {
        if (*cursor == L'\\')
            slash = cursor;
        cursor++;
    }
    if (slash == NULL)
        return;
    slash++;
    i = 0;
    while (slash[i] != 0 && i < MAX_NAME - 1) {
        path[i] = slash[i];
        i++;
    }
    path[i] = 0;
}
```

Функция ищет последний обратный слэш и сдвигает остаток строки в начало. Если слэша нет, строка уже является именем и остаётся как есть. Результат — имя exe без пути.

## 8.3. Полное имя процесса

```c
static NTSTATUS QueryProcessImage(PEPROCESS process, WCHAR* dest, int destChars)
{
    HANDLE handle = NULL;
    UNICODE_STRING* image = NULL;
    ULONG bytes = 0;
    NTSTATUS status;
    size_t chars;

    dest[0] = 0;
    if (process == NULL || destChars < 2)
        return STATUS_INVALID_PARAMETER;

    status = ObOpenObjectByPointer(process, OBJ_KERNEL_HANDLE, NULL, 0, NULL, KernelMode, &handle);
    if (!NT_SUCCESS(status))
        return status;

    if (gQueryProcess == NULL) {
        UNICODE_STRING name;
        RtlInitUnicodeString(&name, L"ZwQueryInformationProcess");
        gQueryProcess = (QUERY_INFO_PROCESS)MmGetSystemRoutineAddress(&name);
        if (gQueryProcess == NULL) {
            ZwClose(handle);
            return STATUS_PROCEDURE_NOT_FOUND;
        }
    }

    status = gQueryProcess(handle, ProcessImageFileName, NULL, 0, &bytes);
    if (status != STATUS_INFO_LENGTH_MISMATCH) {
        ZwClose(handle);
        return status;
    }

    image = ExAllocatePoolWithTag(NonPagedPoolNx, bytes, 'xsFF');
    if (image == NULL) {
        ZwClose(handle);
        return STATUS_INSUFFICIENT_RESOURCES;
    }

    status = gQueryProcess(handle, ProcessImageFileName, image, bytes, &bytes);
    if (!NT_SUCCESS(status) || image->Buffer == NULL) {
        ExFreePoolWithTag(image, 'xsFF');
        ZwClose(handle);
        return NT_SUCCESS(status) ? STATUS_UNSUCCESSFUL : status;
    }

    chars = image->Length / sizeof(WCHAR);
    if (chars >= (size_t)destChars)
        chars = (size_t)destChars - 1;
    RtlCopyMemory(dest, image->Buffer, chars * sizeof(WCHAR));
    dest[chars] = 0;
    ExFreePoolWithTag(image, 'xsFF');
    ZwClose(handle);
    return STATUS_SUCCESS;
}
```

Функция устроена по классической схеме «два вызова»:

1. `ObOpenObjectByPointer` открывает процесс как объект ядра. В режиме ядра проверка прав не выполняется, и полученный дескриптор годится для `ZwQueryInformationProcess`.
2. `ZwQueryInformationProcess` с классом `ProcessImageFileName` при первом вызове и `NULL`-буфером возвращает `STATUS_INFO_LENGTH_MISMATCH` и требуемый размер.
3. Буфер выделяется в `NonPagedPoolNx` с тегом `'xsFF'`.
4. Второй вызов заполняет `UNICODE_STRING` с путём вида `\Device\HarddiskVolume3\Users\winuser\...\filetool.exe`.
5. Строка копируется в `dest` с ограничением длины, буфер освобождается, дескриптор закрывается.

Почему адрес `ZwQueryInformationProcess` ищется через `MmGetSystemRoutineAddress`, а не вызывается напрямую: так функция не требует явной импортной библиотеки и один раз кэшируется в `gQueryProcess`. Для учебного драйвера это удобно; в реальном проекте обычно вызывают напрямую.

Ограничение: функция работает только на `PASSIVE_LEVEL`. Поэтому вызывающий код сначала проверяет уровень, а при невозможности получить полное имя использует короткое.

## 8.4. Короткое имя процесса

```c
static void CopyShortName(PEPROCESS process, WCHAR* dest, int destChars)
{
    const UCHAR* raw;
    int i;

    dest[0] = 0;
    if (process == NULL || destChars < 2)
        return;
    raw = PsGetProcessImageFileName(process);
    if (raw == NULL)
        return;
    for (i = 0; raw[i] != 0 && i < 14 && i < destChars - 1; i++)
        dest[i] = (WCHAR)raw[i];
    dest[i] = 0;
}
```

`PsGetProcessImageFileName` возвращает указатель на короткое имя в структуре процесса. Оно хранится в буфере фиксированного размера и обрезается до 14 символов. Функция не выделяет память и не обращается к файловой системе, поэтому её можно вызывать в том числе на повышенном IRQL. Для `filetool.exe` и `fsctl.exe` длины хватает; для длинных имён имя будет обрезано.

## 8.5. Два варианта получения имени

```c
static void CurrentExeName(WCHAR* dest, int destChars)
{
    dest[0] = 0;
    if (KeGetCurrentIrql() == PASSIVE_LEVEL &&
        NT_SUCCESS(QueryProcessImage(PsGetCurrentProcess(), dest, destChars))) {
        KeepFileName(dest);
        if (dest[0] != 0)
            return;
    }
    CopyShortName(PsGetCurrentProcess(), dest, destChars);
}

static void RequestExeName(PFLT_CALLBACK_DATA data, WCHAR* dest, int destChars)
{
    PEPROCESS process;

    dest[0] = 0;
    process = IoThreadToProcess(data->Thread);
    if (KeGetCurrentIrql() == PASSIVE_LEVEL &&
        NT_SUCCESS(QueryProcessImage(process, dest, destChars))) {
        KeepFileName(dest);
        if (dest[0] != 0)
            return;
    }
    CopyShortName(process, dest, destChars);
}
```

`CurrentExeName` нужен в обработчике IOCTL: там субъект — текущий процесс, тот, который открыл устройство. `RequestExeName` нужен в предобработчиках файловых операций: там субъект — поток, от которого пришёл IRP, а не обязательно текущий поток. `IoThreadToProcess(data->Thread)` даёт процесс этого потока.

Оба варианта сначала пытаются получить полное имя, а при неудаче откатываются на короткое. Это важно для стабильности: если процесс завершается или запрос пришёл в необычном контексте, фильтр не должен падать и не должен считать, что субъект неизвестен.

## 8.6. Проверка управляющей программы

```c
static int IsControlProgram(const WCHAR* exeName)
{
    return SameText(exeName, CONTROL_EXE);
}
```

Одна и та же проверка используется в двух местах: в `DispatchIoctl` для допуска команд и в `AccessAllowed` для доступа к `policy.xml`. Требование «имя `fsctl.exe` для IOCTL и для исключения на `policy.xml` — одна и та же проверка» выполнено буквально: обе точки вызывают `IsControlProgram`.

# 9. Определение пути

## 9.1. Путь тома к букве диска

```c
static int VolumePathToC(const WCHAR* full, WCHAR* dest, int destChars)
{
    const WCHAR marker[] = L"HarddiskVolume";
    const int markerLen = 14;
    int i;
    int start = -1;
    int out;

    dest[0] = 0;
    for (i = 0; full[i] != 0 && i < MAX_NAME - markerLen; i++) {
        int k;
        int match = 1;
        for (k = 0; k < markerLen; k++) {
            if (full[i + k] != marker[k]) {
                match = 0;
                break;
            }
        }
        if (match) {
            start = i + markerLen;
            break;
        }
    }
    if (start < 0)
        return 0;
    while (full[start] >= L'0' && full[start] <= L'9')
        start++;
    if (destChars < 4)
        return 0;
    dest[0] = L'C';
    dest[1] = L':';
    out = 2;
    for (i = start; full[i] != 0 && out < destChars - 1; i++)
        dest[out++] = full[i];
    dest[out] = 0;
    return 1;
}
```

Функция ищет в строке подстроку `HarddiskVolume`, пропускает номер тома и всё оставшееся копирует после `C:`. Пример:

```text
\Device\HarddiskVolume3\DriverConfig\data\note.txt
-> C:\DriverConfig\data\note.txt
```

Ограничение: буква всегда `C:`. Защищаемые файлы лежат на этом диске, поэтому для лабораторной этого достаточно. Если на машине есть другой том с таким же относительным путём, он будет отображён на `C:` и может быть ошибочно проверен по правилам. Это осознанное упрощение.

## 9.2. Путь для открытия

```c
static int CreatePathToC(PFLT_CALLBACK_DATA data, WCHAR* dest, int destChars)
{
    PFILE_OBJECT file;
    USHORT chars;
    USHORT i;
    int out;

    dest[0] = 0;
    file = data->Iopb->TargetFileObject;
    if (file == NULL || file->RelatedFileObject != NULL)
        return 0;
    if (file->FileName.Buffer == NULL || file->FileName.Length == 0)
        return 0;
    chars = file->FileName.Length / sizeof(WCHAR);
    if (chars == 0 || chars >= destChars - 2)
        return 0;
    dest[0] = L'C';
    dest[1] = L':';
    out = 2;
    for (i = 0; i < chars; i++)
        dest[out++] = file->FileName.Buffer[i];
    dest[out] = 0;
    return 1;
}
```

В `IRP_MJ_CREATE` у объекта файла имя обычно хранится без буквы диска: `\DriverConfig\data\note.txt`. Функция добавляет `C:` и получает полный путь. Если `RelatedFileObject` не `NULL`, значит, открытие относительное (от дескриптора каталога), и функция возвращает 0: такой запрос фильтр не проверяет.

Именно из-за этой проверки относительное открытие обходит контроль на открытии. Для `filetool` и `fsctl` это не важно: они передают полные пути. Но в разделе 16 это отмечено как ограничение.

## 9.3. Путь для чтения и записи

```c
static int OperationPath(PFLT_CALLBACK_DATA data, WCHAR* dest, int destChars)
{
    PFLT_FILE_NAME_INFORMATION info = NULL;
    NTSTATUS status;
    WCHAR raw[MAX_NAME];
    USHORT chars;
    int ok = 0;

    dest[0] = 0;
    status = FltGetFileNameInformation(data, FLT_FILE_NAME_NORMALIZED | FLT_FILE_NAME_QUERY_DEFAULT, &info);
    if (!NT_SUCCESS(status))
        return 0;
    status = FltParseFileNameInformation(info);
    if (NT_SUCCESS(status) && info->Name.Buffer != NULL) {
        chars = info->Name.Length / sizeof(WCHAR);
        if (chars > 0 && chars < MAX_NAME) {
            RtlCopyMemory(raw, info->Name.Buffer, chars * sizeof(WCHAR));
            raw[chars] = 0;
            ok = VolumePathToC(raw, dest, destChars);
        }
    }
    FltReleaseFileNameInformation(info);
    return ok;
}
```

В чтении и записи нет `FileObject->FileName` в удобном виде, зато диспетчер фильтров умеет вернуть нормализованное имя. `FLT_FILE_NAME_NORMALIZED` даёт полный путь с томом, `FltParseFileNameInformation` разбирает его на компоненты. Дальше `VolumePathToC` заменяет том на `C:`.

Если имя получить не удалось или путь не содержит `HarddiskVolume`, функция возвращает 0, и операция пропускается. Это лучше, чем запретить всё: сбой в получении имени не должен ломать файловую систему.

## 9.4. Что проверяется, а что нет

| Операция | Источник имени | Что проверяется |
|---|---|---|
| `IRP_MJ_CREATE` | `FileObject->FileName` + `C:` | полный путь, если открытие не относительное |
| `IRP_MJ_READ` | `FltGetFileNameInformation` | нормализованный путь |
| `IRP_MJ_WRITE` | `FltGetFileNameInformation` | нормализованный путь |
| Каталог | `FILE_DIRECTORY_FILE` | пропускается |
| Подкачка | `IRP_PAGING_IO` | пропускается |
| Относительный путь | `RelatedFileObject` | пропускается |

# 10. Логика доступа

## 10.1. Основная функция

```c
static int AccessAllowed(const WCHAR* path, const WCHAR* exeName, int isWrite)
{
    int allowed = 1;
    int i;

    if (SameText(path, LOG_PATH))
        return 1;

    if (SameText(path, POLICY_PATH)) {
        if (gLoadingPolicy && PsGetCurrentProcess() == gPolicyReader)
            return 1;
        return IsControlProgram(exeName);
    }

    KeEnterCriticalRegion();
    ExAcquireResourceSharedLite(&gRuleLock, TRUE);
    for (i = 0; i < gRuleCount; i++) {
        int j;
        if (!SameText(gRules[i].Path, path))
            continue;
        allowed = 0;
        for (j = 0; j < gRules[i].SubjectCount; j++) {
            WCHAR flag;
            if (!SameText(gRules[i].Subjects[j].Name, exeName))
                continue;
            flag = isWrite ? gRules[i].Subjects[j].WriteFlag : gRules[i].Subjects[j].ReadFlag;
            allowed = (flag == L'1');
            break;
        }
        break;
    }
    ExReleaseResourceLite(&gRuleLock);
    KeLeaveCriticalRegion();
    return allowed;
}
```

Порядок проверок:

1. `image.log` разрешён всегда. Его дописывает драйвер, и его нужно читать при проверке; защищать журнал в этой модели не требуется.
2. `policy.xml` обрабатывается отдельно: разрешён, если идёт собственное чтение драйвера (`gLoadingPolicy` и текущий процесс равен `gPolicyReader`) или если процесс называется `fsctl.exe`. Запись в XML другим процессам запрещена.
3. Дальше идёт поиск файла в `gRules`. Если файла нет, `allowed` остаётся 1 — доступ разрешён.
4. Если файл найден, `allowed` сразу становится 0. Затем ищется субъект. Если субъекта нет, остаётся 0 — отказ.
5. Если субъект найден, берётся его флаг: `1` разрешает, `0` запрещает. После этого поиск прекращается.

Возвращается целое число, а не `NTSTATUS`: вызывающему важно только «можно или нельзя».

## 10.2. Отказ

```c
static FLT_PREOP_CALLBACK_STATUS Deny(PFLT_CALLBACK_DATA data)
{
    data->IoStatus.Status = STATUS_ACCESS_DENIED;
    data->IoStatus.Information = 0;
    return FLT_PREOP_COMPLETE;
}
```

`FLT_PREOP_COMPLETE` означает, что фильтр завершил запрос сам и дальше он не пойдёт. `STATUS_ACCESS_DENIED` — стандартный статус отказа в доступе; именно его получает `CreateFile`/`ReadFile`/`WriteFile`, и программа видит ошибку доступа.

## 10.3. Открытие

```c
static FLT_PREOP_CALLBACK_STATUS PreCreate(PFLT_CALLBACK_DATA data, PCFLT_RELATED_OBJECTS objects, PVOID* context)
{
    WCHAR path[MAX_NAME];
    WCHAR exeName[MAX_NAME];
    ACCESS_MASK desired = 0;
    ULONG disposition;
    int wantsWrite;
    int wantsRead;

    UNREFERENCED_PARAMETER(objects);
    UNREFERENCED_PARAMETER(context);

    if (FlagOn(data->Iopb->IrpFlags, IRP_PAGING_IO))
        return FLT_PREOP_SUCCESS_NO_CALLBACK;
    if (FlagOn(data->Iopb->Parameters.Create.Options, FILE_DIRECTORY_FILE))
        return FLT_PREOP_SUCCESS_NO_CALLBACK;
    if (!CreatePathToC(data, path, MAX_NAME))
        return FLT_PREOP_SUCCESS_NO_CALLBACK;

    RequestExeName(data, exeName, MAX_NAME);
    if (data->Iopb->Parameters.Create.SecurityContext != NULL)
        desired = data->Iopb->Parameters.Create.SecurityContext->DesiredAccess;
    disposition = (data->Iopb->Parameters.Create.Options >> 24) & 0xFF;

    /* ofstream открывает файл с CREATE_ALWAYS и обнуляет его ещё до WRITE. */
    wantsWrite = (desired & (FILE_WRITE_DATA | FILE_APPEND_DATA | GENERIC_WRITE | GENERIC_ALL)) != 0
        || disposition == FILE_SUPERSEDE
        || disposition == FILE_CREATE
        || disposition == FILE_OVERWRITE
        || disposition == FILE_OVERWRITE_IF;
    wantsRead = (desired & (FILE_READ_DATA | GENERIC_READ | GENERIC_ALL)) != 0;

    if (wantsWrite && !AccessAllowed(path, exeName, 1))
        return Deny(data);
    if (wantsRead && !AccessAllowed(path, exeName, 0))
        return Deny(data);
    return FLT_PREOP_SUCCESS_NO_CALLBACK;
}
```

Разбор:

- `IRP_PAGING_IO` и каталоги пропускаются до всякой проверки.
- `CreatePathToC` возвращает 0 для относительных открытий и для путей, которые не помещаются в буфер. Такие запросы пропускаются.
- `DesiredAccess` берётся из `SecurityContext`, если он есть. У ядерных вызовов контекста может не быть, тогда `desired` остаётся 0.
- `Disposition` — старший байт `Options`. Значения `FILE_SUPERSEDE`, `FILE_CREATE`, `FILE_OVERWRITE`, `FILE_OVERWRITE_IF` означают, что открытие само меняет файл, даже если в `DesiredAccess` нет явной записи.
- `wantsWrite` включает биты записи, `GENERIC_WRITE`, `GENERIC_ALL` и все «создающие» disposition.
- `wantsRead` включает `FILE_READ_DATA`, `GENERIC_READ`, `GENERIC_ALL`.
- Если нужна запись, проверяется право записи; если нужно чтение — право чтения. Если нужны оба, должны пройти обе проверки.
- При отказе возвращается `STATUS_ACCESS_DENIED`, и файл не открывается. Это ключевой момент: усечение происходит внутри обработки открытия, поэтому запрет должен стоять именно здесь.

## 10.4. Чтение и запись

```c
static FLT_PREOP_CALLBACK_STATUS CheckDataOp(PFLT_CALLBACK_DATA data, int isWrite)
{
    WCHAR path[MAX_NAME];
    WCHAR exeName[MAX_NAME];

    if (FlagOn(data->Iopb->IrpFlags, IRP_PAGING_IO))
        return FLT_PREOP_SUCCESS_NO_CALLBACK;
    if (!OperationPath(data, path, MAX_NAME))
        return FLT_PREOP_SUCCESS_NO_CALLBACK;
    RequestExeName(data, exeName, MAX_NAME);
    if (!AccessAllowed(path, exeName, isWrite))
        return Deny(data);
    return FLT_PREOP_SUCCESS_NO_CALLBACK;
}
```

`PreRead` и `PreWrite` — тонкие обёртки:

```c
static FLT_PREOP_CALLBACK_STATUS PreRead(PFLT_CALLBACK_DATA data, PCFLT_RELATED_OBJECTS objects, PVOID* context)
{
    UNREFERENCED_PARAMETER(objects);
    UNREFERENCED_PARAMETER(context);
    return CheckDataOp(data, 0);
}

static FLT_PREOP_CALLBACK_STATUS PreWrite(PFLT_CALLBACK_DATA data, PCFLT_RELATED_OBJECTS objects, PVOID* context)
{
    UNREFERENCED_PARAMETER(objects);
    UNREFERENCED_PARAMETER(context);
    return CheckDataOp(data, 1);
}
```

Проверка на чтении и записи нужна даже при проверке на открытии. Причины две. Во-первых, файл могли открыть до загрузки фильтра, и на открытии проверки не было. Во-вторых, права могли измениться через `fsctl set` уже после открытия; следующая операция должна увидеть новые правила.

## 10.5. Почему запрет на открытии

Стандартный поток вывода файла в C++ открывает файл с `CREATE_ALWAYS`:

```cpp
std::ofstream out(file_name);   // внутри CreateFile(..., CREATE_ALWAYS, ...)
```

`CREATE_ALWAYS` означает «создать или перезаписать»: файловая система обнуляет содержимое ещё на этапе обработки `IRP_MJ_CREATE`, до того как программа отправит первый `IRP_MJ_WRITE`. Если проверять только запись, файл к моменту отказа уже будет пустым. Поэтому `wantsWrite` включает не только биты доступа, но и disposition, а отказ возвращается на открытии.

Именно это проверяет `filetool`: запись `hacked` в `note.txt` печатает `file openning failed`, а повторное чтение показывает `hello`, то есть старое содержимое не стёрлось.

# 11. Управляющее устройство и IOCTL

## 11.1. Общие коды

`ioctl.h` подключают и драйвер, и `fsctl`, поэтому номера команд не могут разъехаться:

```c
#pragma once

#define IOCTL_FSFILTERX_RELOAD \
    CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800, METHOD_BUFFERED, FILE_ANY_ACCESS)

#define IOCTL_FSFILTERX_NOTIFY_ON \
    CTL_CODE(FILE_DEVICE_UNKNOWN, 0x801, METHOD_BUFFERED, FILE_ANY_ACCESS)

#define IOCTL_FSFILTERX_NOTIFY_OFF \
    CTL_CODE(FILE_DEVICE_UNKNOWN, 0x802, METHOD_BUFFERED, FILE_ANY_ACCESS)
```

## 11.2. Как собирается код IOCTL

`CTL_CODE(DeviceType, Function, Method, Access)` упаковывает четыре поля в 32-битное число:

```text
31            16 15   14 13        2 1      0
+----------------+-------+-----------+--------+
|  DeviceType    | Access|  Function | Method |
+----------------+-------+-----------+--------+
```

- `DeviceType` — тип устройства; `FILE_DEVICE_UNKNOWN` равен `0x22`;
- `Access` — требуемый доступ; `FILE_ANY_ACCESS` равен 0;
- `Function` — номер функции; в работе `0x800`, `0x801`, `0x802`;
- `Method` — способ передачи буфера; `METHOD_BUFFERED` равен 0.

Для `0x800` получается `0x222000`, для `0x801` — `0x222004`, для `0x802` — `0x222008`. В коде эти числа не пишутся вручную: используется макрос, поэтому при смене типа устройства или метода номера пересчитываются автоматически.

`METHOD_BUFFERED` означает, что диспетчер ввода-вывода сам копирует буфер между пользовательским и системным адресным пространством. В работе буферы не используются: командам не нужны входные и выходные данные, важен только статус. `FILE_ANY_ACCESS` означает, что проверка прав доступа к устройству не выполняется на уровне объекта; вместо неё драйвер сам проверяет имя процесса.

## 11.3. Создание устройства

```c
static NTSTATUS CreateControlDevice(PDRIVER_OBJECT driver)
{
    UNICODE_STRING deviceName;
    UNICODE_STRING linkName;
    NTSTATUS status;

    RtlInitUnicodeString(&deviceName, DEVICE_NAME);
    RtlInitUnicodeString(&linkName, DEVICE_LINK);
    status = IoCreateDevice(driver, 0, &deviceName, FILE_DEVICE_UNKNOWN, 0, FALSE, &gDevice);
    if (!NT_SUCCESS(status))
        return status;
    status = IoCreateSymbolicLink(&linkName, &deviceName);
    if (!NT_SUCCESS(status)) {
        IoDeleteDevice(gDevice);
        gDevice = NULL;
        return status;
    }
    gDevice->Flags |= DO_BUFFERED_IO;
    gDevice->Flags &= ~DO_DEVICE_INITIALIZING;
    return STATUS_SUCCESS;
}
```

Разбор:

- `IoCreateDevice` создаёт объект устройства с именем `\Device\FsFilterX`. Размер расширения устройства 0: своё состояние драйвер хранит в глобальных переменных.
- `IoCreateSymbolicLink` создаёт ссылку `\DosDevices\FsFilterX`, по которой пользовательский режим открывает `\\.\FsFilterX`.
- `DO_BUFFERED_IO` включает буферизованный ввод-вывод.
- Снятие `DO_DEVICE_INITIALIZING` обязательно: пока флаг стоит, диспетчер ввода-вывода не пропускает к устройству запросы открытия.

При ошибке создания ссылки устройство удаляется, чтобы не осталось «висящего» объекта.

## 11.4. Открытие, закрытие, очистка

```c
static NTSTATUS DispatchCreate(PDEVICE_OBJECT device, PIRP irp)
{
    UNREFERENCED_PARAMETER(device);
    return CompleteIrp(irp, STATUS_SUCCESS);
}
```

`DispatchClose` и `DispatchCleanup` устроены так же: они просто завершают IRP успехом. Драйверу не нужно хранить состояние соединения, потому что все команды приходят отдельными IOCTL и проверяются по имени процесса.

```c
static NTSTATUS CompleteIrp(PIRP Irp, NTSTATUS status)
{
    Irp->IoStatus.Status = status;
    Irp->IoStatus.Information = 0;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return status;
}
```

`IoCompleteRequest` с `IO_NO_INCREMENT` не повышает приоритет потока: команды короткие и не требуют планировочных привилегий.

## 11.5. Обработчик IOCTL

```c
static NTSTATUS DispatchIoctl(PDEVICE_OBJECT device, PIRP irp)
{
    PIO_STACK_LOCATION stack;
    WCHAR exeName[MAX_NAME];
    ULONG code;
    NTSTATUS status;

    UNREFERENCED_PARAMETER(device);
    stack = IoGetCurrentIrpStackLocation(irp);
    code = stack->Parameters.DeviceIoControl.IoControlCode;
    CurrentExeName(exeName, MAX_NAME);
    if (!IsControlProgram(exeName))
        return CompleteIrp(irp, STATUS_ACCESS_DENIED);

    switch (code) {
    case IOCTL_FSFILTERX_RELOAD:
        status = ReloadPolicy();
        break;
    case IOCTL_FSFILTERX_NOTIFY_ON:
        status = NotifyOn();
        break;
    case IOCTL_FSFILTERX_NOTIFY_OFF:
        status = NotifyOff();
        break;
    default:
        status = STATUS_INVALID_DEVICE_REQUEST;
        break;
    }
    return CompleteIrp(irp, status);
}
```

Проверка имени процесса стоит перед `switch`: любой процесс может открыть `\\.\FsFilterX`, но команду получит только `fsctl.exe`. Остальным возвращается `STATUS_ACCESS_DENIED`. Неизвестный код возвращает `STATUS_INVALID_DEVICE_REQUEST`.

Обратите внимание: драйвер не смотрит на `Method` и не проверяет размеры буферов, потому что команды не передают данные. Если бы появились команды с параметрами, здесь понадобилась бы проверка `stack->Parameters.DeviceIoControl.InputBufferLength` и `OutputBufferLength`.

## 11.6. Пользовательская сторона

```cpp
static HANDLE OpenDevice()
{
    return CreateFileW(kDevicePath, GENERIC_READ | GENERIC_WRITE, 0, NULL, OPEN_EXISTING, 0, NULL);
}

static bool SendIoctl(DWORD code)
{
    HANDLE device = OpenDevice();
    DWORD returned = 0;
    BOOL ok;
    if (device == INVALID_HANDLE_VALUE) {
        std::wcout << L"устройство не открылось\n";
        return false;
    }
    ok = DeviceIoControl(device, code, NULL, 0, NULL, 0, &returned, NULL);
    CloseHandle(device);
    if (!ok)
        std::wcout << L"IOCTL не выполнен, код " << GetLastError() << L"\n";
    return ok == TRUE;
}
```

`CreateFileW` открывает символическую ссылку, `DeviceIoControl` передаёт код. Буферы не нужны, поэтому все размеры нулевые. При ошибке `GetLastError` показывает, что именно не так: чаще всего `ERROR_FILE_NOT_FOUND`, если фильтр не загружен, или `ERROR_ACCESS_DENIED`, если команда пришла не от `fsctl.exe` (в штатной работе такого быть не должно, потому что программа и есть `fsctl.exe`).

## 11.7. Статусы

| Статус | Когда возвращается | Что видит `fsctl` |
|---|---|---|
| `STATUS_SUCCESS` | Команда выполнена | Успех |
| `STATUS_ACCESS_DENIED` | Процесс не `fsctl.exe` | `IOCTL не выполнен, код 5` |
| `STATUS_INVALID_DEVICE_REQUEST` | Неизвестный код | `IOCTL не выполнен` |
| `STATUS_DEVICE_BUSY` | Уже идёт перечитывание | `IOCTL не выполнен` |
| `STATUS_DATA_ERROR` | Ошибка разбора XML | `IOCTL не выполнен` |
| `STATUS_BUFFER_OVERFLOW` | Файл правил больше 8 КБ | `IOCTL не выполнен` |
| `STATUS_INSUFFICIENT_RESOURCES` | Не удалось выделить буфер | `IOCTL не выполнен` |
| `STATUS_OBJECT_NAME_NOT_FOUND` | Файла правил нет (при загрузке) | Не ошибка: пустая политика |

# 12. Программа fsctl

## 12.1. Командная строка

```text
fsctl set <путь> <процесс.exe> <чтение 0|1> <запись 0|1>
fsctl show
fsctl reload
fsctl notify on
fsctl notify off
```

Разбор команд в `main`:

```cpp
int main(int argc, char** argv)
{
    if (argc < 2) {
        Usage();
        return 1;
    }
    std::string command = argv[1];
    if (command == "set")
        return CommandSet(argc, argv);
    if (command == "show")
        return CommandShow();
    if (command == "reload")
        return SendIoctl(IOCTL_FSFILTERX_RELOAD) ? 0 : 1;
    if (command == "notify" && argc == 3 && std::string(argv[2]) == "on")
        return SendIoctl(IOCTL_FSFILTERX_NOTIFY_ON) ? 0 : 1;
    if (command == "notify" && argc == 3 && std::string(argv[2]) == "off")
        return SendIoctl(IOCTL_FSFILTERX_NOTIFY_OFF) ? 0 : 1;
    Usage();
    return 1;
}
```

`show` работает без драйвера: она только читает файл. `reload` и `notify` без драйвера вернут ошибку открытия устройства. `set` сначала проверяет устройство, поэтому при выгруженном фильтре файл не меняется.

## 12.2. Чтение XML

```cpp
static bool LoadPolicy(std::vector<FileRule>& rules, std::wstring& error)
{
    std::ifstream in(kPolicyPathA, std::ios::binary);
    if (!in) {
        rules.clear();
        return true;
    }
    std::string line;
    int fileIndex = -1;
    rules.clear();
    while (std::getline(in, line)) {
        line = Trim(line);
        if (line.compare(0, 6, "<file ") == 0) {
            FileRule rule;
            if (!ReadAttr(line, "path=", rule.path)) {
                error = L"в policy.xml нет path";
                return false;
            }
            rules.push_back(rule);
            fileIndex = (int)rules.size() - 1;
        } else if (line.compare(0, 9, "<subject ") == 0) {
            Subject subject;
            std::string flag;
            if (fileIndex < 0 || !ReadAttr(line, "name=", subject.name)) {
                error = L"в policy.xml испорчен subject";
                return false;
            }
            if (!ReadAttr(line, "read=", flag) || flag.size() != 1 || (flag[0] != '0' && flag[0] != '1')) {
                error = L"в policy.xml испорчен read";
                return false;
            }
            subject.readFlag = flag[0];
            if (!ReadAttr(line, "write=", flag) || flag.size() != 1 || (flag[0] != '0' && flag[0] != '1')) {
                error = L"в policy.xml испорчен write";
                return false;
            }
            subject.writeFlag = flag[0];
            rules[fileIndex].subjects.push_back(subject);
        }
    }
    return true;
}
```

Чтение устроено так же, как в драйвере: построчно, с проверкой начала строки. Отличие в том, что здесь используется `std::string` и `std::vector`, поэтому ограничения 32/8 не проверяются: если файл больше, драйвер откажется его принять, а `fsctl` вернёт ошибку и откатит изменения.

Если файла нет, возвращается пустой набор и успех. Это позволяет `set` создать первый файл правил.

## 12.3. Запись XML

```cpp
static bool SavePolicy(const std::vector<FileRule>& rules, std::wstring& error)
{
    std::ofstream out(kPolicyPathA, std::ios::binary | std::ios::trunc);
    if (!out) {
        error = L"не удалось записать policy.xml";
        return false;
    }
    out << "<?xml version=\"1.0\" encoding=\"utf-8\"?>\r\n<policy>\r\n";
    for (size_t i = 0; i < rules.size(); i++) {
        out << "  <file path=\"" << rules[i].path << "\">\r\n";
        for (size_t j = 0; j < rules[i].subjects.size(); j++) {
            const Subject& subject = rules[i].subjects[j];
            out << "    <subject name=\"" << subject.name
                << "\" read=\"" << subject.readFlag
                << "\" write=\"" << subject.writeFlag << "\"/>\r\n";
        }
        out << "  </file>\r\n";
    }
    out << "</policy>\r\n";
    return true;
}
```

Файл пишется в бинарном режиме, поэтому `\r\n` попадает на диск ровно как два байта, без дополнительной трансляции. Заголовок XML, отступы и закрывающие теги формируются здесь; драйвер их игнорирует, но файл остаётся обычным XML, который можно открыть в редакторе.

## 12.4. Команда set

```cpp
static int CommandSet(int argc, char** argv)
{
    std::vector<FileRule> rules;
    std::wstring error;
    std::string previous;
    HANDLE device;
    bool foundFile = false;
    size_t i;

    if (argc != 6 || !FlagOk(argv[4]) || !FlagOk(argv[5])) {
        Usage();
        return 1;
    }

    device = OpenDevice();
    if (device == INVALID_HANDLE_VALUE) {
        std::wcout << L"устройство не открылось\n";
        return 1;
    }
    CloseHandle(device);

    if (!LoadPolicy(rules, error)) {
        std::wcout << error << L"\n";
        return 1;
    }
    previous = ReadFileBytes();

    for (i = 0; i < rules.size(); i++) {
        size_t j;
        if (rules[i].path != argv[2])
            continue;
        foundFile = true;
        for (j = 0; j < rules[i].subjects.size(); j++) {
            if (rules[i].subjects[j].name == argv[3]) {
                rules[i].subjects[j].readFlag = argv[4][0];
                rules[i].subjects[j].writeFlag = argv[5][0];
                break;
            }
        }
        if (j == rules[i].subjects.size()) {
            Subject subject;
            subject.name = argv[3];
            subject.readFlag = argv[4][0];
            subject.writeFlag = argv[5][0];
            rules[i].subjects.push_back(subject);
        }
        break;
    }
    if (!foundFile) {
        FileRule rule;
        Subject subject;
        rule.path = argv[2];
        subject.name = argv[3];
        subject.readFlag = argv[4][0];
        subject.writeFlag = argv[5][0];
        rule.subjects.push_back(subject);
        rules.push_back(rule);
    }

    if (!SavePolicy(rules, error)) {
        std::wcout << error << L"\n";
        return 1;
    }
    if (!SendIoctl(IOCTL_FSFILTERX_RELOAD)) {
        if (!previous.empty())
            WriteFileBytes(previous);
        else
            DeleteFileA(kPolicyPathA);
        SendIoctl(IOCTL_FSFILTERX_RELOAD);
        std::wcout << L"правила на диске возвращены\n";
        return 1;
    }
    std::wcout << L"правила обновлены\n";
    return 0;
}
```

Порядок действий:

1. Проверяются количество аргументов и флаги (ровно `0` или `1`).
2. Открывается устройство. Если фильтр не загружен, команда завершается, не трогая файл.
3. Читается текущий XML. Ошибка разбора не даёт продолжить.
4. Сохраняется копия прежнего файла в памяти.
5. Ищется файл с указанным путём. Если найден — ищется субъект. Если субъект есть, флаги заменяются; если нет, добавляется новый. Если файла нет, добавляется новый файл с одним субъектом.
6. Файл записывается.
7. Отправляется IOCTL перечитывания. Если он не удался, файл восстанавливается из копии, отправляется ещё одно перечитывание, и программа сообщает, что правила на диске возвращены.

Восстановление важно потому, что драйвер и диск должны хранить одно и то же. Если бы программа оставила новый XML, а драйвер его не принял, следующий `reload` попытался бы применить правила, которые не разобрались, и поведение стало бы непредсказуемым.

Ограничения `set`:

- путь не должен содержать пробелов: аргументы разделяются пробелами;
- путь и имя процесса сравниваются с учётом регистра, а драйвер сравнивает без учёта. Если набрать путь в другом регистре, `fsctl` добавит вторую запись, а драйвер возьмёт первую;
- превышение лимитов 32/8 обнаруживается только драйвером, после чего срабатывает откат.

## 12.5. show, reload, notify

```cpp
static int CommandShow()
{
    std::ifstream in(kPolicyPathA, std::ios::binary);
    if (!in) {
        std::wcout << L"policy.xml не открылся\n";
        return 1;
    }
    std::cout << in.rdbuf();
    return 0;
}
```

`show` читает файл и печатает его как есть. Драйвер при этом не участвует, поэтому команда работает и при выгруженном фильтре. При перенаправлении вывода в файл надо учитывать, что `std::cout` в Windows работает в текстовом режиме и превращает `\n` в `\r\n`, поэтому уже имеющиеся `\r\n` могут дать `\r\r\n`. Для просмотра на экране это незаметно, для копирования файла — неудобно.

`reload` и `notify` — тонкие обёртки над `SendIoctl`, показанные в `main`.

# 13. Нотификатор и журнал

## 13.1. Что вызывает ядро

`PsSetLoadImageNotifyRoutine` регистрирует функцию, которую ядро вызывает при отображении образа в память. Колбэк получает:

- `PUNICODE_STRING fullImageName` — полный путь модуля в NT-форме;
- `HANDLE processId` — идентификатор процесса, который загружает модуль;
- `PIMAGE_INFO imageInfo` — сведения об образе.

Колбэк выполняется в контексте процесса, который загружает модуль, на `PASSIVE_LEVEL`. Это позволяет обращаться к файлам и выполнять `ZwWriteFile`. Если бы уровень был выше, запись в файл была бы недопустима.

Нотификатор не связан с фильтром: он не перехватывает IRP и не зависит от высоты. Поэтому его можно ставить и снимать отдельно, не выгружая фильтр.

## 13.2. Открытие журнала

```c
static NTSTATUS OpenLog(void)
{
    UNICODE_STRING name;
    OBJECT_ATTRIBUTES attrs;
    IO_STATUS_BLOCK io;
    NTSTATUS status;

    RtlInitUnicodeString(&name, LOG_NT_PATH);
    InitializeObjectAttributes(&attrs, &name, OBJ_CASE_INSENSITIVE | OBJ_KERNEL_HANDLE, NULL, NULL);
    status = ZwCreateFile(
        &gLogHandle,
        FILE_APPEND_DATA | SYNCHRONIZE,
        &attrs,
        &io,
        NULL,
        FILE_ATTRIBUTE_NORMAL,
        FILE_SHARE_READ,
        FILE_OPEN_IF,
        FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE,
        NULL,
        0);
    if (!NT_SUCCESS(status))
        gLogHandle = NULL;
    return status;
}
```

- `FILE_APPEND_DATA` — открыть на дописывание, не перезаписывая существующие строки.
- `SYNCHRONIZE` нужен для синхронного ввода-вывода.
- `FILE_SHARE_READ` разрешает другим процессам читать журнал, пока драйвер держит его открытым.
- `FILE_OPEN_IF` создаёт файл, если его нет.
- `FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE` — синхронная работа с обычным файлом.
- `OBJ_KERNEL_HANDLE` — описатель в системной таблице.

Если открыть журнал в колбэке каждый раз заново, то `ZwCreateFile` сам вызовет загрузку модулей и новый колбэк. Поэтому описатель открывается один раз при включении нотификатора, а в колбэке только пишется строка.

## 13.3. Формирование строки

```c
static void WriteLogLine(HANDLE processId, const WCHAR* exeName, const UNICODE_STRING* image)
{
    char line[1024];
    int used = 0;
    LARGE_INTEGER now;
    LARGE_INTEGER local;
    TIME_FIELDS fields;
    IO_STATUS_BLOCK io;

    KeQuerySystemTime(&now);
    ExSystemTimeToLocalTime(&now, &local);
    RtlTimeToTimeFields(&local, &fields);

    AppendNumber(line, &used, sizeof(line), fields.Year);
    AppendChar(line, &used, sizeof(line), '-');
    AppendTwoDigits(line, &used, sizeof(line), fields.Month);
    AppendChar(line, &used, sizeof(line), '-');
    AppendTwoDigits(line, &used, sizeof(line), fields.Day);
    AppendChar(line, &used, sizeof(line), ' ');
    AppendTwoDigits(line, &used, sizeof(line), fields.Hour);
    AppendChar(line, &used, sizeof(line), ':');
    AppendTwoDigits(line, &used, sizeof(line), fields.Minute);
    AppendChar(line, &used, sizeof(line), ':');
    AppendTwoDigits(line, &used, sizeof(line), fields.Second);
    AppendText(line, &used, sizeof(line), " pid=");
    AppendNumber(line, &used, sizeof(line), HandleToUlong(processId));
    AppendText(line, &used, sizeof(line), " process=");
    AppendWide(line, &used, sizeof(line), exeName, MAX_NAME);
    AppendText(line, &used, sizeof(line), " image=");
    if (image != NULL && image->Buffer != NULL)
        AppendWide(line, &used, sizeof(line), image->Buffer, image->Length / sizeof(WCHAR));
    else
        AppendText(line, &used, sizeof(line), "-");
    AppendText(line, &used, sizeof(line), "\r\n");

    KeEnterCriticalRegion();
    ExAcquireResourceExclusiveLite(&gLogLock, TRUE);
    if (gLogHandle != NULL)
        ZwWriteFile(gLogHandle, NULL, NULL, NULL, &io, line, (ULONG)used, NULL, NULL);
    ExReleaseResourceLite(&gLogLock);
    KeLeaveCriticalRegion();
}
```

`KeQuerySystemTime` даёт время в UTC, `ExSystemTimeToLocalTime` переводит в локальное, `RtlTimeToTimeFields` раскладывает на поля. Строка собирается вручную, без `sprintf`: в ядре форматирование строк ограничено, а свой набор функций предсказуем.

`AppendChar`, `AppendText`, `AppendNumber`, `AppendTwoDigits` и `AppendWide` — небольшие помощники, которые дописывают в буфер символы, числа и широкие строки. Они не используют `sprintf` и не зависят от формата: в ядре это удобнее и предсказуемее.

`AppendWide` заменяет символы вне диапазона 32–126 на `?`. Это значит, что кириллица в путях модулей в журнале не сохранится. Для путей с латиницей всё в порядке.

Запись защищена `gLogLock`, поэтому строки от разных процессоров не перемешиваются. `ZwWriteFile` с `FILE_APPEND_DATA` и `NULL`-смещением дописывает данные в конец.

Пример строки:

```text
2026-10-30 16:29:33 pid=9908 process=filetool.exe image=\Device\HarddiskVolume3\Users\winuser\Documents\mbks_labs\lab3\filetool\x64\Release\filetool.exe
```

В строке есть всё, что требует задание: время, PID, имя процесса и имя модуля.

## 13.4. Колбэк

```c
static VOID LoadImageNotify(PUNICODE_STRING fullImageName, HANDLE processId, PIMAGE_INFO imageInfo)
{
    PEPROCESS process = NULL;
    WCHAR exeName[MAX_NAME];

    UNREFERENCED_PARAMETER(imageInfo);
    if (InterlockedCompareExchange(&gInsideNotify, 1, 0) != 0)
        return;

    exeName[0] = 0;
    if (NT_SUCCESS(PsLookupProcessByProcessId(processId, &process))) {
        CopyShortName(process, exeName, MAX_NAME);
        ObDereferenceObject(process);
    }
    if (exeName[0] == 0)
        RtlCopyMemory(exeName, L"-", 2 * sizeof(WCHAR));
    WriteLogLine(processId, exeName, fullImageName);
    InterlockedExchange(&gInsideNotify, 0);
}
```

`gInsideNotify` — флаг повторного входа. Если запись в журнал сама вызовет загрузку образа, повторный вызов колбэка увидит флаг и выйдет, не создавая бесконечную рекурсию. Флаг снимается после записи.

`PsLookupProcessByProcessId` увеличивает счётчик ссылок на процесс; после `CopyShortName` вызывается `ObDereferenceObject`. Если процесс уже завершился, lookup не сработает, и в журнал попадёт `process=-`. Это нормальная ситуация для системных загрузок.

`CopyShortName` даёт короткое имя (до 14 символов). Для `filetool.exe` этого достаточно; для длинных имён имя обрезается.

## 13.5. Включение и выключение

```c
static NTSTATUS NotifyOn(void)
{
    NTSTATUS status;

    if (gNotifySet)
        return STATUS_SUCCESS;
    status = OpenLog();
    if (!NT_SUCCESS(status))
        return status;
    status = PsSetLoadImageNotifyRoutine(LoadImageNotify);
    if (!NT_SUCCESS(status)) {
        CloseLog();
        return status;
    }
    gNotifySet = 1;
    return STATUS_SUCCESS;
}

static NTSTATUS NotifyOff(void)
{
    LARGE_INTEGER pause;

    if (!gNotifySet)
        return STATUS_SUCCESS;
    PsRemoveLoadImageNotifyRoutine(LoadImageNotify);
    gNotifySet = 0;
    /* Колбэк, который уже вошёл, дописывает строку и сам отпускает флаг. */
    pause.QuadPart = -10 * 1000 * 10;
    while (gInsideNotify)
        KeDelayExecutionThread(KernelMode, FALSE, &pause);
    CloseLog();
    return STATUS_SUCCESS;
}
```

Повторное включение и выключение безопасны: если нотификатор уже включён, `NotifyOn` возвращает успех; если уже выключен, `NotifyOff` возвращает успех. Это важно, потому что `FilterUnload` вызывает `NotifyOff` независимо от того, включал ли кто-то нотификатор.

`-10 * 1000 * 10` — относительная задержка в единицах по 100 нс, то есть 10 мс. Снятие блокирует новые вызовы, а ожидание флага гарантирует, что уже начатый вызов успеет дописать строку до закрытия журнала; проверка не лишняя.

Состояние нотификатора:

```text
        notify on                 notify off
OFF ----------------> ON -------------------> OFF
 ^                     |                       ^
 |                     | fltmc unload          |
 +---------------------+-----------------------+
        FilterUnload -> NotifyOff
```

После выгрузки драйвера состояние не сохраняется: новый `fltmc load` начинает с выключенного нотификатора.

## 13.6. Почему журнал не защищён

`AccessAllowed` возвращает 1 для `image.log` независимо от процесса. Это сделано по двум причинам:

1. Драйвер сам пишет журнал, и проверка его собственных записей не нужна.
2. Журнал нужно читать при проверке, в том числе пока нотификатор включён. Если бы журнал был закрыт, проверка усложнилась бы.

Обратная сторона: любой процесс может дописать в журнал мусор или удалить его. Для учебной задачи это приемлемо; в реальной системе журнал стоило бы защищать отдельно.

# 14. Сквозные сценарии

## 14.1. Загрузка фильтра

1. `fltmc load FsFilterX` передаёт управление `DriverEntry`.
2. Создаются `gRuleLock` и `gLogLock`.
3. `FltRegisterFilter` регистрирует минифильтр; `gFilter` становится валидным.
4. `CreateControlDevice` создаёт `\Device\FsFilterX` и `\DosDevices\FsFilterX`.
5. `ReloadPolicy` читает `policy.xml`, разбирает его и публикует правила.
6. `FltStartFiltering` включает перехват.
7. Если файла правил нет, политика пустая; `policy.xml` всё равно защищён.

## 14.2. Чтение note.txt

1. `filetool r C:\DriverConfig\data\note.txt` вызывает `CreateFile`.
2. `PreCreate` получает путь `C:\DriverConfig\data\note.txt` и процесс `filetool.exe`.
3. `DesiredAccess` содержит `GENERIC_READ`; `wantsWrite` ложно, `wantsRead` истинно.
4. `AccessAllowed` находит файл в правилах и субъекта `filetool.exe` с `read=1`.
5. Открытие разрешено.
6. `ReadFile` идёт через `PreRead`; проверка повторяется и тоже разрешает.
7. `filetool` печатает `hello`.

## 14.3. Запись note.txt

1. `filetool w C:\DriverConfig\data\note.txt hacked` вызывает `CreateFile` с `GENERIC_WRITE` и `CREATE_ALWAYS`.
2. `PreCreate` видит `wantsWrite = true`: и по битам доступа, и по disposition.
3. `AccessAllowed` находит субъекта с `write=0`.
4. `Deny` возвращает `STATUS_ACCESS_DENIED` с `FLT_PREOP_COMPLETE`.
5. Файл не открывается, усечение не происходит.
6. `filetool` печатает `file openning failed`.
7. Повторное чтение показывает `hello`.

## 14.4. fsctl set

1. `fsctl set ... 1 1` открывает `\\.\FsFilterX` и проверяет, что фильтр загружен.
2. `LoadPolicy` читает XML в память.
3. Находится пара `note.txt` + `filetool.exe`, флаги заменяются на `1` и `1`.
4. `SavePolicy` пишет файл.
5. `SendIoctl(0x800)` вызывает `DispatchIoctl`.
6. `DispatchIoctl` проверяет имя процесса, вызывает `ReloadPolicy`.
7. `ReloadPolicy` читает файл, разбирает и публикует правила.
8. Следующая запись `filetool` проходит без перезагрузки.
9. Обратный `set ... 1 0` возвращает запрет.

## 14.5. Нотификатор

1. `fsctl notify on` открывает устройство и посылает `0x801`.
2. `NotifyOn` открывает `image.log` и ставит `PsSetLoadImageNotifyRoutine`.
3. Запуск `filetool` загружает `filetool.exe` и его DLL.
4. Каждая загрузка вызывает `LoadImageNotify`, который дописывает строку.
5. `fsctl notify off` посылает `0x802`.
6. `NotifyOff` снимает колбэк, ждёт завершения и закрывает журнал.
7. Новые запуски программ строк не добавляют.
8. `fltmc unload FsFilterX` при включённом нотификаторе вызывает `FilterUnload`, который сам снимает нотификатор.

## 14.6. Программа filetool

```cpp
static void read_file(const char* file_name)
{
    std::ifstream in(file_name);
    if (!in.is_open()) {
        std::cout << "file openning failed\n";
        return;
    }
    std::string line;
    while (std::getline(in, line))
        std::cout << line << '\n';
}

static void write_file(const char* file_name, const char* text)
{
    std::ofstream out(file_name);
    if (!out.is_open()) {
        std::cout << "file openning failed\n";
        return;
    }
    out << text << '\n';
}
```

`read_file` открывает файл на чтение и печатает строки. `write_file` открывает через `std::ofstream`, то есть с созданием и усечением, и пишет одну строку. Оба сообщения об ошибке одинаковые — `file openning failed`; опечатка сохранена, чтобы поведение совпадало с прежней проверкой.

## 14.7. Выгрузка

1. `fltmc unload FsFilterX` вызывает `FilterUnload`.
2. `NotifyOff` снимает нотификатор, если он был включён.
3. `DeleteControlDevice` удаляет ссылку и устройство.
4. `FltUnregisterFilter` снимает фильтр с томов.
5. Удаляются блокировки.
6. Служба остаётся в реестре; следующая загрузка — снова `fltmc load`.

# 15. Сборка, проверка, диагностика

## 15.1. Порядок прогона

`install-filter.ps1` выполняет шаги в таком порядке:

1. Проверяет права администратора.
2. Проверяет `testsigning Yes` через `bcdedit`.
3. Подписывает драйвер.
4. Выгружает ранее загруженный фильтр.
5. Готовит `policy.xml`, `note.txt`, `report.txt`, `free.txt`, удаляет `image.log`.
6. Копирует sys в `System32\drivers`.
7. Проверяет подпись.
8. Создаёт службу и параметры экземпляра.
9. Загружает фильтр и проверяет `fltmc filters`.
10. Прогоняет проверки и пишет результат в `install-result.txt`.
11. Выгружает и снова загружает фильтр при включённом нотификаторе.

Ключевой фрагмент — подготовка файлов после выгрузки:

```powershell
$existing = Get-Service FsFilterX -ErrorAction SilentlyContinue
if ($existing) {
    $unload = cmd /c "fltmc unload FsFilterX" 2>&1 | Out-String
    Log "UNLOAD:"
    Log $unload
    Start-Sleep -Seconds 1
}

New-Item -ItemType Directory -Force -Path 'C:\DriverConfig\data' | Out-Null
Copy-Item (Join-Path $root 'config\policy.xml') $policy -Force
Copy-Item (Join-Path $root 'config\data\note.txt') $note -Force
Set-Content -Path $report -Value "before" -Encoding ascii
Set-Content -Path $free -Value "free-before" -Encoding ascii
if (Test-Path $imageLog) { Remove-Item $imageLog -Force }
```

Если не выгрузить фильтр, `powershell.exe` не сможет перезаписать `note.txt` и `policy.xml`: он не `fsctl.exe`, а значит, правила его не пустят. Это была одна из ошибок первого прогона.

## 15.2. Проверки

| № | Что проверяется | Команда | Ожидание |
|---|---|---|---|
| 1 | Файл правил | `notepad C:\DriverConfig\policy.xml` до загрузки | В файле две записи `file` |
| 2 | Тестовый режим и сборка | `winver`, `bcdedit /enum {current}` | Test Mode, сборка 28000, `testsigning Yes` |
| 3 | Загруженный фильтр | `fltmc filters` | `FsFilterX`, высота 370030 |
| 4 | Подпись | `signtool verify /pa ...` | `sha256`, `Successfully verified` |
| 5 | Чтение и запись note.txt | `filetool r/w note.txt` | `hello`, `file openning failed`, `hello` |
| 6 | report.txt и free.txt | `filetool w/r` | `written`, `free-ok` |
| 7 | Копия notepad.exe | `filetool r/w` | `file openning failed`, затем `hello` |
| 8 | fsctl set | `fsctl set ... 1 1`, запись, `set ... 1 0`, запись | `allowed-now`, затем отказ |
| 9 | Защита policy.xml | `filetool r policy.xml`, `fsctl show` | Отказ, затем XML |
| 10 | Нотификатор и журнал | `fsctl notify on`, `filetool r`, `type image.log` | Строки с `process=filetool.exe` |
| 11 | Снятие нотификатора | `fsctl notify off`, `filetool r`, `dir` дважды | Размер не меняется |
| 12 | Выгрузка с нотификатором | `fsctl notify on`, `fltmc unload/load`, `filetool r` | Загрузка проходит, `allowed-now` |

Последний полный прогон завершился с `FAILED 0`: все проверки прошли.

## 15.3. Диагностика

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `fltmc load` возвращает `Access is denied` | Командная строка без прав администратора | Открыть от имени администратора |
| `fsctl` пишет `устройство не открылось` | Фильтр не загружен | `fltmc load FsFilterX` |
| `file openning failed` вместо `hello` | `note.txt` не содержит `hello` или политика другая | Выгрузить фильтр, положить файл заново, загрузить |
| `policy.xml` не открывается в блокноте | Фильтр загружен, файл защищён | Выгрузить фильтр, открыть, загрузить снова |
| `ReadAllText` не читает `image.log` | Драйвер держит файл с `FILE_SHARE_READ`, .NET не ставит `FILE_SHARE_WRITE` | Читать с `FileShare.ReadWrite` или через блокнот |
| `IOCTL не выполнен` при `set` | Драйвер не принял XML: ошибка разбора, лимиты или размер | Посмотреть `policy.xml`, проверить лимиты; `set` сам откатит файл |
| `fsctl notify on` возвращает ошибку | Не удалось открыть журнал или поставить нотификатор | Проверить права на `C:\DriverConfig`, посмотреть код ошибки |
| Журнал пустой | Нотификатор не включён или не было загрузок после включения | Включить, запустить программу, проверить `image.log` |
| После выгрузки система падает | Нотификатор не снят | Проверить, что `NotifyOff` вызывается в `FilterUnload` |
| `STATUS_DEVICE_BUSY` при reload | Уже идёт перечитывание | Повторить команду позже |

## 15.4. Журнал прогона

`install-result.txt` содержит:

- дату и время запуска;
- вывод `bcdedit` и признак `testsigning`;
- результат подписи и `signtool verify`;
- `fltmc filters`;
- вывод каждой проверки с командой и результатом;
- итоговую строку `FAILED N` и `done`.

Если `FAILED 0`, все проверки прошли. Если больше нуля, в журнале видно, какая именно проверка упала и что напечатала программа.

# 16. Ограничения модели и направления развития

## 16.1. Ограничения

| Ограничение | Причина | Следствие | Что можно сделать |
|---|---|---|---|
| Субъект — имя exe | Так устроен прежний драйвер, проще проверка | Копия программы под другим именем получает другие права | Проверять SID учётной записи через токен |
| `policy.xml` защищён по имени `fsctl.exe` | Нет проверки подписи и учётной записи | Копия любой программы под именем `fsctl.exe` откроет правила | Проверять подпись или SID |
| Удаление и переименование не перехватываются | Нет обработчика `IRP_MJ_SET_INFORMATION` | Правила не мешают удалить файл | Добавить обработчик и проверку `DELETE` |
| Только чтение и запись | В задании достаточно | Нет отдельных прав на выполнение, удаление, смену атрибутов | Расширить набор флагов |
| Только диск `C:` | Приведение пути упрощено | Файл на другом томе с тем же относительным путём может быть проверен неверно | Разбирать букву тома из `FltObjects->Volume` |
| Относительные открытия пропускаются | `RelatedFileObject` не разбирается | Возможен обход проверки на открытии | Использовать `FltGetFileNameInformation` и для `CREATE` |
| Только латиница | Разбор отвергает байты старше 127 | Кириллические пути не работают | Перейти на UTF-8 и широкие строки в разборе |
| Буфер 8 КБ | Фиксированный размер | Большая политика отвергается | Выделять буфер по размеру файла |
| Журнал не защищён | Упрощение | Любой процесс может дописать или удалить журнал | Защищать отдельной ветвью |
| `fsctl set` сравнивает с учётом регистра | `std::string` сравнивает точно | Правило с другим регистром не подействует | Сравнивать без учёта регистра |
| `fsctl show` в текстовом режиме | `std::cout` | При перенаправлении возможны `\r\r\n` | Открыть `stdout` в бинарном режиме |

## 16.2. Что можно добавить

- Проверку SID и токена доступа вместо имени exe.
- Обработчик `IRP_MJ_SET_INFORMATION` для удаления и переименования.
- Права `FILE_EXECUTE`, `DELETE`, `WRITE_DAC`.
- Формат JSON или хранение в реестре как альтернативу XML.
- Проверку подписи исполняемых файлов и хешей.
- Защиту журнала и его ротацию.
- Разбор относительных путей и нескольких томов.
- Автотесты, которые поднимают фильтр в виртуальной машине и прогоняют сценарии.
- Метрики и ETW вместо текстового журнала.

## Приложение E. Глоссарий

| Термин | Значение |
|---|---|
| IRP | Пакет запроса ввода-вывода, единица работы диспетчера ввода-вывода |
| Минифильтр | Драйвер, регистрирующийся у `FltMgr` и наблюдающий операции файловой системы |
| Высота (altitude) | Число, задающее порядок вызова фильтров |
| DACL | Список управления доступом, перечень разрешений для субъектов |
| IOCTL | Управляющий запрос к драйверу через `DeviceIoControl` |
| Нотификатор | Функция ядра, вызываемая при событии |
| Paging I/O | Операции подкачки, которые фильтр пропускает |
| Нормализованное имя | Полный путь, который возвращает `FltGetFileNameInformation` |
| Метод `METHOD_BUFFERED` | Способ передачи буфера через системную копию |
