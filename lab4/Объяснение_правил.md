# Как устроены три собственных правила

Файл для устного объяснения. Правила лежат здесь:

- CodeQL: `rules/codeql/msadpcm-block-size.ql`, идентификатор `cpp/lab4-msadpcm-block-size`
- semgrep: `rules/semgrep/msadpcm-block-size.yaml`, идентификатор `lab4-msadpcm-block-size`
- joern: `rules/joern/msadpcm-block-size.sc`

Одно и то же место в коде описано тремя языками. Имя функции, имя поля и литерал `7` в правилах не заданы.

## Коротко, что сказать

В `wavlike_msadpcm_init` размер буфера собирается из двух величин из заголовка WAV. `blockalign` входит в размер слагаемым, `samplesperblock` — множителем. В libsndfile 1.0.30 с произведением сравнивается слагаемое:

```c
if (blockalign < 7 * psf->sf.channels)
    ...
pmssize = sizeof (MSADPCM_PRIVATE) + blockalign + 3 * psf->sf.channels * samplesperblock;
calloc (1, pmssize);
```

Проверка гарантирует место под преамбулу блока. Число сэмплов, под которое выделяется буфер и которые потом пишет декодер, эта проверка не ограничивает. В 1.1.0 нижняя граница перенесена на множитель `samplesperblock`, а проверка `blockalign` записана как `2 * blockalign < ...`. Слева больше нет голой переменной-слагаемого.

Правило ищет именно эту форму: в одной функции есть `malloc` или `calloc`, в размере есть слагаемое `B` и множитель `S`, при этом `B` сравнивается с произведением, а `S` так не сравнивается. На 1.0.30 все три инструмента дают одну находку, `src/ms_adpcm.c:131`. На 1.1.0 — ноль. На коротком примере с другими именами и с множителем 8 — две находки, в исправленной функции примера — ноль.

Правило узнаёт форму проверки. Выход за границу буфера показывает отдельный PoC под AddressSanitizer.

## Какая ошибка за этой формой

CVE-2021-3246, CWE-787, запись за границу кучи в декодере MS ADPCM.

В режиме чтения `wavlike_msadpcm_init` берёт из заголовка `blockalign` и `samplesperblock`. Для обычного MS ADPCM число каналов ограничено диапазоном 1…2. Для `WAVE_FORMAT_EXTENSIBLE` эта ветка не выполняется. Кроме того, в объединении `WAV_FMT` поле `msadpcm.samplesperblock` лежит на том же месте, что `ext.validbits`. Для extensible-файла чтение `samplesperblock` фактически читает `wValidBitsPerSample`.

Дальше функция считает размер и выделяет буфер. Код 1.0.30, строки 131–138:

```c
if (blockalign < 7 * psf->sf.channels)
{   psf_log_printf (psf, "*** Error blockalign (%d) should be > %d.\n",
                    blockalign, 7 * psf->sf.channels) ;
    return SFE_INTERNAL ;
    } ;

pmssize = sizeof (MSADPCM_PRIVATE) + blockalign + 3 * psf->sf.channels * samplesperblock ;

if (! (psf->codec_data = calloc (1, pmssize)))
    return SFE_MALLOC_FAILED ;
```

Семёрка здесь — размер преамбулы MS ADPCM: семь байт на канал в начале блока. Проверка отвечает на вопрос «влезает ли преамбула в блок». На вопрос «хватит ли буфера на заявленное число сэмплов» она не отвечает.

Декодер пишет в массив `samples`, который указывает внутрь этого буфера. Цикл идёт по байтам блока и кладёт по два отсчёта на байт. Старт индекса — `2 * channels`. При каналах 226, `blockalign` 2592 и `samplesperblock` 10 старые проверки файла проходят, а запись выходит за выделенные 9428 байт. ASan показывает это в `msadpcm_decode_block`, строка 279. Сама слабая проверка — в инициализации, строка 131. Инициализация в конце вызывает декодер, поэтому в стеке видны обе функции.

Исправление в 1.1.0, строки 132–140, меняет форму проверок и оставляет формулу размера прежней:

```c
if (samplesperblock < 7 * psf->sf.channels)
{   psf_log_printf (psf, "*** Error samplesperblock (%d) should be >= %d.\n",
                    samplesperblock, 7 * psf->sf.channels) ;
    return SFE_INTERNAL ;
    } ;

if (2 * blockalign < samplesperblock * psf->sf.channels)
{   psf_log_printf (psf, "*** Error blockalign (%d) should be >= %d.\n",
                    blockalign, samplesperblock * psf->sf.channels / 2) ;
    return SFE_INTERNAL ;
    } ;
```

Первая проверка ограничивает множитель размера. Для PoC `10 < 7 * 226`, файл отклоняется до `calloc`. Вторая проверка связывает размер блока с числом сэмплов, и слева стоит выражение `2 * blockalign`, а не переменная `blockalign`.

Цикл распаковки в 1.1.0 тот же. Правило только про цикл нашло бы обе версии. Поэтому правило смотрит на проверку перед выделением, а не на цикл записи.

Штатные запросы это место не выделяют. CodeQL `cpp/unbounded-write` (CWE-120) ищет запись без явной длины, а здесь длина есть, просто она посчитана из несогласованных полей. `joern-scan` помечает цикл копирования в декодере и не отличает 1.0.30 от 1.1.0. Отсюда отдельное правило на форму слабой проверки.

## Общая форма, которую ищут все три

В одной функции одновременно:

1. Есть `if (B < произведение)`. Слева — переменная, без коэффициента. Справа — умножение. Число в произведении любое.
2. В той же функции есть `malloc` или `calloc`. Если в аллокатор передана переменная, берётся правая часть одного присваивания этой переменной. В libsndfile это `pmssize`.
3. `B` входит в это выражение размера слагаемым.
4. Другая переменная `S` входит в то же выражение множителем.
5. `S` не стоит в правой части этой же проверки и сама не сравнивается с произведением таким же `if`.

На 1.0.30 получается `B = blockalign`, `S = samplesperblock`.

На 1.1.0 сравнение с произведением, у которого слева голая переменная, стоит на `samplesperblock`. Эта переменная — множитель размера, а не слагаемое. Условие «слева слагаемое» ложно, правило молчит.

Три инструмента выражают одну форму по-разному, потому что у них разный разбор программы:

| Инструмент | На чём написано правило | Что видит движок |
|---|---|---|
| CodeQL | предикаты QL | дерево разбора после сборки базы, с типами и привязкой к переменным |
| semgrep | шаблон с метапеременными | дерево разбора исходного текста, без компиляции |
| joern | обход графа на Scala | CPG: узлы AST, вызовы и операторы как рёбра графа |

Скобки вокруг условия для CodeQL снимаются отдельно. Для semgrep записаны две формы `if`: с фигурными скобками и без, потому что шаблон смотрит на текст оператора. joern скобки и фигурные скобки не различает: он смотрит детей узла условия.

## CodeQL

Запрос объявлен как проблема безопасности, CWE-787 и CWE-122, тяжесть 8.8. Это метки отчёта. На логику отбора они не влияют.

### Снятие скобок

```ql
Expr unwrap(Expr e) {
  e instanceof ParenthesisExpr and result = unwrap(e.(ParenthesisExpr).getExpr())
  or
  not (e instanceof ParenthesisExpr) and result = e
}
```

`ParenthesisExpr` — узел скобок в дереве. Функция спускается, пока скобки не кончатся. Условие `(blockalign) < (7 * channels)` после `unwrap` выглядит так же, как без скобок. Дальше сравнение ищется уже по оператору и по видам узлов, а не по тексту.

### Аргумент размера у malloc и calloc

```ql
predicate isAllocator(FunctionCall call) {
  call.getTarget().hasName("malloc") or
  call.getTarget().hasName("calloc")
}

Expr allocatorSizeArg(FunctionCall call) {
  isAllocator(call) and
  (
    call.getTarget().hasName("malloc") and result = call.getArgument(0)
    or
    call.getTarget().hasName("calloc") and result = call.getArgument(1)
  )
}
```

У `malloc` размер — первый аргумент. У `calloc(n, size)` размер одного элемента — второй, в libsndfile это `calloc(1, pmssize)`. Первый аргумент `calloc` — число элементов, его брать нельзя: там константа `1`, и формула размера к ней не привязана.

`getTarget().hasName(...)` смотрит имя вызываемой функции после разбора, поэтому пробелы и переносы строки в вызове не мешают.

### Одно присваивание до аллокатора

```ql
Expr resolvedSize(Function f, Expr arg) {
  arg.getEnclosingFunction() = f and
  (
    result = arg
    or
    exists(Variable v, AssignExpr assign |
      arg.(VariableAccess).getTarget() = v and
      assign.getEnclosingFunction() = f and
      assign.getLValue().(VariableAccess).getTarget() = v and
      result = assign.getRValue()
    )
  )
}
```

Если в `calloc` написана сама формула, берётся она. Если написана переменная, ищутся присваивания этой переменной в той же функции, и берётся правая часть. Для libsndfile цепочка такая:

```c
pmssize = sizeof (MSADPCM_PRIVATE) + blockalign + 3 * psf->sf.channels * samplesperblock;
calloc (1, pmssize);
```

`arg` — доступ к `pmssize`. Правая часть присваивания — сумма, в которой уже видны `blockalign` и `samplesperblock`.

Берётся ровно один шаг. Цепочка `a = формула; b = a; calloc(1, b)` не раскрывается. В этой функции шаг один, его хватает.

### Слагаемое и множитель

```ql
predicate mentions(Expr e, Variable v) { e.getAChild*() = v.getAnAccess() }

predicate isAddend(Expr size, Variable v) {
  exists(AddExpr add |
    add = size.getAChild*() and
    add.getAnOperand() = v.getAnAccess()
  )
}

predicate isFactor(Expr size, Variable v) {
  exists(MulExpr mul |
    mul = size.getAChild*() and
    mul.getAnOperand() = v.getAnAccess()
  )
}
```

`getAChild*()` — сам узел и любой вложенный узел. `isAddend` истинен, если где-то в размере есть сложение и его операнд — эта переменная. `isFactor` — то же для умножения.

В формуле

```c
sizeof (MSADPCM_PRIVATE) + blockalign + 3 * psf->sf.channels * samplesperblock
```

`blockalign` — операнд сложения. `samplesperblock` — операнд умножения. `psf->sf.channels` тоже сидит внутри умножения, но это обращение к полю, и ниже оно отсекается отдельно: эта же переменная упомянута справа в проверяемом `if`.

`mentions` нужен, чтобы не принять за свободный множитель переменную, которая уже стоит в правой части проверки. Справа в уязвимом коде написано `7 * psf->sf.channels`. Каналы в проверке участвуют. Непроверенным множителем остаётся `samplesperblock`: в размере он есть, в правой части этого `if` его нет.

### Слабое сравнение

```ql
predicate weakProductCheck(IfStmt check, Variable blockVar) {
  exists(BinaryOperation cmp |
    cmp = unwrap(check.getCondition()) and
    cmp.getOperator() = "<" and
    blockVar = unwrap(cmp.getLeftOperand()).(VariableAccess).getTarget() and
    unwrap(cmp.getRightOperand()) instanceof MulExpr
  )
}
```

Четыре требования к `if`:

- условие после снятия скобок — одно сравнение;
- оператор именно `<`;
- слева после снятия скобок — обращение к переменной, и эта переменная связывается с `blockVar`;
- справа — узел умножения.

`(VariableAccess).getTarget()` даёт объявление переменной, а не текст. Поэтому `blockalign` в параметре функции и `blockalign` в условии — одна и та же переменная, даже если бы имена в тексте разошлись из-за макроса.

Запись `2 * blockalign < ...` слева имеет умножение, а не переменную. Предикат для неё ложен. Запись `samplesperblock < 7 * channels` предикат принимает, но дальше запрос потребует, чтобы эта переменная была слагаемым размера. В формуле она множитель, и строка отпадает.

### Сборка запроса

```ql
from Function f, IfStmt check, Variable blockVar, Variable sampleVar, Expr size
where
  f = check.getEnclosingFunction() and
  weakProductCheck(check, blockVar) and
  exists(FunctionCall alloc, Expr arg |
    alloc.getEnclosingFunction() = f and
    arg = allocatorSizeArg(alloc) and
    size = resolvedSize(f, arg)
  ) and
  isAddend(size, blockVar) and
  isFactor(size, sampleVar) and
  sampleVar != blockVar and
  not mentions(unwrap(check.getCondition()).(BinaryOperation).getRightOperand(), sampleVar) and
  not exists(IfStmt other |
    other.getEnclosingFunction() = f and
    other != check and
    weakProductCheck(other, sampleVar)
  )
select check,
  "Слагаемое размера сравнивается с произведением, а другой множитель того же malloc/calloc так не ограничен"
```

Порядок смыслов такой.

1. `check` и аллокатор лежат в одной функции `f`. Имя функции не указано.
2. `check` — слабое сравнение, слева переменная `blockVar`.
3. В функции есть `malloc` или `calloc`, и для его аргумента размера получено выражение `size`.
4. `blockVar` — слагаемое этого выражения.
5. `sampleVar` — другой множитель того же выражения.
6. `sampleVar` не встречается справа в найденном сравнении.
7. В функции нет другого `if`, который так же сравнивает уже `sampleVar` с произведением.

Пункт 7 отличает уязвимую функцию от исправленной, если бы слагаемое всё ещё сравнивалось по-старому, но рядом появилась проверка множителя. В 1.1.0 срабатывание гасится раньше: единственное сравнение «переменная `<` произведение» стоит на множителе, и `isAddend` для него ложен.

`select` отдаёт узел `if`. Поэтому в результате строка 131, а не строка `calloc`.

На 1.0.30 запрос находит один такой `if`. На 1.1.0 ноль. База CodeQL при повторном запуске хранит старый текст предупреждения, поэтому после правки запроса анализ гоняется с `--rerun`.

## semgrep

semgrep не строит базу и не знает про объявления переменных. Метапеременная `$BLOCK` — это кусок дерева разбора. Одинаковое имя метапеременной в разных частях правила означает один и тот же кусок. Этим `$BLOCK` слева в `if` связывается с `$BLOCK` в сумме размера.

Правило — набор условий, которые должны выполниться вместе. `pattern-either` — достаточно одной ветки. `pattern-not-inside` — если код сидит внутри отвергаемого шаблона, находка снимается.

### Сам if

```yaml
- pattern-either:
    - pattern: |
        if ($BLOCK < $SCALE * $CH) { ... }
    - pattern: |
        if ($BLOCK < $SCALE * $CH)
          $STMT;
```

Две ветки покрывают `if` с телом в скобках и `if` с одним оператором. В libsndfile тело в скобках, в фикстуре встречаются оба вида. `{ ... }` и `$STMT` — тело, его содержимое правилу безразлично.

`$SCALE * $CH` — одно умножение двух подвыражений. Семёрка сюда попадает как значение `$SCALE`, но шаблон принимает и `8`, и другое выражение. `$BLOCK` слева обязан быть тем же деревом, которое потом встретится слагаемым в размере.

### Формула размера

```yaml
- pattern-inside: |
    $RET $FN(...) {
      ...
      $SZ = $HEAD + $BLOCK + $K * $MID * $COUNT;
      ...
    }
```

Шаблон требует присваивание внутри какой-то функции. `$FN` — любое имя. Строка размера читается так:

- `$HEAD` — первое слагаемое, в библиотеке это `sizeof (MSADPCM_PRIVATE)`;
- `$BLOCK` — то же выражение, что слева в `if`;
- `$K * $MID * $COUNT` — произведение из трёх множителей.

Для реальной строки `3` связывается с `$K`, `psf->sf.channels` с `$MID`, `samplesperblock` с `$COUNT`.

Это место у semgrep жёстче, чем у CodeQL и joern. Те ищут «где-то есть сложение с этой переменной» и «где-то есть умножение на другую». semgrep хочет конкретный вид суммы: голова, затем `$BLOCK`, затем произведение трёх множителей. Формула в libsndfile и в фикстуре так и написана. Если слагаемые переставить, шаблон semgrep разойдётся, а предикаты CodeQL ещё могут сойтись.

### Вызов аллокатора

Дальше `pattern-either` из шести вариантов. Все требуют, чтобы та же `$SZ` попала в `malloc` или `calloc`. Вариант, который совпадает с libsndfile и с фикстурой:

```yaml
- pattern-inside: |
    $RET $FN(...) {
      ...
      if (! ($DEST = calloc($N, $SZ)))
        $S;
      ...
    }
```

Остальные ветки закрывают голый вызов, присваивание без `if` и такой же набор для `malloc`. У `calloc` размер стоит вторым аргументом, у `malloc` — первым. Это записано формой шаблона, отдельного предиката тут нет.

### Множитель не должен быть проверен так же

```yaml
- pattern-not-inside: |
    $RET $FN(...) {
      ...
      if ($COUNT < $SCALE2 * $X) { ... }
      ...
    }
- pattern-not-inside: |
    $RET $FN(...) {
      ...
      if ($COUNT < $SCALE2 * $X)
        $S2;
      ...
    }
```

`$COUNT` — последний множитель формулы размера, то есть `samplesperblock` в библиотеке и `nframes` в фикстуре. Если в той же функции есть `if (этот множитель < произведение)`, находка снимается. `$SCALE2` и `$X` — новые метапеременные, произведение справа может быть другим.

В 1.0.30 такого `if` для `samplesperblock` нет, отрицательный шаблон не срабатывает, находка остаётся.

В 1.1.0 положительный шаблон тоже не собирается. Слева в сравнении с произведением стоит `samplesperblock`, а в сумме на месте `$BLOCK` стоит `blockalign`. Одна метапеременная на два разных выражения не садится. Вторая проверка `2 * blockalign < ...` слева содержит умножение, а шаблон ждёт `$BLOCK` без коэффициента. Отрицательный шаблон здесь дополнительный: даже при другой записи суммы проверка `samplesperblock < 7 * channels` погасила бы находку, потому что `$COUNT` уже сравнён с произведением.

Сообщение правила прямо говорит, что литерал 7 не требуется и что для MS ADPCM так выглядит слабая проверка преамбулы. Ссылки в `metadata` ведут на NVD и на issue 687 libsndfile.

## joern

Скрипт — программа на Scala. Она сама вызывает фронтенд:

```scala
@main def main(inputPath: String, outFile: String) = {
  importCode.c(inputPath)
  ...
}
```

`importCode.c` строит граф свойств кода (CPG). Операторы в этом графе — узлы-вызовы с именами вида `<operator>.addition`, `<operator>.multiplication`, `<operator>.assignment`. Имя такого узла достаёт функция `op`. Обход идёт по детям AST, а не по тексту строки.

Имени метода в фильтре нет. Скрипт берёт каждый `if` в графе.

### Дети условия

```scala
def weakCheck(cond: AstNode): Option[(String, Set[String])] = {
  val kids = cond.astChildren.l
  if (kids.length < 2) None
  else
    kids.head match {
      case left: Identifier if op(kids(1)) == "<operator>.multiplication" =>
        Some((left.code, idents(kids(1))))
      case _ => None
    }
}
```

У узла условия берутся дети. Первый ребёнок должен быть идентификатором. Второй — вызовом-умножением. Из идентификатора берётся его текст, из правого поддерева — множество всех идентификаторов внутри.

Для строки `blockalign < 7 * psf->sf.channels` результат — имя `blockalign` и идентификаторы правой части. Литерал `7` идентификатором не является и в множество не попадает.

Отличие от CodeQL: имя оператора сравнения (`<`, `>`, `<=`) скрипт не проверяет. Он проверяет форму детей. В libsndfile и в фикстуре оператор — `<`, потому что так записан код. Фильтр держится на «слева идентификатор, справа умножение».

`2 * blockalign < ...` первым ребёнком имеет умножение, ветка `Identifier` не берётся.

### Слагаемые и множители размера

```scala
def operands(n: AstNode): (Set[String], Set[String]) = {
  val own = op(n) match {
    case "<operator>.addition" =>
      (n.astChildren.collect { case i: Identifier => i.code }.toSet, Set.empty[String])
    case "<operator>.multiplication" =>
      (Set.empty[String], n.astChildren.collect { case i: Identifier => i.code }.toSet)
    case _ =>
      (Set.empty[String], Set.empty[String])
  }
  n.astChildren.foldLeft(own) { case ((add, mul), child) =>
    val (a2, m2) = operands(child)
    (add ++ a2, mul ++ m2)
  }
}
```

Функция обходит выражение и собирает два множества имён. В первое попадают идентификаторы, которые являются непосредственными детьми сложения. Во второе — непосредственные дети умножения. Вложенные операторы обходятся рекурсией, поэтому множитель внутри `3 * channels * samplesperblock` находится, даже если умножения в дереве вложены.

Поле `psf->sf.channels` — не идентификатор-операнд умножения целиком. Идентификатором среди операндов произведения в формуле размера оказывается `samplesperblock`. `blockalign` оказывается операндом сложения.

### Аргумент аллокатора и одно присваивание

```scala
def allocArgCodes(method: Method): List[String] =
  method.call
    .name("(malloc|calloc)")
    .flatMap { call =>
      call.argument.l.collect {
        case arg if arg.code != call.code => arg.code
      }
    }
    .l

def sizeExprs(method: Method, argCode: String): List[AstNode] = {
  val assigned = method.call.nameExact("<operator>.assignment").flatMap { assign =>
    val kids = assign.astChildren.l
    if (kids.length >= 2 && kids.head.code == argCode) List(kids(1)) else Nil
  }.l
  val direct = method.call.name("(malloc|calloc)").flatMap { call =>
    call.argument.l.collect {
      case arg if arg.code == argCode => arg
    }
  }.l
  (assigned ++ direct).distinct
}
```

Сначала собираются тексты аргументов `malloc` и `calloc`. Узел, чей текст совпадает с текстом самого вызова, отбрасывается: в графе вызов иногда виден среди своих аргументов.

Затем для каждого текста ищутся выражения размера. Если есть присваивание, у которого слева ровно этот текст, берётся правый ребёнок. Плюс сам узел аргумента, если формула написана прямо в вызове. Для `calloc(1, pmssize)` полезный аргумент — `pmssize`. У присваивания `pmssize = ...` правый ребёнок — сумма с `blockalign` и `samplesperblock`. Как и в CodeQL, раскрывается один шаг.

### Связка проверки и размера

```scala
val guarded = method.controlStructure
  .controlStructureType(ControlStructureTypes.IF)
  .condition
  .flatMap(c => weakCheck(c).toList)
  .map(_._1)
  .toSet
val matched = allocArgCodes(method).exists { argCode =>
  sizeExprs(method, argCode).exists { root =>
    val (addends, factors) = operands(root)
    val samples = factors -- addends - blockName -- rightIds
    addends.contains(blockName) && samples.exists(sample => !guarded.contains(sample))
  }
}
```

`guarded` — все имена, которые в этой функции уже стоят слева в таком же слабом `if`.

Для выражения размера считается разность:

- из множителей убираются те, кто одновременно слагаемые;
- убирается само имя слева в текущем `if`;
- убираются имена, которые уже стоят справа в этом `if`.

Остаток — кандидаты в непроверенный множитель `S`. Находка есть, если имя слева входит в слагаемые и хотя бы один кандидат не входит в `guarded`.

На 1.0.30 слева `blockalign`, он есть среди слагаемых. `samplesperblock` остаётся среди кандидатов, и в `guarded` его нет. Строка попадает в список.

На 1.1.0 слабый `if` слева имеет `samplesperblock`. Среди слагаемых размера этого имени нет, `addends.contains(blockName)` ложно. Второй `if` первым ребёнком имеет умножение и в `weakCheck` не проходит. Список пустой.

Дальше скрипт пишет файл вида `файл:строка: текст условия` и число находок. Сортировка и `distinct` убирают повторы, если один `if` подошёл к нескольким аргументам аллокатора.

## Пример, на котором видно, что семёрка и имена не зашиты

Файл `rules/fixtures/msadpcm-shape.c`. Имена другие: `chunk`, `nframes`, `channels`. Три функции.

Уязвимая форма с множителем 7:

```c
int open_block(int chunk, int nframes, int channels)
{
	unsigned size;

	if (chunk < 7 * channels) {
		return -1;
	}

	size = sizeof(int) + chunk + 3 * channels * nframes;
	if (!calloc(1, size))
		return -1;
	return 0;
}
```

Та же форма с множителем 8, `open_block_eight`:

```c
if (chunk < 8 * channels) {
    return -1;
}
size = sizeof(int) + chunk + 3 * channels * nframes;
```

Если бы правило искало текст `7` или имя `blockalign`, вторая функция была бы невидима. Она находится всеми тремя.

Исправленная форма, `open_block_fixed`, повторяет 1.1.0:

```c
if (nframes < 7 * channels)
    return -1;
if (2 * chunk < nframes * channels)
    return -1;

size = sizeof(int) + chunk + 3 * channels * nframes;
```

Слева в сравнении с произведением стоит `nframes`. В сумме `nframes` — множитель, слагаемое — `chunk`. Второе сравнение слева имеет вид `2 * chunk`. Оба свойства, которые правило требует вместе, здесь не собираются. Находок нет, хотя литерал `7` в функции остался. Это прямой ответ на вопрос «вы просто ищете семёрку».

| libsndfile 1.1.0 | 0 | 0 | 0 |

Семёрка в тексте находки на 1.0.30 есть, потому что она есть в исходнике. В шаблоне её нет. Рядом находка с восьмёркой.

## Что правило не делает

Правило не доказывает выход за границу массива. Оно не строит путь от байта заголовка до записи `pms->samples[sampleindx++]`. Этот путь показывает PoC: файл на 2660 байт, 226 каналов, `blockalign` 2592, `samplesperblock` 10. На 1.0.30 ASan сообщает запись двух байт за областью в 9428 байт. На 1.1.0 тот же файл отклоняется текстом `samplesperblock (10) should be >= 1582`.

Правило не заменяет штатные запросы CWE-120, CWE-190, CWE-129, CWE-457 и CWE-468. Те ищут свои классы ошибок по всей библиотеке. Это правило отвечает на один вопрос: есть ли слабая проверка слагаемого при непроверенном множителе размера.

Раскрытие размера останавливается на одном присваивании. Второе присваивание по пути от формулы к `malloc` правило не пройдёт.

Три записи исправления, при которых форма перестаёт совпадать:

- слева не голая переменная, как `2 * blockalign < ...`;
- с произведением сравнивается множитель, как `samplesperblock < 7 * channels`, а слагаемое больше так не сравнивается;
- проверяется только цикл `while (blockindx < blocksize) samples[sampleindx++]`: он одинаковый в 1.0.30 и в 1.1.0, и такая проверка есть ещё в IMA ADPCM.

semgrep дополнительно привязан к виду суммы `$HEAD + $BLOCK + $K * $MID * $COUNT`. CodeQL и joern смотрят на роли операндов и переживут другую расстановку слагаемых, если `B` останется операндом сложения, а `S` — операндом умножения.

1. Показать строки 131–138 в 1.0.30 и сказать: слева `blockalign`, это слагаемое `pmssize`, а `samplesperblock` входит в размер только множителем и своим `if` с произведением не ограничен.

4. Показать связку с размером: `isAddend` / `isFactor` в QL или множества `addends` и `factors` в Scala. Сказать про один шаг от `pmssize` к правой части присваивания.
