## 2. Теория на пальцах

### 2.1. Что проверяет эта работа

Задание смешивает два режима.

**Белый ящик** — исходный код есть. Читаешь манифест, Gradle и Java, сверяешь с MASVS и пишешь, что сломано и как починить. Запускать приложение не обязательно: ошибка видна в тексте.

**Чёрный ящик** — есть только APK. Код восстанавливаешь декомпиляцией, поверхность атаки берёшь из манифеста, поведение проверяешь на эмуляторе, а подозрительные места подтверждаешь или опровергаешь инструментом.

**SAST** здесь — FlowDroid, Trueseeing, APKHunt, разбор androguard. Они не запускают почту. **DAST** в этой работе — эмулятор и Frida: приложение реально открывает письмо, а скрипт записывает вызов.

Срабатывание статического инструмента — гипотеза. Доказательство в этой работе другое: фрагмент исходника mfva, открытое письмо на скриншоте, строка `openInputStream` в трассе, библиотека в карте модулей.

::: say
«Белый ящик — это чтение исходников mfva по разделам MASVS. Чёрный ящик — APK почты: декомпиляция, манифест, эмулятор и Frida. Статический анализатор даёт гипотезу. Открытое письмо и строка openInputStream в трассе — уже наблюдение, а не гипотеза».

### 2.2. MASVS, MSTG и Kotlin-SCP

Это три разных документа об одном и том же.

| Документ | Что это | Как использован |
|---|---|---|
| **MASVS** | стандарт: что должно быть верно в приложении | Восемь категорий v1 как оглавление разбора mfva |
| **MSTG** | руководство: какими тестами это проверять | Те же категории, уже как проверки Android |
| **Kotlin-SCP** | правила безопасного кода на Kotlin | mfva на Java, правила перенесены по смыслу |

Категории MASVS v1, по которым написан раздел 5 отчёта:

1. Архитектура и модель угроз.
2. Хранение данных и приватность.
3. Криптография.
4. Аутентификация и сессии.
5. Сетевое взаимодействие.
6. Взаимодействие с платформой.
7. Качество кода и параметры сборки.
8. Устойчивость к анализу. Для уровня L1 этот раздел не обязателен.

MSTG содержит десятки тестов с номерами вроде MSTG-STORAGE-1. В отчёте номера тестов не подставлены там, где по коду нельзя честно сослаться на конкретный идентификатор. На защите это лучше сказать прямо: разбор идёт по категориям стандарта, а не по распечатке всех идентификаторов MSTG.

Kotlin-SCP говорит то же, что и разбор mfva: секрет не хранить в исходнике, JavaScript в WebView не включать без нужды, компонент не открывать без разрешения, DES и MD5 не использовать, токен по HTTP не отправлять.

::: say
«MASVS говорит, что проверять. MSTG говорит, как проверять. Kotlin-SCP — те же ошибки для Kotlin. mfva написан на Java, поэтому правила перенесены по смыслу. Разбор идёт по восьми категориям MASVS v1».
:::

### 2.3. Компоненты Android и флаг exported

Чужое приложение попадает в цель через четыре вида компонентов:

- **Activity** — экран. Запуск через `startActivity` и Intent.
- **Service** — работа без экрана. Запуск или `bindService`.
- **BroadcastReceiver** — приёмник широковещательного Intent.
- **ContentProvider** — чужие данные по URI, методы `query`, `insert`, `update`, `delete`.

`android:exported="true"` разрешает запуск снаружи. Intent-filter без явного `exported` на старых targetSdk тоже открывает компонент. С targetSdk 31 компонент с фильтром обязан объявить `exported` явно, иначе приложение не ставится. У почты targetSdk 33, у mfva targetSdk 30.

**Permission** на компоненте означает: вызвать может только тот, у кого есть это разрешение. Если тега `<permission>` с таким именем в манифесте нет, обычное приложение себе это разрешение не получит. Компонент выглядит открытым по имени, а снаружи закрыт. Это главный нюанс mfva.

Подпись **signature** означает: разрешение получит только приложение, подписанное тем же ключом. Так закрыта часть компонентов Passport в почте (`com.yandex.permission.READ_CREDENTIALS`).

`adb shell am start` с корня эмулятора — это не чужое приложение. С корня можно стартовать и неэкспортированную активность. В работе так запущен сканер документов. В отчёте это сказано: обычное стороннее приложение так сделать не может.

### 2.4. Source и sink

**Source** — место, куда попадают данные, на которые влияет кто-то снаружи: `Intent.getData()`, `openInputStream`, extras, курсор провайдера, сеть, файл, который пользователь открыл.

**Sink** — место, где эти данные становятся опасными: `Runtime.exec`, SQL, `WebView.loadUrl`, `addJavascriptInterface`, запись в файл, отправка на сеть, вызов native-метода.

Задание прямо говорит: вызовы native-функций относить к стокам. Скрипт `audit_apk.py` поэтому пишет их ещё и в формате FlowDroid, файл `results/native-sinks.txt`. В файл, которым реально кормили FlowDroid, эти строки не подмешивались.

Цепочка, которую просят найти:

```text
source (Intent / файл / сеть)
    → код приложения
    → sink (WebView, SQL, exec, native)
```

Для письма цепочка короткая и до native не доходит:

```text
ACTION_VIEW на file://…/lab5-external.eml
    → EmlActivity.onCreate
    → ContentResolver.openInputStream
    → разбор письма в Java
    → текст в WebView
```

Для сканера цепочка другая и к письму не привязана:

```text
запуск DocScannerCameraActivity, bundle == null
    → System.loadLibrary("camera360-arcadia")
    → библиотека отображена из base.apk
```

Дальше, до вызова конкретной JNI-функции на кадре, трасса не идёт.

::: say
«Источник письма — Intent.getData и openInputStream в EmlActivity. Сток этого пути — разбор потока и отдача текста в WebView. Native-вызовы я тоже считаю стоками, их 339, но письмо до них не доходит. Сканер грузит другую библиотеку, camera360, и это отдельный сценарий».
:::

### 2.5. Декомпиляция

APK содержит DEX, ресурсы и манифест в бинарном виде. **JADX** поднимает из DEX Java-подобный текст. Это не исходник автора: имена часто обфусцированы, часть методов не восстанавливается.

В прогоне APKHunt сам вызвал JADX и dex2jar. Его JADX закончил строкой `finished with errors, count: 267`. Классы `EmlActivity`, `DocScannerCameraActivity`, `OfflineCalendarActivity` и константу SpeechKit открывай в окне JADX: `lab5/scripts/jadx-mail.sh`. Выгруженное дерево `lab5/sources/yandex-mail` удалено. Дерево того прогона APKHunt лежит в `lab5/results/apkhunt/yandex-mail-8-81-2_SAST/` и в git не входит.

**apktool** и **androguard** нужны для манифеста и байткода. Подсчёты отчёта сняты androguard, не глазами по XML.

### 2.6. Frida

**Frida** — динамическая инструментация. На устройстве работает `frida-server`, на хосте — клиент. Скрипт на JavaScript цепляется к процессу и подменяет методы или смотрит память.

Два способа подключения:

- **spawn** (`frida -f пакет`) — процесс стартует под отладчиком с самого начала;
- **attach** (`frida -p PID`) — скрипт садится на уже живой процесс.

У этой почты spawn до `Java.perform` не доходит. Итоговая трасса — attach. В `frida-ps` процесс называется `Yandex Mail`, а не `ru.yandex.mail`, поэтому в команду идёт pid.

Клиент и сервер обязаны быть одной версии. Здесь оба **17.4.0**, архитектура сервера `android-x86_64`. Клиент 16.7.19 из venv анализа к этому серверу не подходит.

Сессия Frida живёт, пока открыт stdin. Команда в фоне с `&` сразу получает EOF, печатает `Thank you for using Frida` и выходит. Поэтому сессию держали так: `sleep N | frida ...`.

Что ломает эту почту, если хукнуть слишком широко:

- подмена `System.loadLibrary` роняет создание WebView в `EmlActivity` (`InflateException`);
- хук на все `Activity.onCreate` роняет тот же экран;
- хук `android_dlopen_ext` в Frida 17.4 роняет процесс;
- подмена native-методов `EyeNative` убивает процесс.

В итоговом `trace.js` этих хуков нет. Включены только `EmlActivity.onCreate`, `DocScannerCameraActivity.onCreate` и `ContentResolver.openInputStream`. Появление библиотек скрипт смотрит опросом карты модулей. В той сессии карта агента библиотеку не показала (`watched=0`). Сразу после неё новый attach к тому же pid библиотеку увидел.

::: say
«Frida пишет трассу живого процесса. Клиент и сервер оба 17.4.0. Подключался attach по pid, потому что имя процесса — Yandex Mail, а spawn до Java.perform не доходит. Хук на все Activity и подмена loadLibrary роняют WebView, поэтому в итоговой трассе только две активности и openInputStream».
:::

### 2.7. JNI, native и OSS внутри .so

Метод с флагом `ACC_NATIVE` (0x100) не имеет байткода. При вызове JVM ищет соответствующую функцию в загруженной `.so`. Загрузка — `System.loadLibrary("имя")` или `System.load("путь")`.

Имя библиотеки и имя Java-пакета связаны соглашением JNI, но в этом APK связь восстановлена по строкам `loadLibrary` рядом с классами, а не по всем 339 методам вручную:

| Префикс класса | Методов | Библиотека в APK |
|---|---|---|
| `ru.yandex.speechkit` | 110 | `libYandexSpeechKitJni.4.15.7.so` |
| `org.webrtc` | 89 | `libjingle_peerconnection_so.so` |
| `ru.yandex.dict` | 78 | `libcamera360-arcadia.so` |
| `org.sqlite.core` | 38 | имя `sqlitejdbc`, файла `.so` нет |
| `com.yandex.metrica` | 16 | имена `appmetrica-*-native`, файлов нет |
| `com.yandex.eye` | 8 | `libeye.so` |

**OSS-компонент** внутри `.so` ищут по строкам: пути исходников, баннеры, имена функций. Номер версии пишут только если он реально есть в строке или в имени файла. OpenCV виден по путям `contrib/libs/opencv`. Номера версии в строках нет. BoringSSL виден по путям `third_party/boringssl` и строкам CRYPTOGAMS. Номер релиза OpenSSL ей приписывать нельзя: это не OpenSSL. SpeechKit 4.15.7 взят из имени файла `libYandexSpeechKitJni.4.15.7.so`.

`extractNativeLibs=false` значит, что библиотека может остаться внутри APK и отображаться как `base.apk!/lib/x86_64/...`. Именно так виден путь `libcamera360-arcadia.so` в трассе.

### 2.8. FlowDroid

**FlowDroid** — статический taint-анализ для Android поверх Soot. Он строит граф вызовов, размечает источники и стоки из текстового файла и ищет пути, по которым метка доходит от источника до стока.

Файл источников и стоков в прогоне — штатный Android-набор, 460 строк: `getIntent`, курсоры, `Log`, `startActivity` и соседние методы платформы. Свои 339 native-стоков туда не добавлялись.

Результат — XML. Один элемент `Result` — один найденный путь: сток и список источников. Консоль написала:

```text
Data flow solver took 86 seconds. Maximum memory consumption: 8512 MB
Found 18 leaks from 36 sources
```

В XML атрибут `TerminationState="DataFlowOutOfMemory"`. Файл на диске — повторный прогон: `TotalRuntimeSeconds=340`, `MaxMemoryConsumption=8379`, те же 18 путей и 36 источников. Цифры 86 с и 8512 МБ — консоль прогона, которую цитирует отчёт. Таймаут 480 с не сработал. Анализ остановился, потому что кончилась куча, а не потому что он перебрал всё приложение.

18 путей — это то, что успело записаться. Среди них нет `EmlActivity`, `openInputStream`, `camera360`, SpeechKit и WebRTC. Отсутствие пути в оборванном прогоне не доказывает, что пути нет. Для письма доказательство другое: в `onCreate` нет `loadLibrary` и native-вызовов, и трасса после `openInputStream` библиотеки APK в процесс не ввела.

::: say
«FlowDroid ищет путь от источника к стоку по штатному списку Android. Он напечатал 18 путей за 86 секунд работы решателя и оборвался по памяти: в XML стоит DataFlowOutOfMemory. Письма среди этих 18 нет. Что письмо не вызывает native, я показываю по коду EmlActivity и по трассе, а не по оборванному прогону».
:::

### 2.10. Три частые путаницы

**Путаница 1: срабатывание и уязвимость.** 8068 строк Trueseeing и 1451 вхождение `Log` у APKHunt — это не 8068 дыр. Инструмент посчитал шаблон. В отчёте разобраны группы Medium и Low и отдельно сказано, какие из них не подтверждаются манифестом.

**Путаница 2: «APKHunt написал 0 exported».** Инструмент так напечатал по всем четырём видам компонентов. В манифесте, который он сам записал, у псевдонима `ru.yandex.mail.ui.LoginActivity` стоит `android:exported="true"`, и таких атрибутов 43. Поверхность атаки берётся из подсчёта androguard в разделе 8 отчёта.

**Путаница 3: cleartext.** В ресурсах есть `res/xml/network_security_config.xml` с `cleartextTrafficPermitted="true"`. Тег `<application>` на этот файл не ссылается, `usesCleartextTraffic` не задан, targetSdk 33. Рабочей политикой этот XML не является. Trueseeing и APKHunt ставят находку по факту наличия файла. Это надо говорить именно так.

Ещё одна, уже про mfva. Имена `UnprotectedService` и `UnprotectedReceiver` описывают намерение автора, а не фактический доступ. На обоих висит необъявленное `CustomPermission`. Снаружи закрыты они, а открыты `ExportedService` и `ExportedReceiver`.

## 4. Как всё работает по шагам

### 4.1. Белый ящик: mfva

Исходники: `lab5/sources/mfva`. Сборка `compileSdk 30`, `minSdk 25`, `targetSdk 30`, `versionName 1.0`, `versionCode 6`. Зависимости: OkHttp 3.8.0, Jedis 2.9.0, AppCompat 1.0.0. `minifyEnabled` выключен. Отдельного прогона и кода возврата у этого шага нет: это чтение восьми классов и манифеста.

Что говорить по категориям, коротко.

**Хранение.** `android:allowBackup="true"`. Кнопка пишет системное свойство в `SharedPreferences` с именем `pref` и режимом `0`, это `MODE_PRIVATE`. `FLAG_SECURE` нет. `Log.d("YOLO", quote)` пишет отладочную строку в logcat.

**Криптография.** MD5 считается, а на экран попадает `hash.toString()` у массива байт, то есть идентификатор объекта, а не дайджест. Шифрование:

```java
SecretKey keyspec = new SecretKeySpec("Gangnam!".getBytes(), "DES");
Cipher c = Cipher.getInstance("DES/ECB/ZeroBytePadding", "BC");
```

DES, ECB, ключ из восьми символов в исходнике. Провайдера `BC` в `build.gradle` нет, вызов на устройстве падает. Параметры алгоритма от этого не становятся нормальными. MD5 без `BC` считается штатным провайдером.

**Аутентификация и сеть.** `ApiRequestsActivity` шлёт `user1` / `pass1` на `http://vapi.appknox.io/tokens`. Пароль нового пользователя — `pass0`. Токен показывается в `TextView` и уходит заголовком `X-Auth-Token` по HTTP. Своего `networkSecurityConfig` нет. На API 28+ ясный текст по умолчанию запрещён, так что на современном устройстве запрос, скорее всего, не уйдёт. Исходник требование «не передавать секрет открытым каналом» всё равно нарушает.

**Платформа.** WebView включает JavaScript и открывает `http://example.com`, своего `WebViewClient` нет.

| Компонент | exported | Что с доступом |
|---|---|---|
| `ExportedActivity` | true | permission не объявлен, снаружи закрыт. Внутри `Jedis("localhost")` без пароля и тот же DES |
| `UnprotectedService` | true | то же необъявленное permission, снаружи закрыт |
| `UnprotectedReceiver` | true | имя обманчиво, снаружи закрыт |
| `ExportedService` | true | разрешения нет. `onBind` бросает `UnsupportedOperationException` |
| `ExportedReceiver` | true | разрешения нет. Явный broadcast дойдёт, URI intent пишется в лог и в Toast |
| `StubProvider` | true | закрыт тем же permission. Authority `com.example.android.datasync.provider` не совпадает с пакетом |

`RECEIVE_BOOT_COMPLETED` приложение не просит, системный boot оно не получит.

**Что легко забыть на вопросе.** В манифесте есть `ACCESS_FINE_LOCATION` и `BLUETOOTH`, в Java использования нет. У провайдера `grant-uri-permission` на `path="/"`. В отчёте этих двух строк нет. Если спросят «все ли разрешения разобраны», скажи про них.

Исправления, которые уже написаны в отчёте: `allowBackup=false`, AES-GCM и ключ в Android Keystore, пароль из ввода, только HTTPS, `exported=false` или настоящее signature-permission, JavaScript выключен, `onBind` возвращает `null`.

::: say
«Самые прямые ошибки mfva: DES/ECB с ключом Gangnam!, MD5, который ещё и печатается как toString массива, пароли user1, pass1, pass0 и токен по HTTP, allowBackup и WebView с JavaScript. CustomPermission не объявлен, поэтому Unprotected-компоненты снаружи закрыты. Открыты сервис, чей onBind бросает исключение, и приёмник без разрешения».
:::

## 6. Вопросы преподавателя и короткие ответы

**1. Какой вариант и какие приложения?**
Вариант 11. Белый ящик — mfva, пакет `com.appknox.mfva`. В таблице написано mvfa, ссылка [14] ведёт на репозиторий mfva. Чёрный ящик — Yandex Mail 8.81.2, пакет `ru.yandex.mail`, versionCode 105397.

**2. Почему не Mail 8.78.1 из второго архива?**
В столбце варианта указана сборка 8.81.2 из `AndroidApps4Research`. Хеш файла в работе совпадает с этой сборкой. 8.78.1 не ставилась.

**3. Чем MASVS отличается от MSTG?**
MASVS — список требований. MSTG — как эти требования проверять на Android и iOS. В отчёте восемь категорий MASVS v1. Kotlin-SCP разобран по смыслу, потому что mfva на Java, файлов Kotlin в нём нет.

**4. Назовите три уязвимости mfva и как их исправить.**
DES/ECB с ключом `Gangnam!` в исходнике — заменить на AES-GCM, ключ положить в Android Keystore. Пароли `user1`/`pass1`/`pass0` и токен по HTTP — пароль брать из ввода, канал только HTTPS, токен не печатать на экран. `ExportedReceiver` без разрешения — `exported=false` или signature-permission. Рядом стоит WebView с JavaScript на `http://example.com`.

**5. Почему UnprotectedReceiver на самом деле закрыт?**
На нём висит `android:permission="com.appknox.mfva.CustomPermission"`, а тега `<permission>` с таким именем нет. Чужое приложение не может получить несуществующее разрешение, система вызов не пропустит. Имя класса описывает задумку автора, а не фактический доступ.

**6. Что тогда реально открыто в mfva?**
`ExportedService`: разрешения нет, `onBind` бросает `UnsupportedOperationException`. Это отказ в обслуживании при bind. `ExportedReceiver`: разрешения нет, явный broadcast доходит, приёмник пишет URI intent в лог и в Toast. Системный `BOOT_COMPLETED` приложение не получит, разрешения `RECEIVE_BOOT_COMPLETED` у него нет.

**7. Почему DES в mfva может не выполниться, но это всё равно находка?**
`Cipher.getInstance(..., "BC")` просит провайдер Bouncy Castle. В `build.gradle` его нет, исключение перехватывается. На устройстве шифрование падает. В коде остаются DES, ECB, ZeroBytePadding и ключ в исходнике. MD5 без провайдера `BC` выполняется.

**8. Что такое source и sink в этой работе?**
Source — место чтения данных, на которые влияет внешний субъект. Для письма это `Intent.getData` и `openInputStream`. Sink — опасная операция. Задание относит к стокам и native-вызовы. Их 339. Путь письма заканчивается в Java и в WebView, до native не доходит.

**9. Почему внешние данные — именно eml, а не ссылка из сети?**
`EmlActivity` экспортирована, permission нет, фильтр принимает `VIEW` на `message/rfc822`, `application/eml` и путь `.eml`. Это прямой вход недоверенного файла. Сценарий воспроизводится без аккаунта и без сервера.

**10. Почему файл лежит в приватном каталоге почты, а не на sdcard?**
На API 34 чужой `file://` из общего хранилища просмотрщик часто не отдаёт. Файл положен в `/data/data/ru.yandex.mail/files/` от имени uid приложения, режим 640. Это стендовый способ отдать активности тот URI, который она умеет открыть. Для чужого приложения рабочий путь — `content://`.

**11. Что именно видно в трассе Frida?**
Pid 9066. `EmlActivity.onCreate` с action `VIEW`, типом `message/rfc822` и data на `lab5-external.eml`. Следом `openInputStream` на тот же URI. Потом `DocScannerCameraActivity.onCreate` с `bundleNull=true`. Снимки библиотек в этой сессии: `watched=0`.

**12. Где доказательство, что библиотека вообще загрузилась?**
Второй attach к тому же pid, файл `modules-pid9066.log`: `libcamera360-arcadia.so` по пути `base.apk!/lib/x86_64/libcamera360-arcadia.so`. Это согласуется с `extractNativeLibs=false`. В коде сканера при пустом bundle первая содержательная строка — `System.loadLibrary("camera360-arcadia")`.

**13. Почему нет трассы входа в JNI?**
Хук `android_dlopen_ext` ронял процесс. Подмена `System.loadLibrary` роняла WebView письма. Подмена методов `EyeNative` убивала процесс. В итоговой трассе этих хуков нет. Карта модулей долгоживущего агента загрузку не показала. Факт загрузки есть, вызова функции на кадре нет. На защите так и говорю.

**14. FlowDroid нашёл 18 утечек. Письмо среди них есть?**
Нет. 18 элементов `Result` и 36 элементов `Source` в XML есть, консоль отчёта написала ту же пару чисел: решатель 86 секунд, пик 8512 МБ. В корне XML стоит `TerminationState="DataFlowOutOfMemory"`. Файл на диске — повторный прогон: 340 секунд и 8379 МБ. Прогон оборвался. Эти 18 путей — аналитика, курсоры, кэш и выбор компонента. Отсутствие письма в этом списке не доказательство само по себе. Доказательство для письма — код `EmlActivity` и трасса.

**15. Почему native-методы не попали в FlowDroid?**
Скрипт выписал их в `results/native-sinks.txt` в формате стока. В `SourcesAndSinks.txt`, который передан флагом `-s`, эти 339 строк не добавлялись. Поэтому FlowDroid на достижимость native не отвечает. Её разбирал вручную.

**16. Как устроено средство, которое перечисляет native-методы?**
`lab5/scripts/audit_apk.py` на androguard. Оно обходит DEX, берёт методы с флагом `ACC_NATIVE` и печатает класс, имя и JNI-дескриптор. Итог: `results/natives.txt`, 339 строк определений. Отдельный JEB не использовался. Задание разрешает androguard.

**17. Какие OSS-библиотеки и какие версии?**
OpenCV внутри `libcamera360-arcadia.so`, номера версии в строках нет. В `libjingle_peerconnection_so.so` — WebRTC, BoringSSL, libyuv, libvpx, Opus и соседние кодеки, номер релиза BoringSSL не назван. SpeechKit 4.15.7 — из имени файла. libpng во всех четырёх файлах: 0 совпадений.

**18. Откуда ключ SpeechKit и что с ним сделано?**
Константа `SPEECHKIT_API_KEY` в классе `com.yandex.mail.l`, она передаётся в `native_init`. Значение приведено в разделе 13 отчёта. Запрос к API не отправлялся. Исправление: убрать ключ из клиента, выдавать короткоживущий токен, уже утекший ключ отозвать.

**19. Почему APKHunt пишет ноль экспортированных компонентов?**
Так напечатана его сводка по активностям, провайдерам, приёмникам и сервисам. В манифесте, который лежит в дереве того же прогона, `android:exported="true"` есть, у одного только псевдонима входа он уже стоит. Для цифр поверхности атаки я пользуюсь androguard: 20 активностей с входом, 12 сервисов, 29 приёмников, 3 провайдера.

**20. Разрешает ли почта cleartext?**
Файл `network_security_config.xml` содержит `cleartextTrafficPermitted="true"`. Тег `application` на него не ссылается, своего `usesCleartextTraffic` нет, targetSdk 33. С API 28 ясный текст по умолчанию запрещён. Trueseeing и APKHunt отмечают файл. Рабочей политикой он не является. Исправление в отчёте: удалить файл или подключить явно и убрать cleartext, чтобы следующий рефакторинг его не включил.

**21. Почему нет MobSF и SEBASTiAN?**
Оба в наборе OWApp запускаются через Docker. Сокета Docker на машине нет, sudo нет, `DownloadScript.sh` набора начинается с `apt-get`. Прогнаны те два средства, которые живут без Docker: Trueseeing и APKHunt. Файла `download_script.py` в репозитории набора нет, локальный скрипт только кладёт APK жёсткой ссылкой.

**22. Что из автоматических находок вы считаете стоящим исправления?**
Семь пунктов из раздела 17 отчёта. Первые по смыслу: убрать ключ SpeechKit из клиента, выключить file URL в WebView офлайн-календаря, сузить экспорт `EmlActivity`, убрать тестовые активности Compose и AndroidX из release, закрыть `SsoContentProvider`, не оставлять неподключённый cleartext-XML, разобрать `processBufferBug` в `libeye`.

**23. Чем статический анализ здесь отличается от динамического?**
FlowDroid, Trueseeing и APKHunt читают APK и не открывают письмо. Эмулятор и Frida открывают конкретный файл и записывают конкретный вызов. Статика дала 18 путей и тысячи срабатываний. Динамика подтвердила один сценарий: просмотр `.eml`.

**24. Можно ли этим отчётом пользоваться как инструкцией по атаке на боевую почту?**
Нет. Это разбор учебной сборки 8.81.2 и учебного mfva. Запросы к API SpeechKit не отправлялись, аккаунт не заводился, эксплуатация не разрабатывалась. Рекомендации в отчёте — про исправление кода.

**25. Что вы не успели или не смогли?**
Вход в JNI на кадре сканера. Полный прогон FlowDroid до конца: он оборвался по памяти, и native-стоки в него не входили. MobSF и SEBASTiAN. Загрузку `libeye`, WebRTC и SpeechKit: для них нужен аккаунт, звонок или голосовой ввод. Разбор чёрного ящика по всем идентификаторам тестов MSTG по отдельности: он собран по шагам задания и по найденным местам, а не по полной простыне номеров тестов.
